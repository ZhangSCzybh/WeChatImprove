# 聊天分组 CPU、内存与耗电风险审计：1.7-8

审计日期：2026-10-17。源码：`45e3ff8521f20821af276cede1da00e878120350`；`control` 为 `1.7-8`，开始时工作区干净。核心 Adapter、NativeBridge、Projection、Preferences、TabContainer 和 SessionGroupHooks 与 `0ebe90ba`（1.6-35 两阶段优化交付）的文件内容相同。本次只新增报告和隔离分析证据，不修改生产代码、安装包、微信数据，也没有连接手机测量。

**结论：** 常规主列表没有常驻周期性全量扫描或逐帧数据计算。主要耗电风险来自前台持续收消息时反复全量读取和重建，以及条件性刷新重试。离开主列表后已有暂停保护。设置页面另有每秒账号检查。指示器只做有限时长动画，优先级明显低于刷新调度和全量计算。不能从源码或 Mac 基准直接推导手机 CPU 百分比、耗电率或温升。

## 哪些行为会持续发生

| 场景 | 分组额外行为 | 停止条件与风险 |
| --- | --- | --- |
| 主列表静止，没有模型/设置事件 | 保留快照、投影、按钮、手势和代理；没有自主刷新循环 | 常驻内存不等于持续 CPU/GPU 工作 |
| 主列表持续收消息、未读变化 | Hook 包装原生事件，失效缓存，40ms 合并后全量刷新；部分入口立即调度 | 消息停止且没有新失效时停止；这是主要常规 CPU 风险 |
| 滚动分组列表 | 代理转发、可见行身份复核、原生布局和绘制 | 由滚动/原生回调驱动；不是每帧遍历全部会话 |
| 已有刷新请求，手指按住/分组手势运动/菜单动画 | 约 50ms 后重试刷新准入 | 交互结束或离屏；静止展开的菜单不持续轮询；运动标志异常不结束时存在长时间轮询风险 |
| 进入具体聊天、通讯录等，主列表触发消失生命周期 | 普通通知仅标脏、更新代次和结束批处理，不发布列表 | 原生消息处理仍执行；显式原生导航是受控例外 |
| 分组设置页显示 | 1 秒账号检查一次；账号没变立即返回 | `viewWillDisappear` 和 `dealloc` 停止；不每秒扫描会话 |
| 切组 | 轻量保存选中项，重建投影/角标/列表；有有效快照时复用 | 单次动作；快速连续切组会累积计算需求 |
| 指示器动画 | Core Animation 的位置和尺寸动画，约 0.26s | 不重复；离开 window/关闭动画/减少动态效果有停止或跳过路径 |
| 编辑自定义成员/联系人搜索 | 读取并排序联系人，输入时筛选联系人；保存定义有校验/备份/同步 | 只在对应设置操作执行，不能解释正常聊天页持续计算 |

“主列表离屏”与“App 进入系统后台”是两件事。暂停标志来自控制器生命周期（`SessionGroupHooks.xm:59–76`），未发现分组模块独立注册 App 后台/前台状态并作为刷新准入条件。不能假定所有切后台场景一定触发这组消失回调。若微信仍获准短时后台处理且控制器标志未暂停，事件仍可能进入前台刷新路径；iOS 完全挂起后这些代码不会继续执行。模块本身未申请后台保活或网络轮询。

## 1. 主要风险：消息驱动的全量主线程刷新

入口：`Hooks/SessionGroupHooks.xm:90–99`、`:181–188`、`:297–345`。

发布：`Controllers/CSGroupListAdapter.m:348–440`；快照构建：`Controllers/CSGroupNativeBridge.m:157–206`。

一次有效数据刷新会：

1. 在主线程读取全部原生会话的身份、联系人分类、置顶、未读、红点；多个数值 getter 使用 `NSMethodSignature`、`NSInvocation`。
2. 新建全量不可变行快照。
3. `CSGroupProjection` 重建成员反向索引，验证并复制每一行，计算所有显示分组的未读数和当前分组坐标映射。
4. 重建当前分组身份索引，更新分组栏和标题。
5. 无条件执行该表的 `reloadData`、`layoutIfNeeded`，必要时恢复定位。这里的整表重载不是创建全部行的 cell，但会触发可见 cell、行高、布局等原生工作。

没有按“仅未读变更 / 内容变更 / 顺序或成员结构变更”区分增量处理，也没有在当前组列表没有变化时跳过表重载。来自其他分组的消息同样可以触发。选择只有两条会话的分组，不能把全局读取和所有角标统计降为两条。

复杂度以 N=原生会话数、M=自定义成员关联总数、V=当前组行数表示，主体为 O(N+M+V)，还包含会话对应各目标组的累计成本；不是普遍固定的 N×G 双重遍历，但大量重复归组会增加 M 和分配量。

40ms 是首事件合并窗口，不是统一“最多每秒 25 次刷新”的保障。只考虑便宜且纯被动通知路径时窗口能减少发布频率；直接请求可提前执行，`updateItem`、行更新等路径不走同一窗口。实际频率由事件分布、入口、交互状态和主线程执行时长决定。

即使开启“隐藏角标”，代码也是先完整构建 `projection`，再把显示值改成 0（Adapter:418–424）；隐藏角标目前不会省去角标统计。单纯关闭指示器动画也不减少全量刷新。

## 2. 条件性风险：无退避的刷新反馈与交互重试

**交互重试（已验证调度行为）：** Adapter:359、:360–364、:464–486。已有 dirty 工作时，只要 tracking / groupPanMoving / 菜单运动状态存在，会安排约 50ms 的下一次检查。菜单状态检查遍历可见 cell；dirty 时还复核会话身份。约 20 次/秒是单条持续重试链的理论调度频率，不是测得整机唤醒次数；手势回调还可追加检查，系统调度也可能更慢。

正常手势结束后退出，离屏也退出；静止菜单打开只保留 dirty，不持续轮询。若原生 `_inHideAnimation` 等状态异常保持，则缺少最长时间或次数限制。

**刷新反馈（已验证调度可连锁，触发条件需真机确认）：** Adapter:661–676 取不到 cell 会返回占位 cell 并请求刷新，:730–734 映射失败可请求刷新；:439 在发布结束发现 dirty 会立即安排下一轮。请求期间也失效原生快照。若同样的原生 cell 获取/身份映射错误持续存在，而新快照仍允许发布，可能变成“重载 → 失败 → 重载”，没有错误级退避或按模型代次止损。

隔离 fixture 每次发布注入一次失效，生产调度代码在 100ms 观察窗口中完成 12 次链式发布，测试主动在第 12 次停止。这只证明调度器允许该反馈，不证明实际微信正在返回 nil，也不是实际全量发布耗时。真实重建会更慢，但仍可能持续占用主线程。

另一个 `projectionForSections` 的 50ms 快照重试已有单次限制（Adapter:442–462），不能把它误报成无限重试。两类路径必须分开。

## 3. 高频滚动和分组栏的额外工作

- Adapter:678–743 的通用代理对滚动回调也执行 `NSInvocation`、选择器分类、参数映射准备和线程作用域维护。Mapper:32 开始即使不含行参数也会走通用准备路径。明确无坐标参数的滚动回调有直接转发优化空间。
- Adapter:538–548、NativeBridge:62–130 的行身份复核会调用账号/会话 getter。这是避免删除后误操作的安全保护，不能为性能直接删除。可按同账号、同模型代次复用已验证映射，模型一变就失效。
- `updateTabs` 每次发布都会执行，即便分组定义未变（TabContainer:282–332）：复用按钮但仍遍历、`addSubview`、刷新颜色、请求并执行布局。外观刷新在有颜色 NSData 时重新解档 UIColor（:164–190）。布局测量所有标签文字宽度（:252–279）。标题/字体/未读的部分无变化短路已有，定义和外观整体短路仍不足。
- 旧按钮删除检查使用 `containsObject`，标签极多时仍有较小 O(G²) 检查；旧按钮查找已是字典，不再是旧版主要复用瓶颈。
- 投影列表关闭原生预取（Adapter:703–707）以避免坐标错配。可能减少预加载收益，但不能据此断言增加网络或解码开销，需实机测量。
- UITableView 的全局 Hook 在其他页面也会执行一次适配器查找，未绑定时直接原生返回；不等于所有聊天 table 都进行分组全量处理（Hooks:297–301）。

## 4. 内存：常驻快照和分配峰值，未证实泄漏

主列表可见时持有全量 `cachedNativeSections`（N 个轻量行值）、当前组 `projection`（V 个行值与两个路径映射）、`identityDisplayPaths`、分组定义、按钮及少量交互队列。投影构建时重新复制 N 个行值，建立校验集合、成员索引、目标组集合及数字包装对象；旧投影和新构建中间数据可能在一次刷新内共存。高频刷新造成分配/释放压力，常驻内存和短时峰值随会话、成员关联数上升。

暂停时只显式释放全量快照（Adapter:118–127），当前投影、身份索引、分组 UI 仍保留，所以离开列表不代表清空分组内存。当前选择“全部”时保留的投影也可覆盖 N 行。该保留不等于泄漏，没有真机堆栈和存活对象统计，不能给出 MB 数或泄漏结论。

快照不保留私有 session/contact，只存身份、路径、类型和数字。弱引用 adapter 注册表、弱 controller/table、弱调度捕获等降低循环引用风险。配置备份保存 original/previous，而不是每切组无限追加历史。原生导航闭包和完成回调在等待期间仍可能保留捕获对象；已有清理，但异常生命周期是否造成长期滞留需 Allocations 验证。

未发现专门的内存警告快照回收策略。后续释放离屏投影时，必须保持原生表格坐标与删除回调的一致性，不能只把 `projection=nil`。

## 5. GPU、动画和设置页

分组指示器使用位置和 `bounds.size` 的 Core Animation，约 0.26s，没有重复计数或 CADisplayLink。分组代码没有持续运行的全屏模糊、视频纹理或自建逐帧绘制。有限圆角和文字会产生正常绘制/合成，GPU 的主要潜在增量是频繁列表重载所引出的原生内容更新；没有 GPU trace，不能量化。

设置页 `accountCheckTimer` 为每秒一次，账号不变早退（Settings:87–127），weakSelf，不常驻到普通聊天。正常频率低，优先级低于全量刷新。

成员选择页在主线程读取全部联系人，排序 O(C log C)；搜索每次输入扫描 C 个联系人，重复 lowercase，且搜索词 lowercase 位于循环内（ContactSelect:103–138、:421–450）。联系人多时可导致该页面打开或输入顿挫，局部内存还持有联系人数组。它不在日常聊天输入框运行。

普通切组仅写小的账号选中记录，没有 synchronize（Preferences:215–237）。定义/成员修改才做完整校验、备份与 synchronize（:155–205），设置开关也有同步写入；这些低频编辑动作不应混同为每次收消息落盘。

使用当前源码的 Foundation 计算，构造原生 getter 与内存 defaults；3 次预热、21 次采样，中位数如下。宿主硬件见 metadata.json。完整路径基准每次新建 Preferences 并构建快照，因此不是优化后缓存命中路径，也不代表真实 Adapter/UI 总耗时。

阶段分别独立测量，中位数不能简单逐项相加。切组选中项保存中位数为 0.0033–0.0055ms，仅内存 defaults，不含实际落盘。该项不再是旧版全量配置保存瓶颈。即使快照命中，投影仍会重算，所以高重叠成员配置仍有单次切组开销。

生命周期回放 **52 项检查，0 失败**（原有 46 项加本次 6 项），包括：

- 离屏 200 次模型更新不发布/不布局；离屏分开送达的 20 次事件发布 0 次。
- 静止无事件 250ms 发布 0 次。
- 10 次间隔 55ms 的被动通知，发布 10 次。
- 10 次直接请求分开送达，发布 10 次。
- 菜单持续运动 270ms，菜单状态读取 11 次、完整发布 0 次、仍有待执行重试；随后静止展开停止轮询。
- fixture 注入持续失效，链式发布 12 次，测试主动止于 12。

这些是状态机和纯计算证据，没有测量 iPhone FPS、GPU、实际耗电、温升或内存峰值，也没有证明用户当前存在特定原生异常。

## 建议处理顺序与实机归因

1. **先限制无效持续工作：** 同一失败按账号/模型代次去重，加有界退避；明确交互结束唤醒和超时兜底，保留菜单跟手保护；补齐 App 非活跃状态的刷新准入，同时保留原生模型更新和返回合并刷新。
2. **再减少正常消息的重复成本：** 保留结构变化的安全全量退路；区分未读、内容、结构变化；当前组无结构变化时避免无条件 reload；缓存自定义成员反向索引及其他可复用纯数据。不能把微信可变私有对象直接丢到后台读取。
3. **优化高频细节：** 无路径滚动回调直接转发；分组定义、外观没变时跳过 updateTabs/颜色解档；缓存按模型代次已验证的映射；按安全状态回收离屏内存。
4. **低优先级：** 设置页轮询改事件驱动并保留安全校验、联系人选择搜索去重计算。指示器动画不是首要耗电优化对象。

若主列表静止但持续收消息时发热，优先采样 refresh/NativeBridge/Projection；若进入聊天后仍持续发热，先验证主列表暂停标志和待执行导航，再用 Time Profiler 区分分组与其他功能，不能仅凭开启分组就归因。若无消息、无操作、设置页也未打开仍发热，需要采样是否存在异常重试链。

建议真机固定同一设备、账号、会话数据、亮度和网络，分别比较分组开关：静止无消息、固定消息输入、连续滚动/切组、聊天内输入/滚动、主列表切后台。记录 Time Profiler/CPU、Allocations 常驻及峰值、Energy/Power 工具可用指标及 Core Animation 卡顿；采样记录使用聚合计数，避免新增逐帧日志污染结果。
