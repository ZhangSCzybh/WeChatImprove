附件：docs/feedbacks/2026-10-27-foreground-gap-background-lost.jpg（真机截图，务必先看）

一、用户反馈的现象
从后台返回微信（切回前台）后，会话列表里"会话与会话之间的间距背景"不见了——原本每个会话/每张卡片之间露出来的那层底色消失，卡片看起来直接贴在一起；必须上下滑动一下才会恢复正常。滑动后能恢复，说明数据和布局都在，只是前台回来这一帧的绘制/装饰状态没被重新应用。

截图里请逐处核对：哪些位置缺了间隔底色、缺的是整段列表画布还是卡片之间的缝隙、首末圆角是否还正确、分组与分组之间的间隔是否也缺。

补充要采集的触发路径（都要单独确认，不要只测一种）：
- 冷启动 → 切后台 → 切回前台；
- 锁屏 → 解锁回到微信；
- 上滑进 app 切换器 → 返回；
- 下拉通知/控制中心 → 收回；
- 在别的 app 停留较久（>1 分钟）后返回。
分别记录是否必现、是否与"返回时列表有未读变化"相关。

二、要求先定位，不要凭猜测改
1. 先弄清"间距背景色"到底是谁画的：是列表画布（table/scrollView 的 backgroundColor 或 backgroundView）、是 cell 之间露出的间隙底色、还是圆角卡片装饰层（CSListCornerSessionDecorate / CSListCornerPageContext 那套）画出的卡片底色与 gap。要有代码位置和调用栈/证据，不要只说"应该是"。
2. 定位前台恢复链路上缺了哪一步重绘或失效：
   - willEnterForeground / didBecomeActive / applicationDidBecomeActive / viewWillAppear 上我们的适配器是否被调用、调用顺序如何；
   - 恢复时原生是否把我们设过的 backgroundView / backgroundColor / separator 相关状态覆盖回去（例如原生在某处重设背景）；
   - 恢复首帧的 bounds/尺寸变化是否触发了 layout 但没触发装饰重算；
   - 是否存在快照层（snapshotView / 系统返回动画用的快照）在新帧里仍然盖着旧内容；
   - 是否是装饰层只在 scroll/didEndDragging/重载时更新，前台恢复不在其更新触发集合里。
3. 说明 2.0-19 那次"把列表画布改白"的结论与本次现象的因果关系；确认本次是否为 2.1-1/2.1-2 之后新出现（对照 2.1-1 与 2.1-2 的差异文件），如果与后台同步改动无关也要明确写清。

三、修复要求
- 目标是：从后台返回的那一刻就正确，不需要用户滑动来"救"。
- 不许用固定延时（此前已定结论：设置面板三时序问题已经明确要求不用固定延时），要用确定性的时序/事件收口；若必须异步，用下一帧/布局完成回调这类有依据的时机，并说明为什么它一定在原生恢复之后。
- 不许整表 reload 来刷新，不能让用户看到闪烁、跳位或丢失滚动位置（用户此前反馈过滚动抖动，不能回退）。
- 只改必要的重绘/失效与触发时机，不动：分组数据与顺序、间距数值、圆角语义（同组连续 cell 合成一张卡、仅首行上圆角、末行下圆角、中间无缝直角）、卡片底色取值、隐私隐藏、未读红点、标题/摘要逻辑。
- 深色/浅色、不同分组数量、单会话组、置顶区、折叠入口行（「折叠的聊天」要作为卡片的一部分，不能因为这次修复又变成独立卡）都要一并对齐。

四、诊断与回归
- 加带原因码的日志（沿用现有前缀风格，例如 `[WeChatImprove][ListRestore] stage=... reason=...`），能区分"前台恢复未触发装饰"、"装饰已触发但被原生覆盖"、"尺寸未就绪"这几类，去重且有上限，不打印账号与会话内容。
- 只跑既有指定脚本（verify-list-corners.sh 等），先红后绿；新增用例必须覆盖：
  - 前台恢复后首帧的装饰/背景状态正确（不依赖滚动）；
  - 恢复时列表内容有未读变化、分组数量变化的情况下依然正确；
  - 恢复后连续两次前后台切换不残留；
  - 不丢滚动位置、不触发整表重载。
- 版本顺延 2.1-3，双包（rootful + rootless）+ symbols，独立构建目录，历史产物一律保留不动。

五、用户验收
装 2.1-3 后按上面 5 条触发路径各走一遍：返回微信的第一眼间距背景就必须在，不用滑动；滑动后滚回原位也不能出现新的白块或颜色错位。
