版本起点：2.0-23（packages/com.wechat.improve_2.0-23_iphoneos-arm.deb 已装、已验证）

一、用户对现状的判定
摘要文本仍然不是原生那一条。「折叠的聊天」这一行在原生微信里，摘要区显示的是「会话名称 + 消息」（例如「张三 你好」「家庭群 我明天到」这种形态：先是最新会话的名称，再是该会话最新一条消息的内容）。项目现在产出的只是一段消息正文，缺少或错配了会话名称那部分，所以看起来"不是原生摘要"。

注意：这不是"再多拼一个字符串"的问题。用户要的是**和原生折叠入口行完全一致的呈现**，不要自造格式（不要自己决定冒号、空格、分隔符、截断宽度、字号色值）。

二、本轮要求
1. 先做原生调研，不要直接改代码。目标是把原生「折叠的聊天」（chatroom_session_box 那一行）摘要区的完整呈现链路搞清楚，并给出可验证依据：
   - 这一行的 cell 是哪个类（原生折叠入口行 vs 普通会话 cell 是否同一套 cell 类/data 类）；
   - 摘要区是一个 label 还是多个 label（名称 label + 消息 label 分开摆放，还是一个拼接后的字符串）；
   - 名称从哪个字段来（会话显示名 / 群备注 / 群成员昵称 / 联系人 displayName），消息从哪个字段来；
   - 名称与消息之间的分隔、颜色、字号、截断/换行/省略规则（尤其名称超长、消息超长、单行放不下时各自怎么收缩）；
   - 图片、表情、语音、引用、撤回、系统消息、红包等类型在该摘要里的呈现（是否「[图片]」这类占位、由谁生成）；
   - 折叠成员变化 / 组内最新会话变化时，摘要由哪个原生刷新链路驱动；
   - 原生是否为「按当前过滤集合」生成摘要——特别注意原生只有一个全局折叠入口，而我们要按分组显示各自的最新会话，这一层的差异必须显式说明，并给出你打算如何保持原生格式而只替换"候选集合"的做法。
   把这部分结论写进报告，附头文件、方法签名/编码、反汇编或字符串证据，不要只写推断。

2. 再改实现。目标行为：
   - 标题保持原生「折叠的聊天」，不带会话数、不缩字（沿用 2.0-21/2.0-22 已定结论，不得回退）；
   - 摘要的**呈现方式**与原生折叠入口行一致（会话名称 + 消息，标签分工、颜色、字号、分隔、截断规则都照原生），只是候选集合换成"当前分组过滤后的最新可见会话"；
   - 优先复用原生入口行的取数与渲染：如果原生是 cell 内多个 label 组合，就沿用同样的 label 结构与原生取值来源，而不是把名称和消息拼成一个自造字符串再塞进单个 label；
   - 如果原生格式化入口（如 digestForMsg:withSender:）本身就不产出会话名称（这正是当前偏差的可能来源），必须明确说明原生名称部分由哪一层提供，并在我们这边按同一来源补齐，不能自己猜格式；
   - 右侧时间维持现状：不新增、不显示；时间**不能**作为兜底或降级条件，判定依据只允许是摘要文本本身 + 账号/隐私/可见性校验。

3. 兜底与降级边界（沿用 2.0-23 已交付的收口）：
   - 允许短暂中性，但只允许在"消息与有效时间都不可用"时；
   - 不允许出现"全局聚合摘要"式兜底（拿别的组或全局最新消息顶上）；
   - 不允许用自造占位文案假装原生（除原生自己就会产生的类型占位）；
   - 冷启动不需要先打开折叠列表；若首次数据未就绪，返回或刷新后必须自动重试。

4. 诊断日志：保留现有 `[WeChatImprove][FoldedDigest] stage=... reason=... tab=... count=...`，再补一个维度，能区分这次的关键分歧：摘要文本到底来自
   - 原生入口行（复用原生 cell / 原生 data 的现成文本），还是
   - 我们按原生格式化入口生成、再按原生名称来源补名称，还是
   - 中性兜底。
   命名自定，但要能从日志一眼看出"格式对齐是否走了原生路径"。同一原因去重、进程内上限、不打印正文与账号标识，这些约束不变。

5. 不改动范围：分组增删改、去重、未读/红点、隐私隐藏与顺延、存储与迁移、选择器、连续卡片/圆角/行高/布局、深色适配、字体适配，全部不动。

6. 回归：仍只跑 Tests/verify-list-corners.sh 与 Tests/verify-close-friend-session.sh，先红后绿；新增用例必须覆盖：
   - 私聊与群聊的「名称 + 消息」组合顺序与分隔；
   - 名称超长、消息超长时的截断（与原生同规则）；
   - 图片/表情/引用等类型的原生占位呈现；
   - 组内最新会话切换后摘要随之切换，且跨组不串；
   - 密友隐藏后顺延到下一条可见会话；
   - 账号切换/隐私 revision 变化时拒绝复用旧文本；
   - 冷启动无缓存路径。
   版本号顺延 2.0-24，双包（rootful + rootless）与 symbols，独立构建目录，保留历史产物。

三、验收标准（用户真机判断）
把分组列表里的「折叠的聊天」行和微信原生折叠入口行并排看：
- 标题一致（都是「折叠的聊天」）；
- 摘要的构成一致（都先给会话名称，再给该会话最新一条消息）；
- 名称与消息之间的间隔、字号、颜色、省略方式看不出差别；
- 只是内容按分组过滤：A 组显示 A 组最新可见会话，B 组显示 B 组最新可见会话。

如果原生折叠入口行的名称部分并非"会话名称"而是别的（例如固定文案或来源不同），请在报告里用证据纠正这一点，并按原生实际行为实现——以原生真机表现为准，不要以本条描述的字面为准。
