二、要改的地方
1. 主改动点：Controllers/CSGroupListAdapter.m 的 -performSessionListLayout:（当前 :648 起）。
   现在的逻辑：ready 判定通过后，用双层 for 遍历 projection.sections 的每一行，逐行调 [policy hidesUserName:surface:]，命中隐藏就 ready=NO。这段就是每次布局的 O(N_p) 成本。
2. 需要时在 Controllers/CSGroupProjection.h/.m 上提供只读的 provenance（证明身份信息），让 adapter 能用稳定键判断"这份投影的准入结论还能不能复用"。不要为了取键去改投影的行集合、索引映射或几何。
3. 只读不写：不要改成"把准入结论写进投影再序列化/落盘"。这是进程内缓存，不落盘、不进备份、不进导出。

三、缓存必须满足的正确性条件（这一节是验收重点，逐条落实并写进报告）
1. 缓存内容是：「在当前这份不可变投影上，按当前策略状态，全部行都不需要隐藏」这一条结论。
2. 命中条件必须是全部键完全一致，缺一不可，且每个键都要说明它覆盖了哪一类变化：
   - 投影对象身份（同一份不可变实例；投影被替换/重建即失效）
   - 账号 ID
   - CSCloseFriendAccountEpoch() 的值
   - policy.revision
   - policy.enabled / policy.revealed / policy.blocked 的当前值
   - options[@"hideSessions"] 的当前值
   - 投影自身的 privacyRevision（现有代码已经在比对的那个）
   - snapshotRetryAttempted 状态
   如果你认为还缺别的键，加上并说明理由；但**不许**用「行数」「数组地址」「sections.count」这类不完整信息当证明依据。
3. fail-closed 原则：以下任一情形一律不命中缓存，必须回退到原来的全量逐行判定路径（行为与现在完全一致）：
   - policy.blocked 为真
   - 账号不匹配 / epoch 不匹配 / 投影无效 / snapshotRetryAttempted 为真
   - 任何键读取失败或取值未知（例如 CSGroupReadInteger 返回 fallback）
   - 布局过程中再次取快照发现策略已变
   宁可多扫一遍，不可错误命中。
4. **解锁到期这条必须单独排查并给结论**：如果密友的解锁是"时间到期自动重新隐藏"，那么缓存建立时是"已解锁、无需隐藏"，到期后策略变为"锁定隐藏"，此时若 revision 不自增，缓存命中就会放行本该隐藏的行——这是隐私事故。
   你必须先确认 policy.revision 的语义是否覆盖"解锁到期"这一类变化（去读 CSCloseFriendPolicy / CSCloseFriendRuntime 的实现，不要猜）。如果不覆盖，就必须把到期时间或等效状态纳入键，或者在这种情形下直接不缓存。这一条要在报告里明确写"已覆盖 / 用 X 键覆盖 / 该情形不缓存"。
   同理确认：名单增删、密友主开关切换、hideSessions 切换、surface 设置变化、切换账号、手动上锁，是否都会让键变化。
5. 每次布局仍要保留：
   - 至少一次 CSCloseFriendCurrentSnapshot() 读取（不允许为了性能连快照都不取）
   - 允许原生布局前的那次复检（现有 :669 起那段 current/epoch/account 比对）原样保留，且若发现变化照旧走 shield + dirty + requestRefresh 那条路
   - ready=NO 分支的所有行为（sessionLayoutHeld、shieldCell、privacyRefreshPending、dirty、requestRefresh、return）不得改动
6. 命中缓存时也必须执行原来命中路径上的其余动作：CSGroupWithDisplayIndices(self.table,layout)、sessionLayoutHeld=NO、[self.privacyShield prepareForPublication]。不要因为走了缓存就跳过发布前准备。
7. 缓存只在 adapter 实例生命周期内有效，不跨账号、不跨前台/后台切换复用（除非你能证明键已覆盖）。切换账号、收到策略变更通知、表重建这些点必须显式清空缓存。

四、测试要求
1. 先写测试，在**未修改**的 2.2-1 基线上跑红，证明新断言能抓住"每次布局都全量扫描"这个现状，然后再改代码转绿。把红/绿的检查数与失败数都写进报告，不许只报绿。
2. 至少覆盖这些断言：
   - 同一份稳定投影连续 K 次（建议 ≥ 20）layout，全量逐行判定只发生 1 次；每次 layout 至少取 1 次快照。
   - 策略切换（主开关 / 名单增删 / hideSessions / 解锁 / 到期重新隐藏 / blocked）后，下一次 layout 必须重新做全量判定，且不得命中旧缓存。
   - 切换账号、epoch 变化、投影替换、snapshotRetryAttempted 置位后，旧证明立即不可用。
   - 任意一次 layout 中，属于隐藏名单的行都不得进入原生布局（沿用现有的 surface/召唤记录方式断言，不许放宽判定）。
   - 布局期间策略被同步改动（复检阶段发现 revision 变化）时，走 shield + dirty 路径，不下发带隐藏内容的布局。
   - 计数型断言只验证调用次数与失效语义，**不要**写依赖机器速度的毫秒阈值。
3. 不许修改已有测试的期望值来适配新实现；如果某个既有用例确实与新语义冲突，停下来先报告，别自己改断言。
