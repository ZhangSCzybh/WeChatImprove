3. 允许在工作树之外（/tmp 之类）临时搭度量工具或小工程来取数据；不许把任何临时度量代码提交进仓库，也不许为了度量去改仓库源码。

5. 报告写完就停，等我确认。不要"顺手先把明显的改动做了"。

二、现象（用户真机反馈）
1. 前提条件：插件里同时开启「分组功能」和「隐藏密友」（密友/密群隐藏）。
2. 场景：微信在前台，停在聊天列表页（不切换页面、不滚动、就停着）。
3. 现象：CPU 占用接近 100%，持续不降。用户明确说的是"页面停着也高"，不是只在滑动或返回过程中高。
4. 关闭分组、或关闭隐藏密友，两者只留一个时是否还高——用户没有单独验证过，你在分析里要明确这两者各自的作用，并给出"如果只有一个开关也高，最可能的原因是哪一个"的判断与依据。

三、必须搞清楚的问题（按这个顺序回答）
1. 谁在跑：CPU 是持续占用（有循环在转）还是脉冲占用（高频重复回调）？两者修复完全不一样，必须先定性。
2. 主线程还是后台线程：如果是主线程 100%，说明是每帧都在算东西，报告里要给出"每帧/每秒做了多少工作"的量级。如果是后台线程，要指出是什么队列在转、被谁驱动。
3. 触发源：是显示链（displayLink / CADisplayLink / CoreAnimation 回调）、定时器（NSTimer / dispatch_after 链 / dispatch_source）、通知（KVO / NSNotification 风暴）、还是 table 的布局与 cell 回调自激（layoutSubviews → setNeedsLayout → 再布局）。
4. 为什么两个开关同时开才明显：分别关掉其中一个时，理论上哪条代码路径会消失。要落到具体函数，不要停留在"过滤逻辑比较重"这种程度。
5. 有没有自激环：某个"就绪/已发布"状态被反复判定为变化，导致每帧重新 reload 或重新布局。这种环在停着不动时是最典型的 100% 来源。

四、重点排查清单（逐项给结论，有就指出文件:行与调用链，没有就写"已排除 + 依据"）
A. 分组列表发布链路：Controllers/CSGroupListAdapter.h/.m、Headers/ 下对应头文件、Hooks/SessionGroupHooks.xm
   - refresh / publishProjection: / performSessionListLayout: 的调用次数来源。是否存在每次布局、每次滚动、每次 cell 回调都重新构建过滤后集合与投影的情况。
   - reloadData / beginUpdates-endUpdates / reloadRows / layoutIfNeeded / invalidateLayout 的调用频率与触发者，是否存在互相调用形成的循环。
   - 行高计算：每个 cell 是否重复做文本测量（boundingRectWithSize、sizeThatFits、attributedString 构建），是否每帧重复算。
   - 投影/快照对象的构造成本：每次发布是否新建大字典/数组、做全量排序（MMSessionInfo compare:）、做字符串归一化（小写化、正则、拼音、哈希）。
B. 隐藏密友链路：隐私过滤、密友名单判定
   - 判定一次要遍历多少会话、做多少次字符串比较或哈希；是每次调用重算还是缓存。
   - 名单/配置是否每次从磁盘或偏好读；有没有不必要的加解密、JSON 解析。
   - 被隐藏行的处理方式是否导致每帧重建整个 section 的索引映射。
C. Hooks 与通知
   - 是否有 KVO / NSNotification 在列表可见期间被高频触发（会话更新、角标、活跃会话切换、未读数变化），而每次触发都走重活。
   - 是否监听了不该在列表页监听的通知（例如消息入库、同步进度、数据库变更）。
D. 主线程杂项
   - 列表页驻留期间的日志输出（NSLog / os_log 高频）、字符串拼接、文件读写、sqlite 查询、图片解码。
   - 角标/未读数刷新是否与 table 布局耦合，形成"刷新角标 → 触发布局 → 再次刷新"。
E. 分组本身
   - 分组折叠状态、分组标题、分组聚合行（服务号/公众号聚合）是否每帧重算聚合成员。
   - section 数量/行数 getter 是否被极高频调用（UITableView 在滚动和布局期会大量调用 numberOfSections/numberOfRows），getter 内部如果做实质计算就是灾难。

五、证据标准（这一条最重要，不接受"看代码觉得像"）
1. 每个被指为热点的函数，必须给出：文件:行、被谁调用、静态调用链、以及在什么频率下被调用（可用插桩计数或可复现的度量证明）。
2. 能量化的必须量化：每次调用的循环规模（会话条数 N、分组数 M）、单次估算开销、单位时间内次数。拿不到真机采样就写清"这是静态推断 + 调用次数计数"，不许编造 Instruments 数据。
3. 至少要有一次能落地的度量：例如在工作树外写一个度量工程，把相关 getter / 回调 / 发布方法用桩驱动，统计单位时间内的调用次数与累计耗时占比，产出 top 列表。度量口径要写在报告里能复现。
4. 结论要给"因果链"：开关 X → 路径 Y → 每帧执行 → 100%。链条上每一环都要有代码位置支撑。
5. 如果排查后发现无法在代码层面解释 100%，必须明说"当前证据不足"，并给出下一步最小的取证方案（用户在真机上怎么采、采什么），不许糊一个猜测当结论。

六、修复方案怎么写
1. 按优先级列出 2~4 个候选方案，每个方案都要写清：
   - 改哪里（文件、函数）、改什么思路、预期能削掉多少开销（有依据就写数字，没有就写区间 + 依据）
   - 会不会影响已交付的隐私行为（隐藏密友必须在任何时刻都不泄露）、会不会影响滚动位置、分组折叠、卡片圆角、返回过渡
   - 风险等级、回归面（哪些测试集必须跑）
   - 是否需要新测试，测什么断言
2. 首选方案必须满足：不靠固定延时、不靠降频（比如把刷新从每帧改成每 200ms）、不靠牺牲隐私实时性、不靠整表 reloadData 掩盖。降频/延时类手段只能作为最后手段列出，并写明代价。
3. 明确写出"推荐哪一个"，并给出改动量估计（文件数、增删行数量级）。如果推荐方案超过 300 行改动，要额外说明为什么不拆小步。
4. 如果某个热点是微信原生行为 + 我们的 hook 放大了它（例如原生 getter 被我们包了一层导致每次都走重算），要把"原生本来调用频率多高"和"我们额外增加多少"分开写，这决定了修 hook 还是修策略。
