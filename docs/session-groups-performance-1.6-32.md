# 聊天分组性能分析：1.6-32

2026-10-16，基于提交 e638ba7fac62d6e4229d5cb9b83f53ad3f95a16a 的生产代码。此次仅新增分析与可重复运行的主机基准，未修改插件行为。

## 结论与边界

最大扩展风险在主线程数据路径：每次获准发布的 refresh 都重新读取全部原生会话并构造投影，切组也走同一路径；每次保存选择则处理整份分组配置。列表只有两条显示会话，并不意味着这次刷新只扫描两条。

菜单与切组手势期间已经有刷新避让；这些保护减少交互中重载，却不减少交互结束后那次全量工作的成本。指示器用 Core Animation，按现有源码和主机数据没有理由把它列为第一优化目标。

以下数值是 Apple M4 / macOS 27.0 的隔离微基准，不能解释为 iPhone 耗时或 FPS。没有对用户运行中的微信采样，没有测 UI 绘制、实际私有 getter 的耗时、偏好 IPC/落盘、内存峰值或功耗。源码分析能确认执行路径和复杂度；手机上的耗时占比仍需 Instruments 或有界计时验证。

N 为原生总会话数；G 为四个预设加自定义分组；M 为自定义成员关联总数。同一会话进三个自定义组计三个关联，不能只看去重后的会话数。

## 各路径开销

### 1. 每次发布都完整重建数据：最高优先级

CSGroupListAdapter.m:296 的 refresh 在主线程执行：重建 Preferences，调用 CSGroupBuildNativeSections，构造 CSGroupProjection，重建 identityDisplayPaths，更新每个标签及角标，执行 reloadData/layout，恢复位置或回顶部、更新标题。

CSGroupNativeBridge.m:161 对全部原生行迭代，每行读取会话、联系人分类、置顶、未读及红点。很多整数读取会检查 methodSignature 并构造 NSInvocation。没有快照版本缓存；切换选中组也再次做这些读取。

CSGroupProjection.m:73 已有“用户名 → 自定义组集合”反向索引，不能简单认定为每组扫一遍全列表。常规复杂度接近 O(N + M + G + D)，D 是实际需要累计的会话到分组归属次数。大量成员重叠时 D 增大，但那是关联数据本身变多。

投影先验证并复制每个行值，再分配每行归属集合、累计全部组角标、构造当前组映射。因此即使原生快照已经可用，切组仍有按 N/M 增长的分配与计算。

优化方向：引入账号和数据代次，缓存不可变原生快照、分类、成员反向索引及角标。选择改变不应使会话快照失效；未读改变不应重做分组定义。未知原生结构变化保留完整重建兜底。原生对象读取仍留在主线程，只有独立不可变值的纯计算适合评估移到后台，并在发布前核对代次和账号。

### 2. 选中一个组也规范化和写入整份配置：最高优先级

CSGroupPreferences.m:196 的 setSelectedTabID 先 reload，随后构造完整 profile 并进入 writeProfile。后者再次规范化自定义组和成员，校验 property list，保存完整 original/previous 备份、更新 profiles、调用 synchronize、读回校验，再 applyProfile。

在内存替身中，稳定阶段每次选择仍观察到 2 次 setObject 和 1 次 synchronize。首次保存还可能建立 legacy backup。这里测到的是对象处理和内存 API 调用；真实偏好系统的同步成本没有计入。

原始/前一份备份是覆盖更新，并非每次切组无限追加。性能问题是频繁处理和同步完整配置，而不是据此声称备份无限增长。

优化方向：让“当前选中组”采用轻量持久化路径，配置完整校验与历史备份用于真正的成员/顺序/名称变更。保持账号归属与失败恢复，迁移已有选择值时做兼容处理。不能直接删除校验/备份来换速度，也不能把可变 Preferences 无保护地放进后台。

### 3. 更新请求已合并，但没有稳定的刷新频率上限

原生消息、会话、未读、置顶、reload/insert/delete 等多条入口会请求更新。scheduled 合并尚未执行的刷新，changeDepth 合并事务；不能因此保证跨主队列周期到达的连续消息都只刷新一次。

正常空闲时 requestRefresh 使用 dispatch_async，而不是固定的节流窗口。50ms 延后仅用于触摸跟踪、分组手势运动或菜单运动，不是全局 20Hz 刷新上限。当前代码也没有将“仅角标变化”与“行结构变化”拆开。

优化方向：按更新原因区分结构、内容、角标、偏好与用户选择；对通知型变化做有上限的合并，而用户显式切组仍及时响应。可以从未读角标的轻量更新做起；删行和身份迁移保持严格校验。

### 4. 滚动路径有动态转发与反复身份复核：中等优先级

除 cellForRow 等显式入口，许多 delegate/dataSource 回调通过 methodSignature/forwardInvocation、选择器字符串及路径映射转发。无路径参数的 scrollViewDidScroll 也经过通用处理。索引作用域使用线程字典栈，进入/退出会产生小数组等分配。

高度、显示生命周期和路径查询会重新验证账号与会话身份；普通当前路径命中无需插件自己全表扫描，失配时调用宿主按用户名重新定位，其实现复杂度未测，不能直接假设 O(1) 或 O(N)。匿名笔记在 dirty 时还必须复核边界与内容类型，这是前面修复错位所需的正确性保护。

优化方向：给明确无索引参数的高频滚动回调设置保留原生作用域的直接转发路径；只在同一有效数据代次内复用解析结果。不能恢复不校验身份的旧路径，也不能全局跳过索引映射。

### 5. 分组栏更新有重复工作：次于数据路径

updateTabs 每次按 tabId 在旧按钮数组中线性查找，可形成 O(G²)；还会为所有按钮更新字体、标题、外观并请求布局。layoutTabButtons 为计算总宽及设置 frame 两次计算每个标签的文本宽度。每个 badge 更新即使值没变也设置文本和请求布局。

setNeedsLayout 可以被 UIKit 合并，不能把 G 次请求等同为 G 次完整布局；但 updateTabs 内部确有强制 layoutIfNeeded。分组少时影响通常有限，分组多、消息密集时值得消除。

优化方向：按钮按 tabId 字典复用；将标签定义变化与角标变化分开；值没变时早退；文字宽度按标题/字体/字号/动态字体环境缓存，角标宽度另行失效。

### 6. 菜单状态扫描与动画不是当前首要目标

nativeMenuState 扫描当前可见的菜单 Cell，规模主要随可见行 V，而不是全部 N。pending 更新且菜单运动时可能每 50ms 重新检查，并在 dirty 时验证行身份；requestRefresh 的 scheduled 早退能避免每个 handlePan 都重新安排扫描任务。

菜单静止展开后停止持续轮询，没有无条件常驻高频定时器。清洁状态下的菜单回调只更新切组可用状态，不做全量刷新。可考虑一次刷新决策内复用状态值，但不能移除这些保护，否则可能再次出现菜单中途被重载打断。

指示器使用约 0.26 秒的 Core Animation，不在每个拖动 Changed 阶段重建投影，也没有自建 display link 每帧刷新列表。没有设备证据支持先牺牲动画效果。

### 7. 预取与内存

投影列表主动禁用原生 prefetch 回调，避免取消预取时使用过期路径。这可能降低快速滚动时头像/内容的预准备收益，但未测宿主是否依赖该预取加载，不能断言具体影响。恢复预取必须先解决异步请求与取消的身份映射。

完整构建时同时存在原生行值、二次复制行值、临时索引/集合及旧投影，带来 O(N + M) 级别的临时对象压力。最终持有当前组行与映射、全部组角标及成员配置，而不是为每组永久保留 N 个 Cell。reloadData 也不意味着立即创建全部会话的 UI Cell。

adapter 对 table/controller、proxy 对 adapter/target 使用 weak，UI 回调及延迟刷新使用 weakSelf，未从这些结构看到直接引用环；这不等于通过了泄漏检测。没有测 RSS、峰值、长期泄漏或功耗，不提供虚构的 MB 数字。

## 实施优先级

1. 数据代次与快照/分类/成员索引缓存，让仅切组复用已有会话数据。
2. 独立、轻量保存选中组，避免每次切组走整份配置备份与 synchronize。
3. 区分刷新原因，角标轻量更新，通知合并；未知结构仍完整重建。
4. 高频转发和标签布局去重，保留索引/账号/删除/匿名笔记保护。
5. 有实机证据后再评估预取、内存峰值与更细的菜单状态缓存。

全量重载转增量更新比缓存更容易引入路径错配，建议后置。不要先把原生私有对象访问移到后台，也不要通过减小手势阈值或删菜单保护来掩盖数据刷新成本。

## 实机验证建议

用相同账号和列表，分别记录 500/2000/更多会话量下的切组、消息连续到达、停滑后刷新、菜单展开后收起。Time Profiler/主线程时间拆分为配置读取、原生快照、投影、标签更新、reload/layout、选择持久化，并同时记录实际刷新次数。

观察 p50/p95、最长主线程占用与真实掉帧，不以平均 CPU 或主机基准代替。额外用 Allocations 检查峰值与稳定状态。60Hz/120Hz 对应 16.7ms/8.3ms 帧间隔只是设备评估参考，不将上述 Mac 耗时直接换算成手机丢帧数。
