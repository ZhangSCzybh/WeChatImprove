# 插件配置备份与恢复改造方案

日期：2026-10-20

基线：WeChatImprove `1.8-36`，提交 `a758a5f7`；以本次读取的工作区源码为准。

状态：供评审的设计方案，尚未实现，也不表示设备验证通过。

用户确认的首要场景：**完整保存本机插件配置，升级或误操作后可恢复。**

## 1. 设计结论

采用“配置登记表 + 保留现有存储的模块适配器 + 不可变快照 + 可恢复的恢复事务”。

完整备份的对象是用户设置、账号所属的分组，以及设置引用的自定义资源。微信自身偏好、支付处理账本、登录授权状态、缓存和进行中的动作不属于可回退的插件配置。

保留当前配置所在的域、键名和账号归属，通过登记表准确读写。恢复先生成差异计划和恢复前保护快照，在重新打开微信时、插件功能开始消费配置之前应用；任何中断都通过持久日志收敛到完整旧状态或完整新状态。第一版不追求所有模块即时热恢复。

不承诺跨多个 NSUserDefaults 域的物理原子提交。承诺的是：备份不误收集宿主数据；恢复可验证、可追踪、可回滚；插件功能不消费恢复中的混合状态。该承诺必须通过故障注入与真机验证后才可写入发布说明。

## 2. 当前项目与备份的关系

### 2.1 运行结构

- `Hooks/*.xm` 接入微信原生生命周期、菜单、布局及消息回调。
- `Controllers/*SettingsViewController.m` 直接写偏好；业务组件另有配置快照、缓存和通知监听。
- 聊天分组已拆分为 `CSGroupPreferences`、原生桥接、投影及列表适配器；账号分组保存在一个按账号 ID 索引的字典中。
- 消息操作已有账号 epoch、上下文校验和未提交操作取消机制；恢复不能绕过这些边界。
- 气泡、合并、导航图片、列表圆角等各有缓存与刷新生命周期。
- 红包/收款使用 `CSPaymentAutomation` 与持久 `CSPaymentLedger`，其中去重记录决定某些后续行为是否再次执行。
- 备份管理器由 `CustomEntryHooks.xm` 的 `%ctor` 创建，监听前台通知。当前各 Hook 构造入口之间没有统一的恢复启动屏障。

### 2.2 实际存储分布

| 存储 | 当前内容举例 | 新备份处理 |
| --- | --- | --- |
| 微信进程的 standardUserDefaults | 分组、气泡、底栏、入口、红包/收款参数等，与宿主偏好共存 | 只读取登记的插件键；应用时逐键写回原域 |
| Suite `com.cyansmoke.wechattweak` | 头像、收藏验证、后台运行、后台模糊 | 按精确键和原 Suite 读写 |
| Suite `com.wechat.enhance` | `font.chat_size`、`global.scale` | 单独适配，不合并到 standardUserDefaults |
| `Library/Preferences/WeChatImprove` | 顶栏分隔图、联系人分隔图、底栏图标、触摸轨迹图片 | 保存被登记配置引用的文件及固定文件关联 |
| `Library/Application Support/WeChatImprove/payment-ledger-v1.plist` | 收款/红包统计与已处理事件 | 保留现状；配置恢复不覆盖、不回放 |
| `Library/Backup` | 当前旧备份目录、`backup_info.json` | 只读识别，显式转换；不自动删除 |

这里的路径均相对微信应用容器；本次只检查仓库源码，没有读取设备上的真实配置或账本。

### 2.3 已确认的问题

| 问题 | 源码证据 | 直接影响 |
| --- | --- | --- |
| 备份范围越过插件边界 | `CSBackupManager.m:121–155` 扫描所有 `.plist` | 宿主和其他组件偏好可能被带入、导出及恢复 |
| 恢复删除原文件再复制 | `CSBackupManager.m:200–234` | 复制失败可能留下部分恢复；只要有文件成功就可能继续返回成功 |
| 偏好域映射错误 | `CSBackupManager.m:250–283` 按文件名关键词分成一个 Suite 或 standard defaults | `com.wechat.enhance` 等真实域没有正确的 API 写入映射，多域键可能混入同一域 |
| 导出会丢失嵌套类型 | `CSBackupManager.m:402–412,447–472` | 嵌套含 NSDate/NSData 的整个数组或字典被标记为 unknown，导入时跳过 |
| 分组实际命中日期问题 | `CSGroupPreferences.m:35–41` 在分组记录保存 NSDate | 正常自定义分组可能使整个 account_profiles 顶层值在导出中退化为 unknown |
| 资源目录导出、导入不对称 | `CSBackupManager.m:394–397,475–496,584–623` | 导出的图片目录被导入为同名 plist，没有重建文件树 |
| 成功状态不可靠 | `CSBackupManager.m:136–168,621–632` | 创建部分复制失败、导入无 settings 或写失败，仍可能登记为成功备份 |
| 配置与内存状态没有统一提交 | `CSBackupManager.m:299–309` 只发少量通用通知 | 分组、底栏、入口等专用通知和内存缓存没有完整重载保证 |
| 文件工作同步执行 | `CSBackupSettingsViewController.m:184–189,314,426`；`CSBackupManager.m:49–50` | UI 点击、前台回调直接进入同步读写，大文件可能阻塞主线程 |
| 自动备份只按时间判断 | `CSBackupManager.m:1212–1239` | 无变化也重复备份；有变化不及时保存；无保留上限；不是固定每日后台任务 |
| 备份计数和时间不准确 | 文件数显示为配置项数；导入时覆盖原创建时间 | 用户无法判断实际内容及原始恢复点 |
| 发送动作与备份耦合 | `CSBackupManager.m:637–1135` | 大量私有消息接口与重复实现；AddLocalMsg 返回不能证明文件已送达 |
| 无备份专项回归 | 当前 `Tests/` 没有备份管理器、格式或恢复事务的专门用例 | 关键失败路径缺少可重复验证 |

此外，`CSResetSettingsViewController.m:37–57,183–207` 会扫描删除全部偏好 plist，并清除微信主 bundle 的整个默认域。它与“误操作后恢复”直接相关，必须一并改用配置登记表的精确重置规则。

## 3. 方案比较与范围

| 选择 | 优点 | 代价与缺口 | 结论 |
| --- | --- | --- | --- |
| 在旧文件复制流程上加过滤 | 改动小 | 仍需另修类型、图片、跨域、失败回滚、生命周期；按前缀也会漏掉无前缀键 | 仅适合临时止损 |
| 登记表与模块适配，保留现有存储 | 能精确定义范围，可渐进接入，兼容当前 Hook 和配置 | 需要完成登记覆盖、事务及启动协调 | **推荐** |
| 全项目改为统一配置数据库/存储层 | 长期可用单一版本切换管理配置 | 所有读写和 Hook 需要迁移，扩大本轮风险 | 独立的后续架构项目 |

本轮不增加云同步、多设备同步、聊天记录迁移或主题市场。导出到“文件”和系统分享仍保留，用于用户自行保管恢复点。

## 4. 备份内容与恢复语义

### 4.1 默认完整快照

| 内容 | 创建备份 | 默认恢复 |
| --- | --- | --- |
| 界面、消息、功能开关与参数 | 保存全部登记项 | 恢复选中的模块 |
| 自定义图片与图标 | 保存关联原始字节、类型和摘要 | 校验后还原文件，重建当前容器路径 |
| 各账号分组与成员、顺序、隐藏状态 | 保存所有已存档账号，保留原账号 ID | 默认当前账号；其他账号可在预览中按原 ID 单独勾选 |
| 联系人分隔符、红包群名单等关系配置 | 保存，但标明当前实现的真实作用域 | 同本机和匹配账号上下文下恢复；无法确认归属时不自动套用 |
| 备份开关与用户保留策略 | 保存用户选择 | 提交完成后应用，不允许影响当前保护快照和事务 |
| 当前选中的分组等便捷状态 | 随快照保存 | 仅在目标分组仍存在时恢复；单独切组不触发自动快照 |
| 支付统计、去重账本、已处理事件 | 不纳入配置回退 | 保持当前值与账本，四个统计镜像键也不回退 |
| 登录、授权检查缓存、协议同意状态、头像 URL 缓存、临时任务 | 不纳入可恢复配置 | 保留或由所属模块重新生成 |
| 分组迁移原件与恢复历史 | 作为本机保护资料保留 | 不因恢复旧快照覆盖新的原件或保护历史 |

联系人覆盖字典和红包名单目前并非统一按微信账号隔离，不能在设计中假定它们已有账号归属。第一版保留既有存储语义，以本机来源和捕获时账号作为恢复限制；不擅自重新分配历史数据。所有账号分组 ID 原样保留，不把 A 的分组映射成 B。

### 4.2 配置登记表

每项记录：稳定的逻辑 ID、模块、真实域、实际键或受约束键族、类型、校验器、默认值规则、账号作用域、资源引用规则、适用 schema、恢复/重置策略和初始化依赖。

必须覆盖无统一前缀的配置，例如 `roundAvatar`、`BackgroundRunEnabled`、`GameCheat_Enabled`、`kReceiveTransferAutoEnableKey`、`font.chat_size`。不能以 `com.wechat.*` 前缀代替所有权清单，也不能因为 Suite 名看似属于插件就备份其所有键。

动态键采用模块提供的限定枚举器，例如 `chat_group.selection.<accountID>`。枚举器同时验证账号 ID、记录类型和版本；绝不通过外部备份自带的任意域名/键名决定写入目标。

开发期增加登记覆盖检查：静态扫描配置读写作为线索，人工核对动态生成与间接访问；每个配置项必须明确登记为“备份”“派生”“敏感/瞬态”之一。禁止把静态正则扫描结果直接当成运行时白名单。

### 4.3 恢复是选中模块的替换

- 新版完整快照显式记录 `present`，区分“没有设置”“false”“0”“空字符串”。备份时不存在的、同 schema 已覆盖字段在恢复时删除当前显式值，恢复该字段的默认语义。
- 只替换选中模块和选中账号下、该快照明确覆盖的字段。未选模块、其他账号和未知宿主键保持原样。
- 老快照没有的新功能项保留当前值。禁止把“旧版没记录”解释成“用户希望清空”。
- 默认值跨版本改变时，由明确迁移规则决定是否把旧有效值转换为显式值，并在预览中标注；不能无声套用新默认值却声称完整还原。
- 分组按账号切片更新 `account_profiles`；保留未选账号和备份之后新增的账号。选中账号内，快照覆盖的分组可以完整替换，预览必须展示将移除的分组。
- 账号 ID 不可用时仍可创建全局配置快照，但不能声称账号范围已完整捕获；恢复含账号关系的部分必须等待身份明确。

## 5. 新文件格式与存储

### 5.1 格式选择

第一版使用 **v2 二进制 Property List 容器，统一扩展名 `.wcbak`**，由 `NSPropertyListSerialization` 编解码。无需为了几十个配置模块和有限图片引入 ZIP 依赖，天然保留嵌套 NSDictionary、NSArray、NSDate、NSData、NSNumber 和 NSString。

格式包含这些明确部分：

| 字段 | 含义 |
| --- | --- |
| `magic` / `formatVersion` | 固定产品标记与容器版本，独立于插件发布版本 |
| `snapshotID` / `capturedAt` | 原始快照标识与原始时间，导入不得改写 |
| `source` | 插件版本、真实微信版本、系统版本、本机实例标识、捕获时账号信息 |
| `modules` | 模块 schema、覆盖字段、存在性和值、账号分区 |
| `assets` | 内容摘要为 ID 的资源字节、长度、实际媒体类型 |
| `assetReferences` | 登记字段/嵌套字段与资源 ID 的关联，不保存可执行目标路径 |
| `integrity` | 配置语义摘要和每个资源的 SHA-256 |
| 本地目录记录 | 导入时间、本地 ID、文件位置、收藏状态、校验状态；与可导出的快照元数据分开 |

对保存为 NSData 的颜色等历史对象，使用模块限定的安全解码和语义校验；新格式不从外部输入实例化任意 Objective-C 对象。未知旧归档只能保留为待处理资料，不能不受限制地调用旧的 `requiresSecureCoding = NO` 路径。

摘要用于检测损坏与去重，不等于来源身份认证。配置摘要按类型标记、排序后的字典键、数组原顺序、标准化日期和数据字节生成，不能假定 NSDictionary 的二进制序列化顺序稳定。名称、导出时间、备份历史及易变的分组选择不参与自动备份的内容变更判断。

导入前先检查文件大小，解析后限制对象总数、嵌套深度、字符串/数据大小和资源数量。首版可从总文件 32 MiB、单图片 4 MiB、资源 256 个、嵌套 32 层开始验证；这些是待性能验收的工程上限，不能直接当成已验证性能结论。超限明确失败，不缩图、不截断后声称完整。

### 5.2 目录与文件提交

新存储放在应用容器 `Library/Application Support/WeChatImprove/BackupV2/`，包含完整快照、临时工作目录、可重建索引和事务日志。旧 `Library/Backup` 只读保留。

文件由系统生成的 UUID 定位，用户名称只作显示，不能参与目录拼接。先写唯一临时文件、关闭并校验、再在同文件系统原子重命名发布。发布前不出现在可恢复列表。索引可以由快照重新生成，索引损坏不意味着备份全部丢失。

图片只通过登记的资源关联读写。备份将原来的绝对路径转换为逻辑资源引用；恢复为当前容器生成路径，包括嵌套联系人图片路径。禁止把备份提供的任意文件路径作为写入地址；对本地资源也拒绝逃逸根目录的路径、符号链接和非普通文件。

现有模块使用的固定文件名及 fallback 必须由资源适配器一并处理，不能只改偏好路径而留下过期的固定图片。仅处理选中模块拥有的已登记文件，不替换整个资源目录。

本机快照使用 iOS 文件保护；锁定时不可读取就延后操作。导出通过用户明确选择的系统分享/文件保存进行；界面说明其中可能包含分组成员和自定义文字。v2 明文容器不宣称具有密码加密能力，本轮不新增自制加密协议。

## 6. 创建与自动备份

### 6.1 一致的快照

1. 捕获请求 ID、当前账号及账号代次，取得各模块的配置副本。
2. 短暂协调插件配置写入和资源替换，读取登记字段的实际存在性和值，冻结资源关联。所有相关写入方都必须接入这个协调边界；一个只被备份管理器使用的串行队列不够。
3. 后台复制资源与序列化；再次检查账号代次、配置 revision 和资源身份。期间有变更则丢弃候选并做有上限重试，不发布混合快照。
4. 校验内容完整、类型正确、所有启用的资源引用可解析。
5. 发布完整快照，更新可重建索引，回到主线程报告结果。

常规场景只在主线程读取必要的小型配置副本和账号上下文；文件读取、哈希、格式校验与持久写入在专用串行 I/O 队列执行。资源选择器和配置保存的“文件 + 路径”写入改为一个模块级变更，避免采到新路径、旧图片的组合。

被引用的图片缺失或文件写入失败时，默认完整备份失败并指出所属模块。若将来增加“仅备份可用部分”，必须标记为不完整且由用户主动选择，不能计作自动备份成功。

### 6.2 自动策略

- 保留用户现有开关选择，不通过升级擅自开启；首次开启后尝试创建基线。
- 监听经过筛选的配置变化，静默约 30 秒后备份；持续编辑时以约 5 分钟作为尝试检查点。具体时间作为可测试的调度参数。
- 通过内容摘要去重，无变化不重复生成；仅切换分组、刷新统计或更新授权缓存不触发备份。
- 前台恢复时补做未完成任务；后台只做系统允许且能完成的工作，不能完成则保留 dirty 状态，下一次前台继续。不承诺每天某个时间后台必达。
- 恢复、重置和配置迁移前必须生成保护快照；新版本首次启动的快照必须发生在配置迁移之前，不能称为安装包升级前备份。
- 新版本没有旧 schema 的可靠读取器时暂停自动迁移，保留原始数据，不能为了生成“升级前备份”回到全目录复制。
- 建议默认保留最近 20 份自动快照、最近 5 份操作保护快照；手动和收藏快照不自动删除。当前事务依赖的保护快照不受配额淘汰。
- 只有新快照完整落盘后才能按策略清理旧自动快照。容量不足或保护快照无法创建时，中止会修改配置的操作。
- 显示最近成功时间、等待原因、失败原因和占用空间；失败不能推进最近成功时间。

## 7. 恢复事务与启动协调

### 7.1 用户看到的流程

选择备份 → 校验 → 查看差异和账号范围 → 确认恢复 → 创建恢复前保护快照 → 准备恢复 → 用户重新打开微信 → 应用、核对 → 显示恢复结果。

准备完成只提示“恢复已准备，重新打开微信后应用”，不能提示“恢复成功”。用户可以取消尚未执行的恢复。取消只删除本次待执行计划，不删除原备份或现有配置。

预览至少显示：原创建时间、来源版本、全局模块、当前账号、其他已存档账号、变更/恢复默认/移除项、图片数量、未兼容项，以及自动红包/收款等开关即将发生的变化。提交前再次核对账号和当前配置 revision，过期计划必须重新预览。

### 7.2 为什么首版在重新打开时应用

当前项目存在静态配置快照、NSNotification/Darwin 专用通知和异步图片回调。逐项写入偏好会触发观察者，简单增加一个“恢复完成”通知无法阻止中间状态被消费。首版把提交放在模块初始化之前，减少恢复过程中界面、付款任务和消息操作的交错。

这需要真正增加启动协调，不能依赖 `.xm` 文件名、编译顺序或某个 `%ctor` 恰好先运行：

- 所有插件配置初始化入口和 Hook 回调在消费新设置前检查同一恢复就绪状态；未就绪时保持微信原生路径，不创建依赖配置的单例或启动自动任务。
- 快速判断是否有事务日志；较大校验与资源工作异步执行，不在 `%ctor` 中同步解析整份备份，也不阻塞微信主线程等待 I/O。
- 启动协调器先解析恢复计划、确认账号/本机归属、校验目标当前状态，再启动事务。账号尚不可用时，不猜测也不无限阻塞宿主；保持待执行并提示可取消。
- 无恢复计划时走轻量正常初始化路径；有计划时，在提交或回滚完成后统一释放插件初始化。
- 各模块使用同一配置代次初始化。消息动作和支付任务不从备份恢复；已提交业务的持久完成记录始终保留。
- 账号在异步校验或应用期间发生变化时，使用现有账号边界机制使计划失效；尚未写入则取消应用，已经写入则进入回滚。配置归属由计划中的原账号 ID 决定，绝不随当前账号重新解释。

这项接入是方案中的主要实现成本和必要验收项，不能只改备份页面就宣称完成。

### 7.3 事务状态与失败处理

状态为 `prepared → applying → committed`；失败进入 `rollingBack → rolledBack`。日志记录源快照、目标账号、覆盖字段、原始存在性和值、资源旧/新映射、预期 revision 和事务 ID。

1. **prepared**：目标快照、迁移结果、恢复前保护快照和资源候选均校验并持久化；没有写入活跃配置。待执行期间若目标配置变化或账号切换，计划失效，要求重新预览；不悄悄覆盖新修改。
2. **applying**：启动屏障关闭，持久保存原始值及资源 before-image，再逐域逐键通过正确偏好 API 应用。只删除快照显式覆盖且标为不存在的键。原始/目标值必须含类型与存在性；账号复合字典按选中切片合并写回，不使用旧整份字典覆盖其他账号。
3. **核对**：校验每个模块的结构、账号切片、资源引用及目标值；检查偏好持久化结果。仅同进程 objectForKey 回读不构成重启后持久化证明，需独立重启恢复用例覆盖。
4. **committed**：记录可恢复的提交结果，再开放插件配置消费。保留最近事务的目标值和 before-image 供下次启动复核，不能提交后立即删除所有恢复材料。
5. **失败/被终止**：启动先处理未完成日志。未记录 committed 的应用事务回滚到 before-image；已记录 committed 的事务复核目标，必要时幂等补齐。日志与配置状态不一致时绝不直接开放相关插件功能。
6. **回滚失败**：保留原始备份、保护快照和日志；以原生微信路径继续运行，插件受影响功能保持停用，备份恢复入口仍可访问。报告真实状态，不能覆盖证据或显示成功。

多个偏好域没有系统级事务；原子重命名仅覆盖本地单文件。日志顺序必须满足“先保存恢复材料，再修改活跃配置，最后登记提交”，并检查文件写入、偏好同步及日志发布结果。事务实现必须测试偏好同步失败、单个文件提交失败、进程终止和再次恢复中断。不能把 `synchronize` 或一次 BOOL 返回包装成无条件断电安全。

### 7.4 数据保留规则

- 宿主域中未登记的键不改动；不使用清空整个 persistent domain 的捷径。
- 不改变微信数据库、历史消息、支付去重账本、已提交请求或账号所有权。
- 不删除其他账号或备份之后出现的新账号记录。
- 在恢复完整提交和下一次启动复核之前，不清理事务所需旧资源。
- 恢复配置不能主动补发通知、自动回复或复读历史消息；仅新的、符合原生准入的事件使用恢复后的功能开关。
- 全量恢复和按模块恢复共用同一事务流程，不存在绕过校验的“快速覆盖”。

## 8. 旧格式兼容

继续读取旧 `.wechatbackup`、`.wcbak` 和本地 `Library/Backup`，但进入独立的 LegacyReader，绝不直接调用旧恢复函数。

1. 检查旧 JSON 顶层、版本、元数据和内容结构，限制尺寸与深度。导入缺少有效 settings 时失败。
2. 只从已知域提取登记键。旧包中的微信其他设置不进入新备份，预览显示过滤结果。
3. 旧资源目录按旧导出协议解码，再用新资源白名单重建关联，不能把目录字典当 plist。
4. 原创建时间保留；另加本地导入时间。旧元数据中的绝对路径不作为本机定位依据。
5. 遇到 `__type__: unknown` 或历史丢失字段，标记对应模块不完整。已有导出丢掉的分组字典不能从 description 字符串可靠恢复，禁止 eval 或猜测还原。
6. 只有明确存在的旧键才作为可恢复项。旧包缺失字段不具备“恢复默认/删除当前值”的语义。
7. 旧本地 plist 中仍完整存在的数据优先走只读转换；转换产生独立 v2 快照，原文件、索引和时间线保留。
8. 新于当前支持版本的格式可作为不可恢复文件保管，但不强行套用；兼容恢复必须有明确版本迁移器。

## 9. 页面与交互

保留项目现有原生 UITableView 设置页风格。首页提供“创建备份”“导入备份”“自动备份”，显示最近有效备份时间和本机占用；列表用手动/自动/恢复前标记区分来源。

创建备份默认使用日期名称，名称与备注可选。创建后报告“已保存在本机”，可另选“导出到文件/分享”，不再强制进入发送流程。

详情页显示真实的模块数、配置字段数、账号数、资源数、体积和完整性状态；不把 plist 文件数叫配置项数。详情页提供预览恢复、导出、重命名、收藏、删除。

导入只增加备份，不自动应用。兼容性、缺失资源或不完整模块必须先呈现；用户可选择仅恢复明确完整的模块。系统文件选择器负责文件取得，必要时使用安全作用域和文件协调；归档处理在后台。

去除备份管理器内重复的私有微信发送逻辑，统一交给系统分享。若未来保留“发送文件传输助手”便捷入口，应独立为经过验证的发送适配器，区分提交与送达，不能把 AddLocalMsg 当发送成功。

不再把 `exit(0)` 称作自动重启。默认提示用户退出并重新打开；不能未经明确点击强制结束微信。

## 11. 实施顺序与验收

### 第一阶段：明确边界

完成所有设置页、Hook 配置读取和资源写入的登记表；区分主域/两个 Suite、全局/账号/本机关系配置、用户设置/派生状态。确定恢复后的初始化依赖，并使重置具备精确作用域和前置保护。

阶段出口：每个当前功能的配置项有归属，未登记项不能默默纳入；宿主键和支付账本有“不可写”测试。

### 第二阶段：可靠快照

完成 v2 模型、类型校验、资源关联、原子发布、后台 I/O、旧格式只读导入和索引重建。

阶段出口：从真实配置形状生成快照，导出后再导入，配置类型与图片字节完全一致；失败不产生有效列表条目。

### 第三阶段：可恢复的恢复流程

完成差异预览、按模块/账号计划、保护快照、启动屏障、事务日志、失败回滚、路径重建、代次与身份复核。

阶段出口：在每个持久化切点终止进程，再启动可收敛到完整状态；恢复旧配置不会重放业务动作，也不会覆盖其他账号或宿主配置。

### 第四阶段：自动保护与使用体验

接入变更调度、去重、保留配额、升级迁移前保护和状态展示，移除旧私有发送链路及误导性成功提示，更新 README。

阶段出口：未变化不写新快照，持续修改不会高频写盘，失败和系统后台限制可解释，手动/收藏/当前保护快照不被自动清理。

备份功能的发布门槛是“可完整恢复且失败可收敛”，不是“能生成文件”或“32 个旧脚本继续通过”。

## 12. 本次分析边界

本方案基于仓库源码和当前功能结构，确认了上述静态控制流及存储问题。没有执行真实备份、导入、恢复、重置、微信发送或设备安装，没有改动运行代码与真实配置，也没有把历史验证记录作为新方案已通过测试的证据。

下一步实施应以本方案的范围和验收标准为依据。完整键清单、启动屏障覆盖、偏好持久化及资源上限需要在实现阶段逐项验证；它们是明确交付要求，不是本轮已经完成的成果。


## 13. 1.8-37 实施决策与证据

2026-10-20 已按本方案实施，最终主机检查、包核对及真机未覆盖项以 [交付记录](../../audits/backup-configuration-1.8-37/README.md) 为准。上文第 12 节保留为设计阶段的分析边界。

- 实际登记为 313 个固定字段与受约束的账号选中键族，采用 `standard`、`legacy`、`layout` 三个域别名。精确清单见 [配置登记表](../../backup-configuration-registry.md)。资源引用内嵌在字段中，使用 `csbackup:<摘要>`，不额外维护可失配的路径索引。
- 图片按内容去重保存，但恢复文件名按配置项/联系人所有者生成。两个设置使用相同图片时不会共享可被任一编辑器删除的文件。固定 fallback 文件另有明确的存在性记录。
- 列表按文件扫描并返回紧凑摘要，避免同时保留全部快照图片。损坏旧文件保留并报告，发布成功的新备份不因历史清理错误被误报为失败。原件名称、时间、ID 与本机显示名称分开保存。
- 恢复前必须已知当前账号；账号复合字典仅修改选中且属于原备份覆盖范围的切片。自动去重也包含来源账号和安装标识，不能把相同内容的其他账号快照当作本账号新快照。
- `committed` 仅表示字段/图片已写入并核验；独立 `activation.plist` 才标记交接。未确认提交需继续核验或回滚，不能被新计划归档覆盖；取消此类事务先回滚。已确认提交在后续启动归档，保留用户其后正常修改。
- **最终交接的主线程例外：** 在账号边界锁内再次比较完整账号上下文，写入最多 4 KiB 的确认文件，并同步释放功能初始化回调；串行 I/O 队列等到此次交接完成，阻止同时取消/替换计划。大型事务日志、图片、编码和校验仍在后台。若原子写在重命名后报告目录同步失败，但可回读完全匹配的确认，则在同一锁内完成交接；否则保持失败并回滚。这里证明的是进程异常终止后的收敛，不承诺存储损坏或突然断电的无条件持久性。4 KiB 是字节上限，设备 fsync 耗时仍需实测。
- 首次升级因缺失图片等旧配置问题不能完成保护时，保留原数据并暂停插件功能，提供原生备份入口中的“修复当前配置”。没有活动事务时可进入原有图片编辑页修复，随后重试；不自动清空配置，也不跳过保护。未知未来 schema 仍需兼容版本或明确修复。
- 当前工程限制：文件 32 MiB、单图片 4 MiB、资源总量 24 MiB、256 个资源、1600 万像素、32 层嵌套；事务 before-image 的唯一图片合计不超过 48 MiB，序列化日志不超过 80 MiB。超限拒绝并保留原状，不能据此推定目标设备内存或速度已达标。

实现测试拆为 `Tests/verify-backup-{registry,codec,assets,legacy,engine,transactions,scheduler,store,bootstrap}.sh`，不再使用设计中的单一占位脚本名。真机恢复、私有账号生命周期、已有页面上的延后 Hook 安装、内存和主线程耗时仍为独立验收项。
