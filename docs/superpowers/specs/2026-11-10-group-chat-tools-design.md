# 群聊功能设计方案（评审稿）

日期：2026-11-10。适用项目：WeChatImprove，当前源码基线 `372dfae6`，现有版本 `2.4-2`。

本稿交付需求设计、项目接入方式和微信 8.0.80 IPA 静态分析结论。尚未实现功能、构建安装包或进行真机验收。用户已明确：退群通知只在原群显示为自己可见的本地提示，支持点击昵称进入资料页。

## 1. 推荐方案与取舍

采用“独立群聊模块 + 项目现有设置组件和原生群聊选择器 + 微信原生群服务”的方案。入群欢迎、退群监控、自动保存群聊共享经过校验的群事件；批量退群使用独立的操作队列。这样可以沿用项目风格，并把消息发送、成员数据判断和不可撤销操作分开处理。

考虑过另外两种方案：

| 方案 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- |
| 只解析入退群系统消息文字 | 初期接入少 | 语言、显示昵称、文案和群权限不同；普通成员退出未必产生可见消息；不能可靠定位真实 wxid | 不作为权威依据，只能用结构化消息辅助触发刷新 |
| 周期性获取所有群的全部成员并做差 | 思路直观 | 额外网络与耗电；容易把不完整名单误判为退群；仍不能保证后台实时性 | 不做常驻全量轮询 |
| 原生成员更新和入群结果驱动，完整快照做差 | 可以按 wxid 去重、还原群人数、复用原生操作 | 需要验证原生回调时机和完整性，实际检测时间取决于微信取得成员变化 | 推荐 |

退群监控的能力定义为：**当微信成功取得选定群的完整成员变化后，检测成员离开并插入本地提示。** 不承诺微信未取得群数据时立即知道退群，也不把“检测时间”描述为对方真实退群时间。单凭成员差集不能区分主动退出与被移出，默认文案中的“退出了群聊”只表达成员已离开，不增加“主动退群”等未经证实的原因。

## 2. 项目框架与设置入口

项目采用 Theos、Logos Hook、Objective-C ARC 和 UIKit，编译目标为 iOS 15+，arm64 / arm64e。设置不是 Web 页面，不涉及前后端端口或新的数据库服务。

首页 `CSCustomViewController.m` 的“功能增强”数组中，`clownItem` 是现有末项。在其后新增 `groupChatToolsItem`，标题“群聊功能”，点击 push 到新的设置控制器。

设置页继承 `CSSettingsTableViewController`，复用 `CSSettingSection`、`CSSettingTableViewCell`、InsetGrouped 表格、项目图标和配色、系统开关、右侧摘要与箭头；导航栏、安全区、浅深色适配交给既有公共组件。与小丑、红包等设置页保持相同间距、行高和分隔线规则。

页面分为四个 section，不另加第五个功能区，也不加冗余的总开关：

```text
功能增强
  ……
  小丑功能                         >
  群聊功能                         >

群聊功能
  入群欢迎
    开启入群欢迎                   开关，默认关闭
    选择群聊                       已选 N 个群 >
    欢迎文案                       内容摘要 >
    发送延迟                       3 秒 >

  退群监控
    开启退群监控                   开关，默认关闭
    选择监控群聊                   已选 N 个群 >
    通知文案                       内容摘要 >
    [说明：仅自己可见；点击昵称查看资料；在成员资料更新后检测]

  自动添加通讯录
    加入新群后自动保存             开关，默认关闭
    [说明：保存新加入的群聊到微信通讯录]

  批量退群
    选择群聊                       已选 N 个群 >
    退出所选群聊                   红色操作项
```

退群监控的本地提示就是用户确认的“退群通知”，每个离群事件只插入一条，避免出现简短监控提示和详细通知重复显示。批量退群不是常驻开关，只有明确选择群聊并确认后执行。开关关闭时保留已经编辑的名单和文案，依赖行置灰。

所有群聊选择都调用现有 `CSNativeContactPickerPresent(..., groups:YES, ...)`。该组件使用微信 `GroupSelectContactsViewController`，scene=4，支持原生搜索、多选、勾选回显和取消。欢迎名单、监控名单、批量退群临时名单相互独立。

欢迎文案和通知文案使用独立的多行编辑页，沿用定时任务的 UITextView 编辑交互；下方提供“插入变量”“恢复默认”和静态预览。保存时检查空白内容、长度、已知变量；非变量的普通 @ 文本保留。配置编辑在明确保存后生效，取消不写入。

## 3. 入群欢迎

**适用范围。** 仅欢迎选中群内新加入的其他成员。自己刚进入一个群时，先建立成员基线，不把该群已有成员逐个欢迎。首次启用、恢复备份和首次取得群成员列表同样只建基线。

默认模板：

```text
欢迎@昵称加入@群昵称
```

| 变量 | 含义 | 渲染规则 |
| --- | --- | --- |
| `@昵称` | 本次加入的新成员 | 生成显示文字和对应真实 wxid 的微信 @ 元数据；同批多人时逐个 @ |
| `@群昵称` | 群聊名称 | 替换为群名，不产生 @所有人 |
| `@时间` | 本次检测时间 | 按设备本地时区显示完整日期时间 |
| `@群人数` | 本次有效成员版本中的人数 | 使用完成校验后的人数 |

例如新人张三加入“读书群”，显示为“欢迎@张三 加入读书群”，其中新人昵称是真实可提醒的 @，内部保留微信使用的 @ 片段结束符。按群内成员昵称、原生联系人显示名、微信昵称的顺序取得展示名称，但身份始终使用 wxid，不通过昵称反查目标；这里的“群内成员昵称”与 `@群昵称` 代表的群聊名称不同。

**真实 @ 的原生依据。** 8.0.80.34 中，`CMessageWrap.setM_nsAtUserList:` 是对象参数 setter，IMP `0x104e51b60`。它在保存字符串后直接调用 `UpdateMsgSource`；后者读取用户列表，生成 `<atuserlist>…</atuserlist>`，最终写回 `<msgsource>…</msgsource>`。因此发送适配器要创建独立的新文字消息、设置真实用户列表，并交给微信 `CMessageMgr.AddMsg:MsgWrap:` 队列；不只替换正文，也不借用当前聊天输入框或草稿。

**延迟规则。** 建议默认 3 秒，支持 0–300 秒整数，0 为立即提交。计时从有效入群事件被确认时开始。同一批次多人加入合成一条欢迎语，分别填写真实 @，避免同批入群刷屏；不同成员版本的入群事件保持独立。

提交前重新检查账号、账号 epoch、功能开关、配置版本、群是否仍在欢迎名单、自己是否仍在群、待欢迎者是否仍在群、事件是否已处理。新人提前离开则从本条中移除，全部离开则取消。修改文案、关闭开关、移出名单、退出该群或切换账号后，相关旧任务取消。

微信进程暂停或系统挂起时无法保证精确延迟。进程恢复后，仅允许仍在有效期内且校验通过的任务继续，建议有效期截至计划发送时间后 120 秒；过期取消，不集中补发积压欢迎。微信发送方法返回只表示已提交；提交结果未知时不盲目自动重发，避免双发。

## 4. 退群监控与本地通知

选择需要监控的群，多选。首次启用和新增群时保存完整成员基线；在后续有效成员更新中比较稳定 wxid 集合，产生离群事件。

默认模板完整保留用户要求：

```text
@昵称 退出了群聊
检测时间：@时间
当前剩余人数@群人数，江湖再见！
点击昵称可进入资料页
```

`@昵称` 在本地提示中渲染为“@显示昵称”的可点击资料链接。它不是向退群成员发送 @ 通知。该变量可重复使用，所有出现位置均指向同一成员。`@群昵称`、`@时间`、`@群人数` 的含义与上表一致；文案支持多行、自定义标点和表情。

视觉使用微信 type=10000 的本地系统消息，与项目防撤回提示采用同一路径：居中、系统提示色、自然换行、昵称可点击。只写入原群本地聊天记录，不发送到群服务器，不通知其他群成员，不额外推送到文件传输助手。该功能不依赖“防撤回”开关。

资料链接使用独立命名空间，绑定账号、原群 wxid 和离群成员 wxid。正文、昵称、群名均进行 XML 转义，用户输入的文本不会成为可执行链接。点击时从当前消息所在聊天页进入原生资料页；优先通过微信 `ChatRoomUtils` 的群资料入口传入成员联系人和原群上下文，联系人暂不可解析时给出“该成员资料暂不可用”，不按同名联系人猜测打开。

快照保存离群前的展示昵称和必要的资料定位信息；昵称后来变化不改写既有提示。非好友资料的可见范围服从微信服务端结果，不能保证对已离群或无法查询的账号显示完整资料。

**正确性约束。**

- 只比较成功取得并通过完整性、版本校验的成员用户名集合；空响应、身份名单缺页、错误响应和旧版本不得覆盖有效基线。`isSimplify` 是详细资料简化标志，不能单独用来判定身份名单完整与否；必须核对 `allMemberUserNameList`、去重后的 `allMemberCount`、群身份和版本一致性。
- 不对 `GetGroupMember:` 返回的联系人对象数组直接做差，该方法可能因本地联系人未入库而漏成员；也不对 `newChatroomData.chatRoomMember` 的可合并详细资料集合做身份差分。使用已通过完整性校验的原生成员 username 列表。
- `@时间` 是检测成功的时间；`@群人数` 来自同一份更新后的完整成员数据。同批多人离开使用同一检测时间和最终人数，每人产生一条提示。
- 自己被移出、群已解散、群资料不可用或自己主动退出时，停用该群执行上下文，不把整群成员误报为退群。
- 同一成员退出、重入、再退出属于不同事件；去重绑定成员版本/成员在群周期，不能把 wxid 永久加入“已经通知过”集合。
- 结构化系统消息可以辅助定位成员或触发一次目标群刷新，但中文文案、显示昵称和普通群聊正文不能单独触发退群结论。
- 原生服务尚未取得新名单时无法发现变化。前台进入群、原生群资料更新等事件可以触发补充核实；不常驻高频拉取所有群。

## 5. 自动添加通讯录

开启后，只在本账号**由不在某群变为已在该群，并有可信原生成员状态佐证**时，把该群保存到通讯录。开启前已有群、启动时首次看到的群、旧历史同步、仅收到邀请但尚未加入，都不自动保存。

本次静态检索未找到可证明覆盖邀请、扫码、审批、面对面等所有普通群入口的统一“本人入群成功”回调。因此采用原生群联系人更新和本账号成员状态迁移作为主依据，辅助已确认的建群/入群路径。初次启用和冷启动先建立本人已加入群的基线；本地缓存首次出现一个群不等于新入群。新群状态不明时等待核实，避免把同步下来的旧群全部保存。

“保存到通讯录”是保存群聊条目，不是逐个把群成员加为好友。已经保存的群直接跳过，避免重复写入。

8.0.80.34 的原生调用链已确认：

```text
ChatRoomInfoViewController.switchSaveToAddressBook:
  → DelaySwitchSettingLogic.chatProfileSwitchSetting:withType:andValue:（type=3）
  → 原生设置处理
  → CGroupMgr.ShowInContactBook:sync:
  → CContactMgr.addContact:listType:opLog:callExt:
```

实现应通过当前账号的原生服务 wrapper 使用经过验证的保存接口，并沿原生设置提交链调度对应 oplog 同步，由微信完成通讯录条目、联系人状态和同步操作；不直接改微信数据库，也不只设置插件自己的“已保存”标记。`ShowInContactBook:sync:` 本体在此版本没有使用传入的 sync 值；原生设置提交会调用 `NeedToSyncOplog`。因此不能把传 YES 或 BOOL 返回当成服务端同步完成。调用前检查仍在该群，调用后回读本地原生保存状态，服务端同步结果另行核实；遇账号切换、恢复过程或群失效即取消。

## 6. 批量退群

流程为“原生选择器多选 → 查看待退出群清单 → 明确确认 → 逐群执行 → 结果列表”。选择器完成和退出操作分开，点“完成”只保存本次临时选择，不退出任何群。

确认页显示所有将退出的群名及数量，提供“同时清空所选群的聊天记录”复选项，**默认不勾选**，确认按钮文字为“退出 N 个群聊”。微信 8.0.80.34 原生单群退出弹层的清记录选项默认勾选；本模块依据用户保留数据的长期要求显式采用保留记录的默认策略，底层仍使用原生同一 `deleteAllMsg` 参数。勾选后确认页明确提示会清空相应群的本地聊天记录。

资料页已确认的调用链：

```text
ChatRoomInfoViewController.onQuit
  → 原生退出前业务检查
  → quitChatRoomConfirm
  → DeleteContactConfirmActionSheet
  → quitChatRoomWithDeleteAllMsg:
  → CGroupMgr.QuitGroup:withUsrName:deleteAllMsg:
```

批量能力必须保留原生业务检查、原生退出参数、服务器结果与原生后续清理。不得通过删除会话、隐藏群、修改插件名单等方式冒充退群。

**优先复用已证实的原生批量引擎。** `BatchQuitChatRoomLogic.startWithRoomNames:clearHistory:`（ABI `v28@0:8@16B24`，IMP `0x10038dc44`）内置去重、成员状态检查、CGI 18448 请求、逐群 outcome、成功后的 `reconcileBatchQuitGroupLocally:withUsrName:deleteAllMsg:` 和完成 delegate。单次最多 20 群，插件对更长名单自行拆批并串行启动。结果使用 `didSucceedRoom:`、`didFailRoom:errorMessage:` 及最终完成回调归集。

原生批量引擎没有资料页 `confirmOnArriveFund:` 的待收款检查，外层必须补上同类检查：查询原生有效群收款/转账待办，有待办的群转入“需处理”，由用户进入原群处理后重新选择；不能声称批量类自动具备资料页全部业务检查。检查接口或 ABI 不可用时暂停该群，不绕过检查执行。

执行约束：

- 每次执行前重新解析群 ID、当前账号和在群状态。原生选择器为配置保留的不可解析旧群 ID 不得直接交给退出服务。
- 每批先逐群完成预检，再提交最多 20 群给同一个原生批量引擎；等待本批完成或停止后，再启动下一批。不并发创建多个批量引擎。
- 群收款等原生检查要求处理、需要额外用户操作或群状态不支持直接退出时，标记“需处理”并提供进入原群资料页的入口；保留原生提示。群主相关特殊流程应服从原生实际行为，不能猜测自动转让或解散。
- 显示“等待中、处理中、已退出、失败、结果待核实、需处理、已跳过”。原生接口调用返回不能直接记为已退出。
- 原生批量引擎对缺失结果或特定暂态错误内置最多 3 次重试；保留其原生策略，插件不再叠加自动重试。最终超时、网络中断或结果未知时先核实自己是否还在群，再由用户决定是否重试已确认失败项。
- 操作期间提供“停止后续处理”。它阻止尚未提交的后续批次；已提交批次内的任何群仍可能完成退出，不能承诺撤销。账号切换立即停止后续批次，迟到回调不得写入另一账号的插件执行状态；原生已提交操作的最终结果需要回到原账号后核实。
- 不把自己批量退群导致的数据变化发成成员退群提示，不对已退群发送待执行欢迎。
- 运行队列不随备份恢复，不在重启后自动继续退出；可保留结果供查看，待执行退出必须重新由用户确认。

## 7. 模块与数据设计

使用 `CSGroupChat*` 或 `CSChatRoomTools*` 前缀，避免与现有用于“聊天分组”的 `CSGroup*` 类混淆。

| 组件 | 职责 | 主要依赖 |
| --- | --- | --- |
| `CSGroupChatSettingsViewController` | 四块设置、模板编辑入口、原生选择器接入 | 公共设置组件、原生选择器、配置 |
| `CSGroupChatPreferences / Store` | 按账号保存配置、版本校验、原子写入 | 现有存储与账号生命周期组件 |
| `CSGroupChatNativeAdapter` | 核对微信类/方法 ABI，取得群数据，保存通讯录、退出群、打开资料 | `CSGetService`、当前账号原生 wrapper |
| `CSGroupChatEventCoordinator` | 完整成员基线、差集、事件归并、去重、自入群识别 | 原生成员/入群回调、账号 epoch |
| `CSGroupChatTemplate` | 变量解析、正文渲染、真实 @ 目标映射、本地链接转义 | 已确认的事件数据 |
| `CSGroupChatWelcomeQueue` | 延迟、过期、取消、提交前复核 | 事件、模板、新消息发送适配 |
| `CSGroupChatLocalNotice` | 插入 type=10000 系统行、独立昵称点击路由 | 本地消息接口、原生群资料入口 |
| `CSGroupChatQuitCoordinator` | 确认后的串行退出、业务检查、回调、结果 | 原生退出能力、执行上下文 |

Hook 只采集原生输入输出并投递协调器，保留原始调用，禁止在消息/群数据回调内做阻塞文件 I/O、全群遍历或网络等待。沿用现有 Hook 的签名校验、线程切换和 `CSBackupWhenReady` 启动模式。功能关闭时不持续拉取成员。

成员事件以 `CGroupMgr.OnGetChatRoomMemberDetail:`（`v24@0:8@16`，IMP `0x10203ed80`）外层为候选主入口。原生处理前捕获账号、epoch、群 ID、request/response 身份和前一次有效基线的不可变副本；原生处理返回后再核对响应 ret、完整身份名单、群身份及最终 `chatRoomVersion / localMemberVersion`，然后发布快照。不能 retain 会原地变化的 CContact 对象充当旧快照，也不能在中间 `updateChatRoomMemList:withResponse:` 返回时就把尚未完成更新的版本当成本次最终版本。

建议新模块目录为微信宿主沙盒 `Library/Preferences/WeChatImprove/GroupChatTools/`，按账号 hash 分域：

- `preferences`：欢迎开关/名单/文案/延迟、监控开关/名单/通知文案、自动保存开关、schemaVersion。
- `member-baseline`：仅对已启用的欢迎/监控群存储有效成员版本、稳定 username 集合和必要显示名；新账号或损坏数据重建基线，不解释为退群。
- `event-state`：有限期事件去重、处理状态和自加入群基线；按成员版本维护，设置容量与过期清理。
- 退出临时选择和待执行队列不作为可恢复配置；延迟欢迎不跨进程自动补发。

所有自动动作与编辑回调的异步执行上下文绑定 `account + accountEpoch + configurationGeneration + roomID + eventID`。账号 A→B→A 时旧 epoch 失效，不能因账号名重新相同而恢复旧的自动动作；模板编辑、选择器回调和延迟任务均需要重新复核。

已经写入聊天记录的昵称链接是持久内容，只绑定 `account + roomID + memberID + eventID`，不绑定生成提示时的 epoch 或文案版本。点击时确认当前账号匹配，再创建属于当前账号 epoch 的短期导航上下文；这样重新登录同一账号、修改文案或关闭监控后，历史提示仍可打开资料，切到其他账号则不能使用原链接。

接入现有备份 registry 的显式白名单，只备份可恢复的功能配置。恢复后重建成员基线、取消旧执行，不重放历史欢迎、通知或退出任务。配置异常时保留原文件，关闭自动动作并给出可理解的错误，不重置微信数据。

## 8. 分阶段实施与验收

顺序建议：设置入口/原生选择器/账号配置 → 成员事件与完整性规则 → 本地退群通知与资料页 → 真正 @ 的延迟欢迎 → 新入群保存 → 带原生检查的批量退群。先建立群事件边界，再接自动动作。

静态接口存在不等于真机验收通过。实施完成后至少覆盖：

| 功能 | 必须通过的验收 |
| --- | --- |
| 设置与选择器 | 入口紧跟小丑；四组 UI 与现有设置一致；原生多选/搜索/回显/取消；空名单；浅深色；账号切换不串配置 |
| 入群欢迎 | 邀请入群、二维码、多人同批入群；对端实际收到 @ 提醒；同名成员不串人；0 秒/延迟；新人提前离开；重复回调；自己加入不欢迎全员 |
| 退群监控 | 真实离开后只出现一条本地系统提示；其他群成员看不到；默认文案和人数正确；点击昵称进入正确资料；防撤回关闭仍可用；非好友/无法查询资料可解释 |
| 成员正确性 | 初次启用、冷启动、备份恢复、离线恢复、身份名单缺页、详细资料简化、重复/旧版本响应均不误报；简化资料仍按身份名单完整性判断；自己被移出或群解散不产生全员退群通知 |
| 自动保存 | 新入群成功后在微信通讯录看到群；原生群资料开关一致；旧群不批量补存；已保存群不重复处理；仅收到邀请不保存 |
| 批量退群 | 选择完成不退出；清记录默认关闭且参数正确；20 群及超过 20 群拆批；逐群服务器结果；待收款等原生业务检查；失败/未知结果；停止后续批次；切号停止；重启不自动恢复执行；OpenIM/特殊群通过单独验收前不承诺支持 |
| 回归与数据 | 现有防撤回、定时任务、AI 回复和聊天分组正常；原有包和账号数据保留；只使用明确的测试群验收实际发送/退出 |

本轮仅完成设计与静态取证，不进行真实群聊发送、保存或退出，不产生安装包。
