# WeChat 8.0.78.34 menu and text regressions: static evidence

Target: `/tmp/wechat-8.0.78-inset-analysis/WeChat`, decrypted arm64 Mach-O, SHA-256 `0b3cd1e2ed1da493a6fe12c9ef6e9b9421c95bcac63417c677f309536f7c1c8e`. Target was not executed. Native metadata and bounded `xcrun llvm-objdump` disassembly were extracted into this directory only. Existing evidence was not imported or overwritten.

## Decisive findings

1. **Voice repeat is deduplicated away.** `CSMessageActionMenuAdapter` creates voice-forward before repeat and explicitly sets both `menuType=0`. Native `-[BaseMessageCellView showOperationMenu]` invokes `generateOperationMenu`, `uniqMenuItems:`, then `filteredMenuItems:` (0x1002a4ce4–0x1002a4d34). `uniqMenuItems:` at 0x1002a409c uses only numeric `menuType` as an `NSMutableIndexSet` key; 0x1002a41dc queries `containsIndex:`, and 0x1002a41e0 skips a duplicate. Thus, when both plugin voice actions were admitted into the array, voice-forward wins and repeat disappears. This is derived directly from host assembly and current adapter source, without needing a target-object hypothesis.
2. **App sticker, file, and card builders bypass the Common hook.** `AppEmoticonMessageCellView` (0x1000c6d34), `AppFileMessageCellView` (0x1000cee70), and `ShareCardMessageCellView` (0x1058f85b4) each implement `operationMenuItems` and build a fresh array without calling the superclass method. The six current hooks omit all three. `CommonMessageCellView` has no own native implementation of `operationMenuItems`; its superclass is `BaseMessageCellView`. These separate subclass implementations do not dispatch into a newly installed Common implementation. The actual device class for the user's missing sticker remains unobserved; the AppEmoticon omission is proven for that native class, not an attribution of every sticker to that class.
3. **Card repeat is independently denied by plugin policy.** Coordinator menu-repeat whitelist is `[1,3,34,43,47,48,49]`; type42 is absent although the sender already has a `cardMsgFromMsgWrap:` route. The new explicit card requirement requires admitting42.
4. **Text sender resolves a receiver absent from this binary.** Native `BaseMsgContentViewController` has concrete `m_delegate` getter at 0x100365c14, ABI `@16@0:8`, reading weak ivar `m_delegate` offset152, type `@"<BaseMsgContentDelgate>"`. No `m_logicController` or `logicController` method/ivar exists in this class's native metadata. The current sender probes only those two getters then the controller, which has no `SendTextMessage:` method, and returns nil. That explains `FailedBeforeAcceptance` before submission.
5. **The native logic object is the proven text receiver.** `-[BaseMsgContentLogicController initViewController]` at 0x1002b52e4 generates the page and calls `[page setM_delegate:self]` at 0x1002b5338–0x1002b5340. Consequently the concrete page's `m_delegate` is the native owning logic object on this standard path. Its `SendTextMessage:` implementation is present and matches the adapter's requested void ABI. `SendTextMessageToolView:` on the page itself is a UI input path with validation, input reset, and async/reply behavior; it is not the same selector.

## Menu ABI and retained restrictions

`operationMenuItems` returns `@16@0:8` on all inspected concrete builders. `MMMenuItem` `initWithTitle:icon:target:action:` has encoding `@48@0:8@16@24@32:40`; `initWithTitle:target:action:` is `@40@0:8@16@24:32`. `menuType` is `q16@0:8`; `setMenuType:` is `v24@0:8q16` (0x1167a6f84). `MMMenuController setMenuItems:` is `v24@0:8@16` and converts input to rows through `setMenuItemRows:`.

Use distinct stable **positive** plugin menu IDs. Negative values are unsuitable for `NSIndexSet`. The inspected code does not establish a universal host enum maximum, so an application-reserved namespace is a design choice, not a recovered native constant. Native values observed in inspected builders/reordering include0 through58; that observation is not an exhaustive enum proof. Preserve normal native filtering by adding items in the concrete `operationMenuItems` hooks before the host pipeline, rather than appending globally after restrictions.

`filteredMenuItems:` preserves unknown numeric IDs on the normal iPhone path: `isOnlyShowDeleteMenu` false branches 0x1002a4620->0x1002a4864; `isVisionPro` false branches 0x1002a487c->0x1002a4b68; then the current array is copied. Restricted bypass-user processing uses a localized title whitelist, WeClaw uses a title blacklist, and only-delete mode allows native8/4/5 or a specific localized title. VisionPro excludes numeric IDs14,13,3,25,12,19,15. These restrictions should remain effective. `+[SessionMenuAdjuester adjustCustomMenuItems:]` at0x1057cfbe4 relocates native types5,4,8,46,47,57,58 and preserves unknown values.

`MMMenuController onMenuItemSelected:itemView:` reads explicit item.target; if nonnil, it calls `safePerformSelector:withObject:afterDelay:` on that target (0x1165e1cc8). Only the nil-target branch calls the menu responder's `canPerformAction:withSender:`. Thus a retained CSMessageMenuInvocation explicit target is supported by the inspected dispatcher; static evidence does not require reverting to the cell as target. MMMenuItem's target is weak (getter weak-load helper); retaining the invocation as an item-associated object is necessary and current adapter already does it.

## Card source-context follow-up

The card hook can use the existing source resolver without a card-specific fallback. Native `ShareCardMessageCellView` inherits through AppStandardAccountContentMessageCellView -> AppStandardContentBaseMessageCellView -> CommonMessageCellView -> BaseMessageCellView -> BaseChatCellView -> UIView. Its concrete inherited `viewModel` method is `-[BaseChatCellView viewModel]`, address0x10029cf78, encoding `@16@0:8`, loading object ivar `m_viewModel` at offset16. See BaseChatCellView--viewModel.asm.

Its model chain is ShareCardMessageViewModel -> AppStandardAccountContentMessageViewModel -> AppStandardContentBaseMessageViewModel -> CommonMessageViewModel -> BaseMessageViewModel -> BaseChatViewModel -> NSObject. `-[BaseMessageViewModel messageWrap]` at0x1002b1a44, encoding `@16@0:8`, directly loads object ivar `m_messageWrap` (CMessageWrap) offset48. It overrides the base `-[BaseChatViewModel messageWrap]` at0x10029e294, which returns nil. See BaseMessageViewModel--messageWrap.asm and the exact two-instruction BaseChatViewModel--messageWrap.asm.

No inspected app class on this card cell chain implements `getCurrentMessageWrap`; the resolver's initial getter therefore does not need to succeed. Existing CSMessageActionResolveSourceWrap reads `cell.viewModel`, attempts its bounded parent-model traversal, then returns `root.messageWrap` or `model.messageWrap`. No parentModel implementation appears in the inspected card-model app-class chain. `class_getInstanceMethod` resolves inherited viewModel/messageWrap methods, so the strict concrete-method validation supports this path. The card cell inherits UIView and thus retains the current nextResponder-based page-controller lookup. This establishes native method availability and the intended context path; actual device model population/responder attachment still requires acceptance testing.

## Persisted voice-wrapper refresh follow-up

The exact normal lookup contracts are `-[CMessageMgr GetMsg:LocalID:]` at0x104b32814, encoding `@28@0:8@16I24` (chat username object, unsigned32 local ID), and `-[CMessageMgr GetMsg:n64SvrID:]` at0x104b328b4, encoding `@32@0:8@16q24` (chat username object, signed64 server ID). These return a wrapper or nil. Local lookup passes a stack error flag and `needOriginContent=NO` to `GetMsg:LocalID:hasError:needOriginContent:` at0x104b326c8, encoding `@40@0:8@16I24^B28B36`. That implementation forwards the same chat and ID to its `m_oMsgDB` (`CMessageDB`, native ivar offset8), invokes `CheckMessageStatus:Msg:` on a nonnil result, and returns that same result. Server lookup follows the same database/status-check pattern. `onGetMsg:LocalID:Wrap:` at0x104b44b70 simply tails normal local lookup; the supplied Wrap argument does not provide the refresh result.

This is a persisted-message lookup, not a getter for the original UI object. `CMessageDB GetMsg:LocalID:` at0x104afa2f8 uses column `msgLocalId`, and `GetMsg:n64SvrID:` at0x104afa474 uses `msgServerId`; zero IDs return nil, and each query returns its first row. Their shared query `GetMsg:Where:order:Limit:hasError:needOriginContent:` at0x104af7a40 passes the original x2 chat (saved in x25 at0x104af7a74, restored as x2 at0x104af7b7c) to `GetMessagesByChatName:onProperty:where:order:limit:hasError:`. It constructs a new CMessageWrap from database row type, local/server IDs, content, status, createTime and other fields, then calls `GetMsgExtInMessageExtWithTable:chatName:localId:` and `HandleMessage:ChatName:Des:`. This establishes rehydration from the named conversation's persisted record; it does not establish that a downloaded audio file is usable.

Native downloader corroboration is retained in `docs/evidence/message-actions-native-2026-10-17/VoiceMsgDownloader--OnRecvData_MesLocalID_n64MesSvrID_CreateTime_VoiceTime_Offset_Len_Data_EndFlag_ErrNo_.asm`: callback username x2 is saved in x19 at0x106292c2c, localID x3 in x27 at0x106292c28, and the callback calls CMessageMgr `GetMsg:LocalID:` with x2=x19 and x3=x27 at0x106292d3c–0x106292d4c. Thus normal native voice processing uses this same chat-plus-local-ID contract. Its nil-result fallback creates a new type34 object; a plugin refresh should retain its failure path rather than copy that fallback.

`CheckMessageStatus:Msg:` at0x104b33820 (`v32@0:8@16@24`) prevents describing these manager methods as universally pure reads. For stale uploading image/record-note/emoji cases it can set status5 and call `ModMsgByBitSet:MsgWrap:BitSet:` at0x104b339ac–0x104b339dc; video and app49 have their own status branches. For an ordinary type34 voice wrapper whose native image/record-note/video predicates are false, the emoji47 branch is excluded at0x104b33960, app49 is excluded at0x104b33a24, and the final branch either returns for status!=1 at0x104b33a70 or excludes type!=1 at0x104b33a84. That path reaches the release/return at0x104b33b44 without a status/media setter or database modification. This is a bounded characterization of the ordinary voice path, not a proof that every dynamically classified wrapper has those predicate results.

Use the returned wrap only as a refresh candidate after native callback matching. Preserve the operation's captured source/context and account epoch; validate candidate type34, conversation, sender/recipient and all available local/server IDs before reading readiness from it. Re-run audio readiness checks and retain failure if lookup is nil, identity mismatches, or media remains unusable. Callback completion plus nonnil lookup is not a delivery or audio-readiness acknowledgment. `getmsg-refresh.py`, `getmsg-refresh-methods.json`, `getmsg-refresh-summary.txt`, and the CMessageMgr/CMessageDB assemblies in this directory reproduce the bounded lookup and status evidence. REA session state was checked after extraction and reported `open=false`.

## Limits and provenance

This is static, version-specific evidence; it does not confirm installation, runtime class selection, enabled settings, network delivery, or all device failures. Plain EmoticonMessageCellView's own hook exists; its missing repeat cannot be attributed to a missing concrete hook without the runtime class/menu trace. The methods examined do not show a universal menu-count truncation explaining these failures. Image/reference uncertainty feedback is accounted for by current `CSVoidRoute` returning Unknown on every void call, but the semantics of acknowledgment should be resolved in the coordinator, not fabricated from this static analysis.

The extraction reads Objective-C class/metaclass metadata and both category lists, resolving chained bind import class names. There were no direct categories attached to the selected app classes; local categories may already be merged into class lists by the linker, and foreign superclass categories/dynamic injection remain outside this negative-search claim. Bound superclass pointers are resolved through LC_DYLD_CHAINED_FIXUPS imports. Disassembly boundaries use the next selected class method entry and can include compiler blocks in the same interval; retain exact addresses when citing. Selector comments are analyst-added pointer decodes; machine instructions and metadata.json are primary evidence, and incidental unreadable class-reference comments should not be treated as selectors.

REA open_binary independently confirmed the target SHA and arm64 Mach-O. A Ghidra analyze_function request was interrupted during the model/task interruption and supplied no retained decompilation result; no claims here rely on that request. Files in manifest.json provide the independently reproducible metadata and assembly evidence.
