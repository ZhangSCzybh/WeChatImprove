## Findings

No new proven reason for the missing sticker item has been established. The 1.8-3 controller-accessor correction remains a valid structural improvement, but device failure shows that its host fixture did not establish coverage of the user's failing path. A second speculative sending change cannot fix an item that is never admitted or displayed.

1. The known native sticker classes and source scalar ABIs agree with the current menu code. Both `EmoticonMessageCellView` and `AppEmoticonMessageCellView` have concrete independent `operationMenuItems` hooks in production. Their native model `cellViewClassName` methods return the respective class-name constants directly. The inspected source chain has concrete `-[BaseChatCellView viewModel]` and `-[BaseMessageViewModel messageWrap]`, both object-return `@16@0:8`. None of the inspected sticker/base-cell chain owns `getCurrentMessageWrap`, and neither `BaseMessageViewModel` nor `CommonMessageViewModel` owns `parentModel`. This describes shipped metadata, not a runtime-injected method or subclass.
2. `CMessageWrap.m_uiMessageType` is unsigned32 `I16@0:8` at `0x104bb4040`; current `CSMessageNativeUnsigned` and `CSActionUnsigned` support it. `m_nsFromUsr` and `m_nsToUsr` are object getters at `0x104bb400c`/`0x104bb401c`, both `@16@0:8`. There is no sticker-only scalar-ABI mismatch at these inspected gates.
3. `+[CMessageWrap isSenderFromMsgWrap:]` is `B24@0:8@16`, address `0x104ba814c`. The current class-method invocation is ABI-correct. Native behavior first returns true for `m_uiIsSenderStatus==1`, false for status2; otherwise normal message types compare `m_nsFromUsr` against `MMContext.currentUserName`, with a legacy QQ-address branch. The plugin additionally requires outgoing.from==its captured account or incoming.to==its captured account. A status/endpoint mismatch therefore causes admission failure, but the phone's actual fields are unavailable. Do not weaken account validation merely because such a mismatch is possible.
4. The previously uninspected `+[CBTAskXiaoWeiMenuMutexHelper removeMutexMenuItemsIfNeeded:]` does not explain unknown plugin IDs disappearing in this artifact. It checks for an AskXiaoWei item and an experiment before filtering. Its predicate retains non-MMMenuItem objects and MMMenuItems whose numeric ID is absent from `mutexMenuTypes`. The fixed set is 22,29,28,42; plugin IDs `0x43535001`/`0x43535002` are not members. See instructions at `0x100792500`–`0x100792588`, predicate `0x1007925c4`–`0x10079268c`, and the set construction in `mutexMenuTypes`.
5. The final MMMenuItem container stages inspected here preserve plugin item identity. `-[MMMenuController setMenuItemRows:]` (`0x1165e0f34`, `v24@0:8@16`) directly adds an MMMenuItem to its output row at `0x1165e1118`–`0x1165e1124`. Only plain UIMenuItem inputs are converted to MMMenuItem. It does not gate MMMenuItems on target/action permission. `MMMenuItemData` initialization similarly retains MMMenuItem inputs; `calculateMenuLayout` assigns line-position/item-frame values and does not inspect selector, title or menuType. The plugin's initial linePosition0 does not establish hidden status.
6. The concrete `MMMenuItem initWithTitle:icon:target:action:` at `0x1167a4d08` is `@48@0:8@16@24@32:40` and stores title/icon/weak target/action as the adapter expects. Its alternate initializer is `@40@0:8@16@24:32` at `0x1167a519c`. Numeric `menuType` is q and `setMenuType:` v24@0:8q16. Text/image success in the same installed release independently argues against a universal item-construction failure. Runtime setter/getter postconditions may still improve diagnostics, but are not a demonstrated repair.

The previous evidence remains applicable: `showOperationMenu` calls generate -> uniq -> filtered -> SessionMenuAdjuester -> MMMenuController. Numeric uniq uses menuType; normal iPhone filtering preserves unknown numeric IDs; restricted native modes keep their original filtering. `generateOperationMenu` has record-detail and unsafe-message branches before its normal dynamic `operationMenuItems` call. Do not add an unconditional post-generation/post-filter fallback that silently changes those restrictions.

## Minimum next step justified by current evidence

Keep the known concrete hooks, account/message validation and native filtering. Add bounded local diagnostic observations of the failed menu attempt, so that the next device reproduction distinguishes a missing builder call from failed admission and native item removal. Suggested stages and fields:

- `menu.builder`: actual cell class, resolved model/wrap class, numeric message type, repeat/voice toggles, incoming/native item count, plugin-selector counts before/after. Record whether current-wrap or model-wrap resolution was used and whether they were the same object, not their textual payloads.
- `context.capture`: an explicit reason code for off-main, account absent/suspended, source absent, endpoint absent, native direction mismatch, conversation mismatch, binding missing, controller absent/wrong class, or success. Include only booleans such as fromMatchesAccount/toMatchesAccount/nativeOutgoing and object class names; never actual account IDs, chat IDs, message contents, local/server IDs, sticker MD5 or filesystem/media paths.
- `menu.construct`: constructor ABI match, item class, title/action/target postcondition booleans, requested/read-back menuType. Distinguish init nil, exception, unsupported setter and setter mismatch.
- `menu.generate`, `menu.uniq`, `menu.filtered`: read-only before/after counts and whether our two selectors are present. Observe `BaseMessageCellView.generateOperationMenu` as well as concrete builders; otherwise a missed subclass hook produces no trace. Do not mutate arrays at these observation stages.
- If added items survive these stages yet remain absent, optionally observe `MMMenuController.setMenuItems:` without mutation, recording presence/counts and responder class. A trace correlation token can be an in-process per-attempt counter, not a user/message identifier.

Expose or export only a small bounded recent diagnostic record through an explicit user action. A passive observation should neither create a message/send nor repeatedly display toasts while opening normal menus.

A useful optional discriminating observation is whether the same sticker can be repeated through the configured message gesture. The menu and gesture share context validation; gesture success would narrow the fault to builder/display handling, while an invalid-context message would narrow it to source/page capture. This is not a prerequisite to fixing the independently proven voice constructor mismatch found by the other investigation.
