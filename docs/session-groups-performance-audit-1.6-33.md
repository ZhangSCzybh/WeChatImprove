# 聊天分组性能与隐患复查：1.6-33

2026-10-17，基于已推送的 `217f297b63b1ffd602c38ce4917e1fe017984f51`。本轮在提交 1.6-33 后继续分析，仅增加本地审计脚本、结果和报告，未修改生产代码或重新打包。原有用户文件、旧安装包删除状态均保留。

## 结论

1.6-33 已阻止普通离屏更新持续重建分组列表，但不能据此认定分组已没有性能问题。前台仍然每次全量读取、计算和重载；更重要的是，存在一个待执行导航与账号切换组合导致离屏保护被绕过的条件性缺陷。

优先处理队列生命周期和关闭/搜索时无效计算，再拆分数据变化与用户选择，最后处理转发及分组栏重复布局。指示器动画不应作为首要优化对象。

## 新复现的风险

### P1：跨账号残留导航队列可以绕过离屏保护

位置：`Controllers/CSGroupListAdapter.m:326`、`:347`、`:396`、`:427`、`:459`。

前提：同一个适配器在隐藏期间仍有待执行的原生导航（例如因原生事务尚未结束而排队），随后账号由 A 切换为 B，分组仍启用、非搜索。

1. 待执行导航将 `nativePresentation=YES`，但事务阻止立即发布。
2. 账号变化后，refresh 的 `changed` 分支将 `nativePresentation` 重新设为 NO。
3. 新账号的有效投影使 `isActive=YES`；队列只在 `!isActive` 时取出，因此旧账号任务留在队列里。
4. 离屏保护使用 `!nativeActions.count` 判断是否拦截；残留任务让后续普通刷新持续获得例外权限。

将真实账号变化分支纳入隔离回放后：队列残留 1 项，旧账号动作实际执行 0 次，仍处于暂停状态的适配器收到后续 3 次普通更新时发生 3 次发布。

这不是已确认的跨账号误操作：执行块自身的账号校验仍有效。确定的问题是失效任务不被淘汰，导致不必要的离屏重建和导航排队滞留；闭包也可能延长所捕获对象的生命周期，尚未做泄漏测量。实机是否满足“适配器跨账号继续存在”等触发前提，需要运行时验证。

建议：任务显式携带账号/代次，账号变化先取消失效任务；离屏发布例外只能由当前有效的导航任务获得。不要用任意非空数组代表有合法导航。

**测试覆盖更正：** 既有 `GroupLifecycleTests.m` 的 `publishFixture` 省略了真实 refresh 中账号变化重置 `nativePresentation` 的分支。因此上一轮 336 项测试通过是真实结果，但其“跨账号导航”场景不足以覆盖这个组合问题。本次审计脚本直接抽取该分支，补足回放，不修改或掩盖原测试结果。

### P2：刷新重入时的导航请求可能排队后没有唤醒

位置：`Controllers/CSGroupListAdapter.m:323`、`:396`、`:455`。

若发布已经进入投影模式的刷新过程中，同步回调再次请求原生导航：动作入队，`useNativePresentation` 改变展示标志后调用 refresh，但 refresh 因 publishing 直接返回。如果外层此时仍是 active 投影，完成路径不取出队列，而且没有设置 dirty 或安排补跑，动作需要等后续其他事件才能继续。

隔离状态回放得到：待执行任务 1 项，dirty=NO，scheduled=NO。回放验证了方法状态机缺少唤醒；未证明微信原生在用户设备上一定会在这个精确窗口发出导航。

建议：重入请求独立记录待处理状态；外层发布完成后合并唤醒一次，并再次验证账号，避免递归重载。

### P2：回顶部没有覆盖独立的分组手势状态

位置：`Controllers/CSGroupListAdapter.m:756`。

refresh 已保护 `groupPanMoving`，但 applyPendingScrollToTop 只检查 table 的 tracking/dragging/decelerating/editing 和菜单。两处的交互保护不一致。

抽取真实方法后，设置 pendingScrollToTop=YES、groupPanMoving=YES、所有原生 table 跟踪标志为 NO，仍写入一次 contentOffset 并消费待执行请求。这与此前必须单独保护分组手势的原因一致，可能表现为手势途中跳到顶部。

建议：回顶部与刷新共用明确的交互准入规则；手势结束后再执行一次待处理顶部定位。保留短列表、搜索及原生表头语义。

## 仍然存在的主要性能开销

### P1：前台全量重建，跨事件循环没有限频

位置：`Controllers/CSGroupListAdapter.m:348`、`:358`、`:378`、`:387`、`:424`；`Hooks/SessionGroupHooks.xm:174`。

每次获准刷新都读取整份分组配置、全部原生会话并计算所有角标，更新整个分组栏，重载并布局表格。scheduled 仅合并尚未执行的任务；50ms 延迟只属于手势避让，不能解释为稳定刷新上限。

本次前台主机回放中，20 次分开进入事件循环的请求产生 20 次发布。会话总量较大或连续消息到达时，主列表可能在停滑后集中卡顿，切组同样重读全量数据。

建议按账号和数据代次缓存不可变快照，用户只切换选中组时复用快照；未读变化和结构变化区分处理。通知更新做有上限的合并，用户显式操作仍及时响应。私有模型读取继续留在主线程，不能直接把可变宿主对象丢到后台。

### P1：关闭分组或搜索中，仍先执行分组构建

位置：`Controllers/CSGroupListAdapter.m:350`、`:358`、`:367`。

enabled/searching/nativePresentation 的投影启用判断出现在原生快照和投影构建之后。关闭分组或进入搜索并不让前台 refresh 提前跳过这些工作；挂接和原生事件 Hook 仍在，请求仍可进入。随后还会更新分组按钮/角标并 reloadData，即使分组栏实际隐藏。

这是源码中直接可达的路径，不声称已经测出设备关闭分组后的具体 CPU 占比。它意味着关闭功能并不等于完全消除分组计算成本，也可能叠加原生列表自己的刷新。

建议：模式切换时执行必要的一次清理/恢复；已处于禁用或搜索状态时走原生轻量路径。需要保留代理坐标、表头和预取切换的一致性，不能仅在 refresh 顶部直接 return 而留下旧投影。

### P1：选择保存与全量刷新串行发生在切组路径

位置：`Controllers/CSGroupListAdapter.m:733`；`Controllers/CSGroupPreferences.m:142`、`:196`。

setSelectedTabID 会 reload 全量配置、规范化成员、构造完整 profile、保存原始/上一份备份、写入 profile 集合、synchronize 并读回校验。完成后 selectIndex 又进入全量 refresh。因此单次切组的等待由配置保存和数据/UI 重建共同组成。

本次使用真实 Preferences + 内存 defaults 检查：即使直接给 setter 传入相同 selectedTabID，也执行 2 次 setObject、1 次 synchronize。UI 的 tabButtonTapped 已经忽略点击当前选中标签，不能将此描述为每次点击当前标签都会写入；该结果反映的是 setter 缺少无变化早退及完整配置保存的成本。

建议：选中组采用账号隔离的轻量保存路径；成员、名称、顺序变更继续保留完整校验、备份和冲突保护。

### P2：高频代理与分组栏重复工作

- `CSGroupListAdapter.m:615`：滚动回调也走 NSInvocation、选择器字符串、作用域与通用路径处理；可对明确不含行索引的高频回调增加直接转发路径。删除和匿名业务行的身份复核仍须保留。
- `WESessionTabContainerView.m:276`：updateTabs 每次线性查找旧按钮，形成 O(G²) 复用查找；再对所有按钮更新字体、外观并强制 layoutIfNeeded。
- `WESessionTabContainerView.m:175`：refreshAppearance 会重新读取、解档自定义颜色；updateTabs 每次都调用它。可以按外观配置及 trait 变化失效缓存。
- `WESessionTabContainerView.m:85`、`:257`：未读值不变仍重设文字和请求布局；布局中每个标题宽度计算两次。setNeedsLayout 可被 UIKit 合并，不将请求次数等同于真实绘制次数。

## 正确性保护与其他边界

- 85%/15% 起手归属与菜单跟手保护已有回归，不能通过去掉刷新避让来提高表面响应。
- 原生静止菜单展开后不持续轮询；菜单运动检查主要扫描可见行，不是全部会话。普通隐藏场景已在 1.6-33 停止轮询。
- 指示器使用 Core Animation，没有发现自建逐帧重建分组的数据循环。
- 投影模式禁用原生预取是索引安全措施；可能影响预加载收益，但未测真实影响，不能贸然恢复。
- 菜单展开时点标签被拒绝，而有效横滑会先关闭菜单再切组；这是当前两个入口的行为差异，不是新的性能根因。
- 旧账号动作实际执行被阻止；本轮没有证据表明已发生会话删除误操作或用户数据丢失。也没有完整设备泄漏、内存峰值、功耗或线程时序测量。

## 建议处理顺序

1. 修复导航队列跨账号失效和重入唤醒，补足包含真实账号重置分支的回归；统一回顶部的手势准入。
2. 禁用/搜索状态停止无效分组计算；缓存快照，让切组选中状态与底层会话数据变化分离。
3. 轻量持久化选中组，区分角标与结构更新并合并通知。
4. 标签/字体/颜色/角标去重与高频滚动回调快路。
5. 用设备 Time Profiler / Animation Hitches / Allocations 验证收益，再决定是否需要增量重载或异步纯计算。
