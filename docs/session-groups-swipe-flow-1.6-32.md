# 分组滑动切换完整链路：1.6-32

基于 2026-10-16 当前工作区源码梳理。本文描述现有实现，区分已实现行为、保护条件及未统一的入口。生产代码和安装包未因本次梳理修改。

## 入口与职责

| 位置 | 职责 |
| --- | --- |
| `CSGroupListAdapter.m` / `ensureChrome` | 创建分组栏 pan 与会话列表 listPan，两者最多接受一根手指 |
| `listZoneForTouch`、`shouldReceiveTouch` | 按落点锁定接收归属 |
| `gestureRecognizerShouldBegin` | 判断初始滑动方向 |
| `shouldBeRequiredToFailByGestureRecognizer` | 左区切组与表格原生 pan/swipe 的本次识别优先级 |
| `groupPan` | 松手时判断距离/速度、目标分组及关闭菜单 |
| `selectIndex`、`refresh` | 保存稳定分组 ID，重建过滤列表、同步标题、请求回顶部 |
| `SessionGroupHooks.xm` / `MenuReceiveTouch` | 微信菜单手势接收同一分区限制 |
| `WESessionTabContainerView.m` | 标签选中、指示器动画、触感、选中标签可见性 |

`isActive` 表示当前是否正在使用过滤后的会话投影，不等同于“分组手势可用”。只要分组栏可见且相关开关开启、没有搜索，即使临时采用原生列表展示，仍保持左右分区。

## 1. 是否启用

`groupSwipesAvailable` 要求：table 存在、聊天分组 enabled 开启、swipe_gesture_enabled 开启、分组栏可见、没有搜索。菜单展开与 table.editing 不再作为全局禁用条件。

关闭分组切换手势时，分组横滑停止接收，菜单恢复原生范围；直接点击标签不受这个手势开关限制。指示器动画开关是另一个独立设置，不影响是否切组。

## 2. 按起手位置决定归属

位置取 `touch locationInView:table`，边界为 `table.bounds.minX + table.bounds.width * 0.85`，同时检查是否在 bounds 内。使用列表坐标，不使用已经被菜单横移的 Cell 坐标。

| 起手位置 | 列表切组识别器 | Cell 原生菜单识别器 |
| --- | --- | --- |
| 左侧 85%，不含边界 | 接收 | 拒绝 |
| 85% 分界线至最右侧 15% | 拒绝 | 交给原生接收回调继续判断 |
| 表格可视范围外 | 拒绝 | 对被分区限制的菜单识别器拒绝 |

菜单未展开、已展开、标准编辑标志是否为 YES，都不改变表格左右分区。手指中途跨区不重新分配：左边起手始终不能转成菜单，右边起手始终不能转成切组。

原生限制只作用于目标 Cell 的 `_panGestureRecognizer`。如果宿主已有 `gestureRecognizer:shouldReceiveTouch:` 实现，右区仍保留宿主拒绝权；无该可选实现时补充 UIKit 默认接受行为。其他表格、搜索、关闭手势、非菜单识别器保留原生行为。

## 3. 顶部分组栏是另一入口

分组栏 `pan` 不采用列表 85%/15% 分区。标签没有溢出时，分组栏横滑可以切组；标签过多、内部 scrollView 内容宽于视口时，在标签滚动区域的横滑优先滚动标签，外侧可接收区域才用于切组。搜索按钮等位于标签滚动区域外的 UIControl 不交给栏横滑。

列表 `listPan` 拒收分组栏、原生表头及其子视图，避免与分组栏入口重复处理。列表行内按钮可参与左区横滑；识别为切组后才取消原来的触摸，普通点击继续由原控件处理。

## 4. 判定方向与处理手势竞争

开始条件为 `abs(vx) > abs(vy) * 1.5`，是严格大于。横向速度恰好等于纵向的 1.5 倍时不开始切组。纵向或方向不明确时，分组 pan 失败，表格可以继续滚动；左区菜单已在接收入口拒绝，因此不会接管这个失败手势。

对于已接收的左区触摸，列表切组通过 `shouldBeRequiredToFailByGestureRecognizer` 请求：当前列表内的原生 pan/swipe 等待分组做出开始/失败决定。条件不覆盖其他页面、原生 header 或分组栏 pan，不建立永久失败依赖。

`listPan.cancelsTouchesInView=YES`，用于阻止横滑被识别后又打开会话或点击行内按钮；分组栏 pan 的该属性为 NO。

## 5. 松手时才决定是否切组

Began/Changed 阶段不切组、不推动列表或指示器跟手移动。只有 Ended 执行以下判断；Cancelled/Failed 不切组。

- 开关与页面状态仍允许，且触摸曾被当前识别器接收。
- `abs(translation.x) >= 44pt`，或 `abs(velocity.x) >= 350pt/s`，至少满足一个。
- 方向优先取整次滑动的净水平位移：负数下一组，正数上一组。只有净位移为零时取结束速度方向。
- 一次只移动一个分组。越过首尾无动作，不循环，也不因距离很长跨过多组。

因此“先向右挪一点，最后快速向左甩”，若最终净位移仍为正，会判定上一组。初始方向判断和结束阈值是两个阶段，结束时不再次套用 1.5 倍纵横速度比。

## 6. 菜单展开时切组的顺序

存在有效目标组后调用 `closeMenusForGroupSwitch`：

1. 开启原生变更事务，暂缓中途发布。
2. 对当前可见的原生菜单 Cell 调用 `setMenuOptionsViewHidden:YES animated:NO completionHandler:nil`。
3. 关闭 table.editing，并清理 swipeActive/行身份等状态。
4. 结束事务，合并待更新请求。
5. 再次确认原生菜单与编辑状态已解除。
6. 移动选中指示器，调用 `selectIndex` 切换数据。

如果没有目标组、阈值未达到、手势取消，不会由这条切组路径主动关闭菜单。如果原生菜单在关闭调用后仍报告活动状态，返回 NO，当前动作不切组；没有额外保存目标并重试的队列。微信自身触摸逻辑仍可能自行关闭菜单。

## 7. 分组 ID、数据、标题和位置

`selectIndex` 检查索引及账号；取得当前 displayedTabs 中的稳定 tabId，清除旧原生导航任务，保存账号内的 selectedTabID。普通选择将 nativePresentation 关闭；只有选择临时加入且不属于偏好配置的原生“全部”项才进入原生展示。

随后设置 pendingScrollToTop，删除目标组旧滚动锚点并请求 refresh。refresh 取得原生会话快照、生成目标组投影，重建用户名到显示路径映射，更新分组栏和角标，再 reloadData/layout，更新标题并完成回顶部。

快照暂时不完整时，保留选中的组 ID、展示该组安全空投影，并安排一次受代次和账号保护的 50ms 重试，不因快照失败自动选第一组。

回顶部使用 `y = -table.adjustedContentInset.top`，保持 x 不变；不修改 inset，不恢复目标组上一次停留位置。刷新、编辑、原生菜单或表格交互未结束时先保留 pendingScrollToTop。

指示器先更新、数据后发布：两者通常在同一调用链完成，但遇到延后刷新时不是原子更新，可能短暂出现标签已变、列表仍待发布的阶段。

## 8. 刷新如何避让

| 状态 | 刷新行为 |
| --- | --- |
| 表格 tracking 或分组 pan Began/Changed | 标记 dirty，合并成一个 50ms 延后任务 |
| 原生菜单 pan Began/Changed 或收起动画中 | 标记 dirty，同样合并延后 |
| 菜单静止展开 | 保留 dirty，停止持续轮询，等待菜单回调唤醒 |
| 原生变更事务、表格 dragging/decelerating/editing、swipeActive | 暂缓发布，等待对应结束路径 |
| 交互结束、状态允许 | 发布更新；请求已经被消费时不重复 reload |

原生菜单状态独立读取，不能只依赖 UITableView.editing。handlePan 与菜单隐藏方法的 Hooks 唤醒待更新请求；关闭标准 editing 也会解除相应状态。删除行和账号切换分别复核身份，防止失效菜单永久占住刷新。

50ms 是待刷新任务的合并/检查间隔，不是菜单手势延迟，也不是每 50ms 刷新一次列表。

## 9. 动画与触感

动画仅在选中目标发生变化后触发。指示器约 0.26 秒平滑移动，宽度在 45% 时间处达到轻微伸展，再收回；伸展量为移动距离的 12%，最多 14pt，无弹簧反弹。快速连续切换从 presentation layer 当前可见位置续接。

动画需要独立开关开启、视图在 window 中且系统未启用减弱动态效果；否则直接落位。同一分组的刷新确认不会中断已在进行的动画。触感按单独的触感配置执行。

## 10. 本轮核查确认的差异与缺口

### 点击标签与横滑的菜单处理不一致

横滑先关闭菜单再调用 selectIndex；直接点标签则先更新标签选中视觉，再直接调用 selectIndex。后者仍在菜单/编辑状态存在时拒绝选择，并恢复 publishedTabID。因此当前会出现“菜单展开时能横滑切组，但点标签可能退回原组选中”的差异。先更新标签还可能产生一次短暂指示器变化或触感。这是源码确定的入口差异，不是实机新反馈。

### 回顶部缺少分组 pan 的独立保护

refresh 会检查 groupPanMoving，applyPendingScrollToTop 只检查表格交互和原生菜单等状态，没有检查 groupPanMoving。对同一生产方法的主机替身实验：groupPanMoving=YES、表格 tracking/dragging/editing 等为 NO，执行 returnToGroupTop 后仍写入一次 contentOffset，将 y 从 -20 改为 -100，pending 被清除。

这说明“刷新正在避让”不能推导为“所有位置更新都避让”。建议回顶部入口复用独立手势保护，同时明确结束后的唤醒路径。该实验验证逻辑缺口，不证明手机已经出现同样时序。

### 需要明确保留的边界行为

- 本功能是松手触发切组，不是跟手分页；不能把没有 Changed 阶段横移动画误认为手势未接收。
- 首尾越界/未达阈值时，切组本身不收起旧菜单。
- 快速反向甩动按净位移优先，可能与松手方向不同。
- 原生菜单没能同步关闭时，本次切组放弃，没有延迟重试。
- 私有类、ivar 及 delegate 回调仍依赖宿主版本；主机替身不能覆盖 UIKit 实际仲裁、不同插件的 hook 顺序。
