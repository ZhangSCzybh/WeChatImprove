# 微信自定义侧滑菜单刷新保护 1.6-31

2026-10-16，基于当前 1.6-30 工作区，保留此前的触摸起手保护、置顶笔记修复与左侧 85% / 右侧 15% 手势分区。

## 现象与证据

用户视频中的菜单短暂露出后回收，继续左滑才完整展开。此前保护主要依赖 `UITableView.tracking/dragging/editing` 和标准编辑回调；这不能覆盖微信自定义菜单的全部生命周期。

本地微信 8.0.78.34 可执行文件的 Objective-C 元数据及有界反汇编显示：

- 会话 Cell 的继承链包含 `MMBaseMultiMenuTableViewCell`；其 `handlePan:` 使用自己的 `_panGestureRecognizer`，通过原生内容容器的位置实现侧滑。
- 该文件中的 `checkTableViewEditingStyle` 只有一条 `ret`。自定义菜单并不保证通过表格编辑状态通知插件。
- `isMenuHidden` 与 `_inHideAnimation` 表示不同阶段：收起开始时隐藏标志可能先变化，动画尚未完成。只读取隐藏标志会过早放行刷新。
- 原生收起完成回调受动画代次控制，旧动画的回调可以被跳过，因此不能通过包装回调累加计数来判定生命周期结束。

结合源码可确认一个可触发冲突的缺口：独立菜单正在跟手时，分组适配器可能认为列表空闲，执行 reload、回顶部或切换展示。reload 会重建正在被拖动的 Cell，表现为菜单回收或被拉回。主机回归复现了该状态下的错误放行。视频没有内部调用轨迹，不能据此断言每次卡顿均由这一路径导致。

静态证据与样本 SHA-256 见 [manifest](evidence/session-groups-menu-1.6-31/manifest.json)。REA 用于打开本地目标，方法定位使用 Mach-O 元数据读取及 Xcode `llvm-objdump -d` 的指定地址范围；没有运行完整反编译或设备跟踪。本地包不保证与手机当前可执行文件逐字节一致。反汇编中的最近导出符号标签不是 Objective-C 方法名，应以元数据解析出的地址为准。

## 修复行为

`CSGroupListAdapter` 只检查当前分组列表可见的原生菜单 Cell，并区分阻止刷新与仍在运动两类状态：

1. 独立手势处于 Began/Changed，或原生收起动画未结束：延后刷新、回顶部、分组切换和原生展示切换。已有待更新任务每 50ms 合并唤醒一次，直到运动结束。
2. 菜单静止展开：保留待更新状态，不持续轮询。
3. 菜单关闭、取消：通过原生 `handlePan:` 与 `setMenuOptionsViewHidden:animated:completionHandler:` 的观察入口唤醒待更新任务；真正结束后发布一次。
4. 没有待更新任务时，正常开关菜单不会额外 reload。

原生调用的参数、完成回调对象、执行时机和异常传播均保留。原生手势的 delegate、速度、位移与阈值不变。切组是否允许在手势接收/开始/完成及标签选择时检查；不因自定义菜单收起动画而切换识别器的 enabled，以免缺失标准编辑结束回调时无法恢复。

已删除会话在原生事务结束后按用户名复核，不允许失效菜单永久阻塞刷新；事务进行中不提前认定删除。旧账号交付的 Cell 不阻塞新账号。其他表格、分组未激活时不产生菜单刷新保护。本次未增加诊断日志。
