# 聊天页性能隔离修复 1.6-33

2026-10-17。用户反馈进入聊天内容页后滚动严重卡顿，键盘输入也不流畅；参考录屏 `ScreenRecording_10-17-2026 06-49-41_1.MP4`（约 15.46 秒）。抽帧核对了进入聊天、上下滚动和键盘输入场景。录屏不包含主线程调用栈，不能据此量化具体方法耗时或断言全部卡顿只有一个原因。

## 代码确认的问题

分组适配器的 `projecting` / `chromeVisible` 分别表示投影模式、分组栏启用状态，不能代表主列表当前位于前台。原实现没有离开页面后的暂停状态：

```text
MainFrameLogicController.onSessionChanged / unread / reload 等
    → Native(change=YES)
    → beginNativeChange：保存列表锚点
    → 原生方法：正常处理会话数据
    → endNativeChange → requestRefresh
    → 主线程 refresh
    → 全会话原生快照 + 分组投影/角标 + 列表 reloadData/layoutIfNeeded
```

从聊天页触发相关原生通知时，上述分组派生工作依然针对被覆盖的主列表执行。刷新扫描的是全部会话，当前分组只有两条会话并不会将扫描量限制为两条。键盘和聊天滚动与这些操作使用同一个主线程，因此这是会干扰聊天页响应的明确代码缺陷；每个按键是否实际产生该原生通知，仍需要设备调用栈确定。

Git 历史显示，`931705ea`（1.6-0 分组重构）已经包含无离屏判断的全量刷新链。1.6-29～1.6-32 增加了触摸、原生菜单及分组手势期间的 50ms 延后刷新机制，但同样没有页面可见性边界。离开时若还残留移动状态，任务也可能继续唤醒。不能将该缺陷描述为仅由最近的 85%/15% 分区改动引入。

另一个全局入口是 `UITableView.reloadData` Hook：原代码即使没有分组适配器，也进入分组索引作用域，操作线程字典和临时集合。其成本低于全量刷新，但聊天页没有必要承担它。

## 修复行为

- 在原生主列表拥有者的 `viewWillDisappear:` 之前暂停分组派生工作；`viewDidDisappear:` 保持暂停。`viewWillAppear:` / `viewDidAppear:` 恢复，仍执行原来的原生方法与返回顶部逻辑。头文件确认拥有者是提供这些生命周期回调的 `NSObject`，无需假定它继承 UIViewController，也不使用被覆盖后仍可能存在的 `table.window` 作为前台依据。
- 暂停期间，消息、会话、未读等原生逻辑照常运行；只保留分组 `dirty` 状态，不重建会话快照、不更新分组布局或标题、不捕获/恢复滚动锚点。设置变化也合并至返回时处理。
- 已进入主队列或 50ms 延迟队列的刷新会重新检查暂停状态；最多让既有任务空跑退出，不继续自调度。快照失败重试令牌在离开时失效。
- 所有者保留暂停状态。隐藏期间更换表格时，新适配器仍暂停；返回时才初始化。旧适配器 detach 后停止派生刷新。
- 原生批量更新仍执行其模型操作。隐藏期间 UI 动画无法完成，最外层事务结束后以 `finished=NO` 回调一次，避免无限保留回调。异常路径使用同一个复制后的 block 对象删除待执行回调，修复异常场景重复回调。
- 显式的 `selectCellForName:` / 下一会话等原生导航是受控例外：允许一次原生坐标模式发布以执行导航，不被隐藏状态永久挂起；继续检查账号身份，完成后保持暂停。
- 没有关联分组适配器的表格 `reloadData` 直接调用原实现。

保留索引映射与会话身份校验；不将微信私有模型或 UIKit 操作移到后台线程，不关闭原生消息处理。保留菜单跟手保护、固定 85%/15% 分区、删除校验、置顶笔记验证、分组选择和指示器行为。未添加常驻调试日志。
