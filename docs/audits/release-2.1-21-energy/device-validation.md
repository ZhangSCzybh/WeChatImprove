# 2.1-21 安装后前台 CPU 复测

2026-10-30，在用户原有 iPhone、微信账号及功能组合下，安装后的 **2.1-21 已明显降低微信聊天列表的前台 CPU**。第一轮静置平均为 **4.67%**；第二轮包含分组切换和进入聊天，全窗平均为 **11.47%**。本次观察没有再复现旧版持续占满约一个核心的列表刷新负载。

## 加载版本与场景

设备为 iPhone 14 Pro Max、iOS 27.0.1、微信 8.0.78。目标是原微信 `com.tencent.xin`；两轮 CPU 采样及随后线程快照均核对为同一目标进程，前台检查均为 `foregroundRunning=true`。

线程快照中的插件镜像 UUID 为 `32eee29d-4de4-39af-bd02-d291fd350601`，与交付的 **2.1-21 Rootless arm64e** 包及 dSYM 一致，见[包校验记录](package-verification.json)。微信镜像 UUID 为 `9cd58b8e-b7ab-3487-adbd-2ac0aa16a5de`。该证据确认复测实际加载了新版本。

用户确认聊天分组开启、密友锁定隐藏、列表圆角和底栏等原样式开启，其余功能维持原设置。R1 为亮屏前台聊天列表静置；**按用户最新补充，R2 全程亮屏前台，包含切换分组和进入一次聊天**，不能将 R2 写成纯静置场景。操作没有逐秒对时，因此不能把某个峰值精确归到其中一个动作。

## CPU 结果与方法

约每秒读取一次进程累计 CPU 计数。每轮仅排除采集通道的首条初始化样本，其余有效区间全部保留，没有剔除交互高负载或选择性排除启动暖机。CPU 计算为 `100 × Δ(cpuTotalUser + cpuTotalSystem) / ΔprocAge`；**100% 表示一个 CPU 核心**，并非整机利用率。全窗均值按累计 CPU 时间除以累计设备时间计算；中位数、P90 和峰值来自约一秒的有效区间，P90 使用最近秩。

| 版本／场景 | 有效跨度 | 全窗平均 CPU | 区间中位数 | P90 | 约一秒区间峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2.1-19，原功能组合，旧前台基线 | 33.82 秒 | 86.18% | 106.39% | 107.02% | 112.40% |
| 2.1-21 R1，聊天列表静置 | 57.98 秒 | **4.67%** | **2.07%** | 10.05% | 35.73% |
| 2.1-21 R2，包含切换分组／进入聊天 | 58.77 秒 | **11.47%** | **2.19%** | 43.57% | **46.65%** |

R1 相对旧原配置全窗均值下降 **94.58%**；R2 将全部交互区间计入后下降 **86.69%**。旧基线本身包含低负载片段，未只挑选旧版高负载尾段，也没有使用关闭分组、解锁密友后的低负载作为当前原配置的基线。

两轮共 111 个有效区间，均低于 50% CPU。R2 最忙的约 10 秒平均为 **35.60%**，最高区间为 **46.65%**；最后两个约 10 秒段分别回落至 **1.86%** 和 **2.02%**。两轮合计 116.743 秒，按时长加权平均为 8.09%；该值混合静置和交互场景，不能作为纯静置值。

辅助的进程逻辑写入速率由旧基线约 0.614 MiB/s 降为 R1 约 0.103 MiB/s、R2 约 0.147 MiB/s；该计数不等于文件净增长或物理闪存写入，不能换算成耗电量。

## 主线程与系统负载

两轮 CPU 采样结束后约 13:00:00–13:00:12（北京时间），四份同进程主线程快照构成独立交叉验证。以设备 `mach_absolute_time` 和 `mach_timebase_info` 换算间隔，对 `cpu_times.user_usec + system_usec` 做差，12.017 秒内主线程累计 CPU 为 0.152415 秒，平均 **1.27%**。四个采样点均处于系统事件循环等待链路：`mach_msg2_trap → mach_msg → __CFRunLoopServiceMachPort → __CFRunLoopRun`。

系统符号按目标 task 的 shared-cache 基址、cache UUID、镜像范围、镜像 UUID 及精确偏移匹配，没有用最近符号猜测。相比旧版主线程约 99% 的累计 CPU 和反复出现的 `scheduleRefresh → refresh → publishProjection → reloadData / layoutIfNeeded`，本次结果支持持续刷新循环在所测场景中已明显缓解。四份稀疏快照不能统计全部刷新次数；插件有界内存诊断计数未在本轮读取，不能声称重载次数为零，也不能用这个后续窗口归因 R2 峰值。

| 系统进程 | R1 平均 CPU | R2 平均 CPU |
| --- | ---: | ---: |
| `assetsd`，系统媒体资源服务 | 98.60% | 95.93% |
| `fileindexerd`，系统文件索引服务 | 32.75% | 32.37% |

这两个系统进程在两轮中持续高于微信，可能是整机仍有负载的来源。采样没有证明具体照片、同步或索引任务，也没有证明由微信或插件触发。开发采样相关的 `sysmond`、`DTServiceHub` 还会增加额外开销，不能把整机 CPU 变化全部算作插件收益。

## 测量边界与原始记录

旧、新版本来自不同时间窗口，进程运行时长、消息与系统工作负载没有完全一致地重放，以上降幅只描述这些实际窗口。收发消息、快速滚动和长期使用仍需各自验证。手机连接数据线，本次没有自然放电、电功率或温度测量，**不能给出续航提升百分比、节省瓦数或降温度数**。

**本轮未重测后台。** 旧版此前约 89 秒锁屏采样未复现持续后台高 CPU，不能据此认为已解决或排除用户长期后台掉电问题。
