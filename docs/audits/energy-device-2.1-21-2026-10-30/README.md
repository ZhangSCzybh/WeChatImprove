# 2.1-21 安装后的 iPhone 前台 CPU 复测

2026-10-30，在用户原有 iPhone、微信账号和功能组合下，2.1-21 已明显降低聊天列表的前台 CPU。本轮没有再复现 2.1-19 中持续约占满一个核心的主线程刷新／重载现象。第一轮静置的微信平均 CPU 为 **4.67%**；第二轮包含用户切换分组、进入聊天的操作，全窗平均 **11.47%**，最高约一秒区间 **46.65%**，随后回到约 **2%**。

## 实际设备与加载版本

- 用户设备信息：iPhone 14 Pro Max、iOS 27.0.1、微信 8.0.78。
- 目标为用户原微信 `com.tencent.xin`，PID `67466`，task unique PID `167280`，进程于北京时间 12:50:23 启动。设备上另有微信副本，本轮没有将其作为目标。
- 已加载插件镜像 UUID 为 `32eee29d-4de4-39af-bd02-d291fd350601`，与交付的 **2.1-21 Rootless arm64e** 及 dSYM UUID 一致。微信镜像 UUID 为 `9cd58b8e-b7ab-3487-adbd-2ac0aa16a5de`。
- 通过用户已连接的数据线建立性能采样连接；工具使用隔离的 `uv` 依赖环境中的 `pymobiledevice3==11.48.0`。
- 功能状态由用户确认：聊天分组开启、密友锁定隐藏、列表圆角及底栏等原样式开启，其他功能维持原设置。本轮没有请求关闭功能来取得低负载，也没有启动、重启或停止手机上的微信。

身份原始记录见 [process-identity.json](process-identity.json)，加载镜像见 [preflight-stack.json](preflight-stack.json) 和四份 `foreground-stack-*.json`；包 UUID 来源见 [2.1-21 包校验](../release-2.1-21-energy/package-verification.json)。

## 场景与统计口径

两轮各请求 60 秒、约每秒采集一次进程累计 CPU 计数。首条记录作为通道初始化样本排除，按随后记录间的累计 CPU 差计算；排除首条不代表剔除应用启动暖机。第一轮首个保留样本时微信已经运行约 364 秒，第二轮约 465 秒。

CPU 百分比为 `100 × Δ(cpuTotalUser + cpuTotalSystem) / ΔprocAge`，计数统一为纳秒。**100% 表示一个 CPU 核心，允许超过 100%，不是整部手机的利用率。** 全窗平均按累计 CPU 时间除以累计设备时间计算；中位数、P90 和峰值来自约一秒的有效区间，P90 使用最近秩。

每轮开始、过程中及结束共五次独立检查，均为同一 `com.tencent.xin` 进程，`foregroundRunning=true`。用户确认持续亮屏在前台，并随后补充：中间十几秒负载升高时，应该进行了切换分组和进入一次聊天。因此第一轮按静置聊天列表记录，第二轮按包含上述交互的前台复核记录。交互没有与计数逐秒对时，不能精确归因峰值至其中某一个动作；第二轮所有区间均完整保留。

## 微信 CPU 前后对比

| 场景 | 有效跨度 | 全窗平均 CPU | 区间中位数 | P90 | 约一秒区间峰值 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 2.1-19 原功能组合，旧前台基线 | 33.82 秒 | 86.18% | 106.39% | 107.02% | 112.40% |
| 2.1-21 第一轮，聊天列表静置 | 57.98 秒 | **4.67%** | **2.07%** | 10.05% | 35.73% |
| 2.1-21 第二轮，包含切换分组／进入聊天 | 58.77 秒 | **11.47%** | **2.19%** | 43.57% | 46.65% |

第一轮相对旧原配置全窗均值下降 **94.58%**，是本轮最接近静置场景的对比。第二轮将交互负载全部计入，均值仍比旧原配置低 **86.69%**。两轮合计 116.743 秒消耗 9.450 CPU 秒，按时长加权为 **8.09%**，较旧全窗均值低 **90.61%**；此合并值包含静置和交互两种场景，不能当作纯静置值。

旧原配置均值中包含低负载片段，故同时列出全窗均值与中位数，没有只挑选旧版的高负载尾段。旧版其他分组或密友投影启用场景均值约 104–109%，而关闭分组且解锁密友后的 5.75% 属于关闭功能的机制对照，不能当作当前原配置的旧基线。

两轮共 111 个有效区间，均低于 50% CPU。第二轮最忙的约 10 秒平均 **35.60%**，最高区间 **46.65%**；该轮最后两个约 10 秒段分别为 **1.86%** 和 **2.02%**。这次短时上升没有延续成旧版的持续高负载；操作时间未精确对齐，不能仅凭这组计数断言每次交互都具有相同峰值。

进程写入计数作为辅助观测：旧原配置约 0.614 MiB/s，新第一轮约 0.103 MiB/s，第二轮约 0.147 MiB/s。这是进程逻辑写入计数，不能换算成实际闪存物理写入量或耗电量。

## 主线程交叉验证

CPU 采样结束后，在北京时间约 13:00:00–13:00:12，继续获得四份被动线程快照。它们均为同一 PID、同一主线程 `13684450`，且微信检查为前台运行。

使用快照中设备 `mach_absolute_time` 与 `mach_timebase_info={numer:125, denom:3}` 换算间隔，对 `cpu_times.user_usec + system_usec` 做差：

| 相邻快照 | 设备间隔 | 主线程 CPU 时间增量 | 主线程平均 CPU |
| --- | ---: | ---: | ---: |
| 1 → 2 | 3.989 秒 | 0.016303 秒 | 0.41% |
| 2 → 3 | 4.011 秒 | 0.025536 秒 | 0.64% |
| 3 → 4 | 4.017 秒 | 0.110576 秒 | 2.75% |
| 合计 | **12.017 秒** | **0.152415 秒** | **1.27%** |

四份主线程快照均为等待状态，帧位于 `mach_msg2_trap → mach_msg → __CFRunLoopServiceMachPort → __CFRunLoopRun` 的系统事件循环等待链路。系统符号使用目标 task 自己的 shared cache 基址，严格匹配 cache UUID、镜像范围、镜像 UUID 与精确偏移；没有用最近符号猜测函数。

旧版八份快照约 140 秒内主线程 CPU 差为单核 98.65–99.16%，六份瞬时栈命中插件 `scheduleRefresh → refresh → publishProjection → reloadData / layoutIfNeeded`。这与本轮主线程低占用和等待状态形成独立于进程计数的交叉验证，支持针对持续刷新循环的优化已在本次场景生效。

四份稀疏快照不能统计全部刷新次数，也不能证明插件从未执行过重载。本轮没有读取插件有界内存诊断中的事件计数，不能声称诊断计数为零。主线程快照属于 CPU 两轮结束后的独立短窗口，不能用它直接归因第二轮交互峰值。

详细累计时间、原始帧、UUID、来源哈希见 [main-thread-summary.json](main-thread-summary.json)。

## 仍在消耗 CPU 的系统进程

| 进程 | 第一轮平均 CPU | 第二轮平均 CPU | 已确认的职责范围 |
| --- | ---: | ---: | --- |
| `assetsd` | **98.60%** | **95.93%** | 系统媒体资源服务 |
| `fileindexerd` | **32.75%** | **32.37%** | 系统文件索引服务 |
| `backboardd` | 17.05% | 24.50% | 系统显示与输入相关服务 |

第二轮另有 `ScriptableWidgetExtension`，在其自身 47.40 秒可观察窗口内平均 CPU 为 24.00%；它的观察窗口与整轮长度不同，详细计数保存在最终对比 JSON 中。

通过设备进程路径确认 `assetsd` 来自 `/System/Library/Frameworks/AssetsLibrary.framework/Support/assetsd`，`fileindexerd` 来自 `/System/Library/PrivateFrameworks/FileIndexerDaemon.framework/Support/fileindexerd`，详见 [system-process-paths.json](system-process-paths.json)。

在当前两轮中，这两个系统进程持续负载明显高于微信，因而微信 CPU 降低后整机仍可能有较多发热来源。现有采样没有证明它们正在执行哪项照片、云同步或索引任务，也没有证明由微信或插件引起，不能据此要求删除媒体或关闭系统功能。

`sysmond`、`DTServiceHub` 包含开发性能采样的额外开销。旧、新采样时系统其他活动也不同，因此没有把整机总 CPU 的变化当作插件节省值。

## 结论与边界

这次安装后的实际复测支持：**原功能组合下，微信前台静置 CPU 明显下降，旧版持续占满一个核心的列表刷新负载本轮未再复现；分组切换／进入聊天产生的短时负载随后能够回落。**

测量发生于不同时间窗口，旧版进程运行更久，消息及系统工作负载没有做完全一致的重放；上述降幅描述实际采样窗口，不是所有使用场景的固定收益。收发消息、快速滚动、长时间使用及后台需要各自的场景验证。

手机连接数据线且没有自然放电、电功率或温度测量。本次不能给出续航提升百分比、节省瓦数或降温度数；本轮也没有重测后台。旧版此前约 89 秒锁屏采样没有复现持续后台高 CPU，这不等于已经解决或排除了用户长期后台掉电问题。

本轮采样程序均已结束，其 DVT／隧道会话随上下文退出关闭；手机上的微信保持运行。交付版本和安装包沿用已经安装的 2.1-21，本次没有再次修改生产源码或打包。
