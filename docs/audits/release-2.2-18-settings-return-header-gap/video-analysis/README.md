# 录屏只读取证

本目录独立解码、测量用户提供的旧版本录屏，不含新代码真机验证。输入视频与五张原关键帧未修改。原文件 SHA256 为 `0114183b48080011124a10ea595a3e84083fb08dae96f34a47b75e6de1a43116`。

**本地源可以确认“微信号不动、下方分组短暂上移、随后恢复”，但无法复现题面所列的 480→498→480、115 帧或四帧缓动数据。** 两套测量必须分开保留，不可用题面数值去反推生产 padding。附件五张关键帧与本地同序号解码 RGB 全部逐字节一致。

## 用户提供的测量，按原文留档

用户口径：f001 是从 1 开始的解码帧序号，不是时间码；视频 HEVC、592×1280、30fps、3.83s、115 帧；灰度行均值，x=120–470，“首个白卡顶边”。

| f022–f035 | 0.70–1.17s | — | push 进入“顶栏头像设置” |

## 独立解码与算法

`analyze.py` 用 ffprobe 读取 presentation timestamps，用 ffmpeg `-fps_mode passthrough -pix_fmt rgb24` 输出视频帧，不补齐、不复制 CFR 帧。f001 是第一个真实解码输出，f011 是第十一个；每帧的实际 PTS 单独存入 `all-frames.csv`。本地 ffprobe、实际解码均为 **114 帧**；nominal rate 30/1、average rate 684/23，duration 3.833333s。后段 PTS 有一次 3.166667→3.233333 的空档；因此不能用恒定 30fps 补帧后的总数冒充解码帧数。该空档晚于本次关键返回区间。

测量完全在 592×1280 源像素上进行：

1. 灰度为 `0.299 R + 0.587 G + 0.114 B`。对 x=120..470（两端包含）求行均值，在 y=340..550 中找第一个随后连续八行均值均≥250 的 y，作为账号信息白卡的上边缘。只对视觉确认主设置页可见的 f001..f021、f047..f094 解释其含义；其他帧的 candidate 列保留原始候选但不称为主设置页白卡。
2. 微信号文字取 x=[180,415)、y=[310,345)、gray<200 的墨迹包围框；分组标题“账号与安全”取 x=[50,160)、y=[345,411)、gray<170 的包围框。转场水平位移会改变 x 包围框，不改变这里观察到的 y 位置。
3. 将列表 ROI x=[120,471)、y=[370,1150) 与 f011 作整块竖直配准，遍历 −40..40px，以 RGB mean absolute error 最小值记录最佳位移。该独立指标避免把白卡抗锯齿阈值的 1px 波动当作几何变化。
4. 另保留微信号 ROI 竖直模板配准。转场尚有水平位移时其误差较大，不能把拟合最优值强称为真实文字坐标；文字墨迹边界和稳定帧对照是主要依据。

|---|---:|---:|---|---|---:|
| f001–f021 | 0.000000–0.666667 | 413 | 386–402 | 318–336 | 0 |
| f047 | 1.533333 | 390 | 362–378 | 318–336 | −24 |
| f048–f054 | 1.566667–1.766667 | 389 | 362–378 | 318–336 | −24 |
| f055–f057 | 1.800000–1.866667 | 390 | 362–378 | 318–336 | −24 |
| f058–f094 | 1.900000–3.100000 | 413 | 386–402 | 318–336 | 0 |
| f095–f114 | 3.133333–3.800000 | 不解释 | 不解释 | 不解释 | 不解释；系统控制中心进入 |

“微信号文字底边→分组标题墨迹顶边”的坐标差从 **50px 变为 26px，再回到 50px**。完整列表 ROI 与分组标题均给出 **−24px→0** 的几何变化；阈值识别的圆角白卡顶边给出 −23/−24px，差别是抗锯齿和转场亮度的 1px 阈值误差。f055 相对 f011 的列表 ROI 在 −24px 配准时 MAE 约 0.828，f058 相对 f011 在 0px 配准时 MAE 约 0.357。

在本地源中，f057（1.866667s）仍是压缩态，f058（1.900000s）已恢复；**没有观察到 f058–f062 在多个中间 y 值逐步恢复**。视频帧间无法排除屏幕在 30fps 采样之间有更短动画，但不能据此声称已测得四帧缓动。题面 480/498 均落在本地白卡内容的 y 范围内，不是本算法识别到的白卡顶边；这里不推断原测量产生差异的原因。

若只沿用用户 592px≈393pt 的屏宽假定，24px 对应约 15.93pt。视频没有 UIKit bounds/scale 数据，**该换算不是实际点值证据，也不用于选择修复高度**。

## Push 方向与路径范围

录屏只覆盖一个实际子页：“顶栏头像设置”。在该子页首次进入时，x=120..470 的首白卡候选自 f025..f043 保持 **208px，f034 单帧为207px**（同类阈值误差），静止 f036..f042 均为208px；未看到该子页有返回主列表那样约24px的竖直阶跃。f022..f024 目标采样带仍被水平转场遮挡，不能量测；也不能排除被遮挡的主列表在 push 时已有不可见的几何变化。该证据只支持“本次录屏未见子页可见区域的对称阶跃”，不能扩为所有 push 路径无问题。

其他界面定制子页以及普通/快捷密友页没有设备录屏，**均未实测**。新代码的主机契约测试与设备转场证据必须分别报告。

## 能证明与不能证明的范围

可以证明：微信号文字在可见主列表帧的 y 边界不动，而其下分组标题和整个列表内容短暂上移约24px，然后恢复。这与整个屏幕/整个 header 同步滚动的简单解释不符。

不能单凭视频证明：`tableHeaderView.frame` 的高度、具体约束、section header/footer 估算、safe-area、contentOffset、nav bar 状态、调用顺序或系统私有实现。子视图文字不动不等于其容器高度必然不动；滚动与其他布局变化也可能抵消。实际根因必须靠生产源码、契约复现及设备进一步验证，不能将“系统一定估算”当成视频测量结果。

## 复查文件

- `provenance.json`：原视频 SHA256、真实工具版本和完整命令、解码序列 RGB SHA256、五张原关键帧逐像素一致性、输出 SHA256。
- `all-frames.csv`：全部114个真实解码帧，实际 PTS、相位分类、白卡候选、文字包围框、两种配准结果及每帧 RGB SHA256。
- `gray-row-profiles.csv`：全部114帧在 y=260..560、x=120..470 的灰度行均值。
- `ffprobe-stream.json` / `ffprobe-frames.json`：未加工的流元数据和实际逐帧时间戳。
- `comparison-annotated.png`：f011/f055/f070 的微信号、标题和白卡顶边标线。
- `geometry-trace.png`：真实源像素 y 随1-based解码帧的变化；被子页遮挡期间留空。
- `contact-sheet.png`：包括 push、pop、恢复及系统控制中心的24帧全画面联系表。
- `analyze.py` / `run.log`：可复跑脚本和测量输出。运行所需的 bundled Python 路径在 provenance 中，未安装或修改系统 Python 环境。

本分析不声称真机验证新版本；手势、UIKit 真实转场、修复后首帧、间距观感和 iOS Keychain 均未由本目录验证。
