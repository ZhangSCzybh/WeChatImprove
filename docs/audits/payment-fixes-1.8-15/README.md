# 1.8-15 收款与红包回归修复

本轮以用户实际使用的 1.8-14 工作区源码为起点。原分组动画、语音功能及其他性能优化保持原文件；只修改支付核心、两个 Hook、对应设置页、相关测试和版本信息。源文件备份见 `before-source.zip`，原文件校验值见 `baseline.json`，历史产物见 `prior-artifacts.json`。

## 问题与处理

| 用户反馈 | 本轮修复 | 验证与边界 |
| --- | --- | --- |
| 私聊转账不能自动收款 | 原始转账子类型必须明确；原生标量 0 作为未填充值处理，允许由 XML 的子类型 1 确认。仅一对一入站消息允许用 from/to 补齐缺失的付款人、收款人。显式身份冲突继续拒绝。 | 新增用例在 1.8-14 解析器中失败，见 `regression-before.log`。群聊没有明确收款人仍拒绝。 |
| 群聊已到账却没有回复、没有累计；红包不能继续打开 | 请求关联从动态 protobuf 的 `setReqText:` 移到具体网络提交入口，在请求字段、命令号都填好时记录原请求。成功响应允许缺省 baseResponse、缺省/0 回包命令号；所有显式错误仍拒绝。正文 retcode 缺省遵从原生读取语义，但仍必须有完整业务成功信息。 | 旧测试的 setter 人工回调、固定完整响应字段不等同于真机。本轮替身取消 setter 回调，执行生产网络 Hook；使用百分号编码 form、缺省 protobuf 字段。动态 Hook 在用户设备上的实际失败点仍是推断，没有设备调用轨迹。 |
| 收款成功仍漏判 | 非空 `real_name_info` 不再直接判失败，改查 `guide_flag`；有待执行引导、拦截信息、金额非法或身份不符仍不计数。转账确认命令按微信 8.0.78 的 85 校验。 | 核心测试覆盖 guide_flag 0/1、错误收款人、错误付款人、平台/BaseResponse/命令错误。 |
| 红包自动回复没有开关 | 新增“红包自动回复”，键 `com.wechat.enhance.redenvelop.autoReplyEnable`。旧用户有回复文本时默认延续原行为，显式关闭后保持关闭。 | 开关只影响回复，领取、计数、金额及独立通知设置照常。 |
| 红包领取后记录不更新 | 从原生支付对象或合法 XML 提取 nativeUrl；支持已有实现使用过的领取金额字段，并要求多个金额别名不冲突。领取成功才写入账本。 | 只使用本次领取金额，绝不把红包总金额当领取金额。正文状态必须支持打开、携带有效 timingIdentifier 后才自动打开。 |
| 手动收款没有回复／记录 | 保存有上限的、已验证归属本人的消息元数据，在本机真正发出 confirm/open 请求时关联其回包。不会自动操作手动查询，不依赖广播确认回调。 | 本次运行已识别且在缓存有效期内的交易支持手动领取观察；不扫描历史聊天、不跨重启补建来源。自动和手动争抢同一笔成功时以业务键持久去重，只统计/回复一次。 |
| 记录页显示旧值 | 账本写入并同步旧设置键后发统计更新通知，已显示的记录页刷新；页面重新出现时也重新读取。 | 没有新增刷新计时器。 |
| 他人的专属红包／转账不得领取或回复 | 群转账仍要求明确 receiver 为本人；红包检查支付对象、XML、URL 的专属收款人，以及查询／打开回包中的明确收款人。发现他人收款人即拒绝，并撤销手动观察来源。 | 覆盖他人群转账、确认收款消息、他人专属红包和查询回包归属不符；身份缺失不以广播成功补算。 |

## 原生证据

复用 `../payment-optimization-1.8-14/native/` 的微信 8.0.78.34 arm64 只读证据，本轮补充 `native/` 中网络提交方法的元数据和反汇编。原二进制 SHA-256 为 `0b3cd1e2ed1da493a6fe12c9ef6e9b9421c95bcac63417c677f309536f7c1c8e`。

- `WCPayNetworkHelper WCToTenpayCommonRequest:RetryCount:routeInfo:`：`0x10977140c`，ABI `v32@0:8@16I24C28`。
- `WCRedEnvelopesNetworkHelper WCToHongbaoCommonRequest:`：`0x109ca605c`，ABI `v24@0:8@16`。
- 原生 `ConfirmTransferMoney:` 在 `0x109711d24` 传确认命令 85。
- 原生红包构建器先编码值、构造 form、设置 reqText，随后设置 cgiCmd，再调用网络 helper；观察边界位于完整请求提交前。
- 原生公共响应处理检查平台及支付错误，读取正文 retcode 的 intValue；并不要求 baseResponse 一定存在。转账解析器继续读取 fee、fee_type、payer、receiver 和 real_name_info.guide_flag。

这些是静态程序证据，不代表在用户手机上观察到了对应字段取值。未发起真实支付、未发送微信消息、未安装到设备。

## 回归范围

只运行 `bash Tests/verify-payment-core.sh`，编译执行生产解析器、任务表、账本、自动化桥以及从生产 Hook 提取的网络提交/回调方法；未扩展到其他模块测试。

核心模块共 2,213 项断言（含原有有界队列压力断言），网络桥和 Hook 共 95 项断言。新覆盖包括：私聊缺省身份字段、缺省协议字段、表单编码与二次转义、正常实名信息、显式错误、原请求串单校验、手动领取、回复开关、金额字段冲突、XML URL、他人专属红包以及手动/自动同时发生的去重。具体结果见 `core-tests.log`。

构建使用原工作区以及独立 Theos 缓存/暂存包目录，不执行 make clean。第一次构建发现 Logos 提前生成声明时不能解析参数中的私有类名，已将 Hook 参数改为 ABI 等价的 id；最终构建日志见 `build-final.log`。最终包、架构、dSYM UUID、源码和历史包完整性见 `verification.json`。

## 性能与数据

保留原有单次定时唤醒、有界队列、超时清理、设置缓存和异步账本写入。手动观察来源最多 384 条、有效期 24 小时，按需清理，不周期轮询。功能关闭时跳过请求解析；未新增调试日志、主线程同步磁盘读写或常驻轮询。

保留 `payment-ledger-v1.plist` 和旧统计键格式，不重置旧记录。1.8-14 漏记的历史金额没有可靠成功明细，不能自动追补。手动观察依赖本次运行识别过的来源；重启前的未识别旧消息不凭估计归属补记。

## 最小设备验收

安装 1.8-15 后彻底退出并重开微信，核对对应私聊/群聊范围、自动回复开关及回复文本。用少量真实交易检查：

1. 私聊与群聊各一笔转给本人的转账：自动收款、回复、次数和金额一致；另一笔在等待期间手动收款仍只累计一次。
2. 私聊与群聊各一个本人可领红包：自动领取、回复、次数和实际领取金额一致。
3. 关闭“红包自动回复”再领取：不回复，记录继续累计。
4. 群内他人之间转账及他人的专属红包：不自动领取、不回复、不增加本人的记录。

手机上的网络、原生支付状态与其他插件组合仍需这组实际操作确认。本地替身测试不能替代真机支付验收。
