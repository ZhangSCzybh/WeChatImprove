# Independent review of collected native navigation evidence

This review reads the source and the already-collected targeted disassembly. It does not execute WeChat and does not replace the unavailable device property logs. The reverse-engineer-anything skill's distinction between static observation, inference and runtime unknowns applies.

The binary at the recorded extracted path is still present and hashes to `571c5b8cf8732eb5402ffddcbeb93830cb6695bad180be5613ad4167764524e9`, equal to both REA target binding and collector provenance. The metadata reader and selector annotator hashes also match. All 16 annotated disassemblies preserve their raw files' complete instruction sequences; comments are additions only. Details are in `independent-static-review.json`.

## Supported static conclusions

1. `MMUIViewController -initWithNibName:bundle:` (`@32@0:8@16@24`, IMP `0x115878564`) sends `setHidesBottomBarWhenPushed:YES` at `0x1158785cc..0x1158785dc` after its superclass initializer succeeds. `CSNativeSettingsHost.m` dynamically subclasses this native class and overrides only `viewDidLoad`/`viewDidAppear:`, not the initializer. Its plugin root content is a child controller. This establishes the structural difference from directly pushed UIKit plugin children, whose source did not declare the hide policy before this fix. The actual initializer dispatch and instantiated class in the recording remain runtime unknowns.

2. `WCTabBarController -transitionForNavigationController:destinationViewController:animated:` (`@36@0:8@16@24B32`, IMP `0x1157db5d4`) reads the destination VC's `hidesBottomBarWhenPushed` at `0x1157db648..0x1157db654` when navigation depth is at least two. It separately derives `sourceHidden` from an existing transition, current native hidden state, and the coordinator's source VC. It stores that result and the destination result as `sourceHidden`/`targetHidden` (`0x1157db828..0x1157db8b8`). The destination policy is read before the transition's prepare phase; setting it only in an appearance callback could be too late.

3. `-prepareTabBarForTransition:` (`v24@0:8@16`, IMP `0x1157db994`) branches on `targetHidden` at `0x1157dbacc..0x1157dbad8`. For a showing destination, it explicitly calls native `setTabBarHidden:NO animated:NO` at `0x1157dbb58..0x1157dbb68`, performs layout, makes a native snapshot, and installs the transition view in the destination view. For a hiding destination it creates a snapshot for the outgoing view and calls native `setTabBarHidden:YES animated:NO` at `0x1157dbd28..0x1157dbd38`. The code also resets native bar alpha/transform at preparation. This supports a mechanism where changing destination policy overrides the previously hidden root state, and explains why a styled native capsule/snapshot can move with a pushed child. It does not establish whether the observed pixels are the live bar or snapshot at a particular frame.

4. `-finishTabBarTransition:cancelled:` (`v28@0:8@16B24`, IMP `0x1157dc26c`) selects source or target hidden state based on cancellation, restores native alpha/transform/interaction, sends `setTabBarHidden:selectedState animated:NO` at `0x1157dc3e0..0x1157dc3f0`, then removes the snapshot and clears transition views. `-syncTabBarVisibilityForNavigationController:` (`v24@0:8@16`, IMP `0x1157dbfec`) verifies that this is the selected navigation controller, reads its top VC's hide policy for depth≥2, and sends it to native `setTabBarHidden:animated:` at `0x1157dc084..0x1157dc0bc`. At navigation depth one it selects `NO`. These are concrete native visibility writers; main-screen restoration should remain owned by these existing paths.

5. `Hooks/TabBarStyleHooks.xm` forwards the caller's unchanged `hidden`/`alpha` arguments through `%orig` for both `MMTabBar` and `WCTabBarView`. `Controllers/CSTabBarNativeAdapter.m` changes surfaces, icon layout, native-background child visibility and snapshots, but the reviewed source does not assign the bar's `hidden` or `alpha`. Its explicit purpose is retaining native navigation visibility. The style code can faithfully style a native transition snapshot; styling a visible capsule does not establish that this style hook forced it to show.

## Attribution to 2.2-18

Five relevant navigation and style files are byte-identical between the frozen 2.2-17 and 2.2-18 sources: native settings host, shared settings table base, settings presentation helper, tab-bar hooks and tab-bar adapter. The 2.2-18 functional change in `CSCustomViewController.m` configures section-header estimates, not destination hide policy. This is evidence that the missing declaration exists in the earlier frozen source too. It is not a recording of 2.2-17 reproducing the defect and does not establish the earliest affected version.

## Remaining runtime boundary

The static call graph is sufficient to justify declaring a plugin-owned destination's policy **before push**, at the VC/navigation contract level. It is not sufficient to claim the device's `hidden`, `alpha`, `superview`, object `frame`, `window`, actual modal/child status, callback order, native snapshots or touch interception were logged. Those remain **未验证**. The video pop ROI counterexample must also be preserved: the capsule survives f096/f144 outside the original fixed bottom ROI and slides off with the child.
