# 备份配置与收藏备份消失分析

分析日期：2026-10-22（Asia/Shanghai）。源码：`main`，`f82de8039c43770076d039ccc8e9f7ab4120a134`，版本 `1.9-5`。

本文件记录修复前的分析与复现；后续 `1.9-6` 的最终实现及交付见 [备份保护修复记录](../backup-retention-fix-1.9-6/README.md)。

用户补充：没有手动删除，自动备份或更新后消失；原备份可能是自己点击“创建备份”生成，也可能记不清类型。以下明确区分源码确定行为、临时数据复现结果和设备端尚未核实的事实。

## 结论与适用范围

1. 当前源码没有“清空全部备份”入口。真实删除路径是单份手动删除和保留数量清理；导出结束清理的是临时分享文件。
2. 自动清理存在可复现的数据保护缺陷：收藏状态只存在同 ID 的 `.meta` 文件中。读取失败一律返回空字典，导致原收藏的自动/操作保护备份被按未收藏处理，超过数量后直接删除且不报告元数据错误。
3. **上述缺陷不解释真正的手动备份被自动删除。** “创建备份”固定写入 `kind=manual`，保留策略对它直接跳过；元数据损坏也不改变类型。正常与损坏收藏标记下，模拟升级保存都保留手动备份。
4. 列表消失不等于文件已删除。`.wcbak` 校验失败会被排除在可恢复列表之外，文件仍保留；当前 UI 没有按文件列出异常条目的管理区。
5. 当前没有访问手机容器，实际安装版本、消失文件的 `kind`、`.wcbak` 是否仍存在，以及 `.meta` 是否发生异常均未确认。因此不能把已发现的条件性缺陷认定为本次手机事件的唯一根因。

## 项目框架与功能

这是运行在 iPhone 微信进程中的 Theos 插件，使用 Objective-C / Logos、UIKit 和微信私有接口；最低编译目标 iOS 15，目标架构 `arm64` / `arm64e`。`Makefile` 自动收集 `Hooks/*.xm` 与 `Controllers/*.m`，使用 ARC，输出 Debian 安装包。

`Hooks/` 接入微信界面与生命周期；`Controllers/` 包含业务策略、原生接口适配、渲染及设置页；`Headers/` 和 `HeadersFile/` 提供项目与微信私有接口声明；`Tests/` 使用 macOS Foundation 和必要替身验证策略、存储及事务。

主要功能包括会话分组、列表/气泡/导航/底栏外观、消息手势与转发、防撤回、红包和收款自动化、密友保护，以及入口、版本、备份与重置管理。多数设置写入 `NSUserDefaults`，账号分组保存原账号归属；密友另外使用加密文件和 Keychain。

本项目没有前后端服务、交付 URL 或监听端口。这里的验证是 macOS 临时文件测试，没有启动或切换微信运行环境。

## 配置、文件与数据边界

运行时根目录由微信进程自己的 `NSLibraryDirectory` 决定；具体 iOS 容器 UUID 本轮未读取。`CSBackupManager.m:32–37` 绑定以下位置：

```text
<当前微信容器>/Library/
├── Application Support/WeChatImprove/BackupV2/
│   ├── <UUID>.wcbak          # 不可变完整快照：kind、来源、配置、图片、完整性
│   ├── <UUID>.meta           # 可变本机元数据：收藏、显示名、importedAt
│   ├── transaction.plist     # 待处理/处理中恢复或重置事务
│   ├── last-transaction.plist
│   └── activation.plist
├── Backup/                  # 旧版目录，只读兼容
└── Preferences/WeChatImprove/ # 当前自定义图片资源
```

配置域有三个：宿主标准域（取实际 bundle identifier，默认 `com.tencent.xin`）、`com.cyansmoke.wechattweak`、`com.wechat.enhance`。登记表覆盖 313 个固定键及受约束的账号选中分组键；并非整个微信偏好域的镜像。

快照包括已登记插件设置、可读取的相关图片和账号分组。它不包含备份历史/收藏元数据、微信聊天记录、登录凭据、授权缓存或支付账本/累计统计。当前密友状态保存在独立的 `Application Support/WeChatImprove/CloseFriends` 和 Keychain，也没有接入这套备份。

因此，“完整备份”指这套登记范围的完整快照；恢复一份配置快照不会重建整个备份目录及其收藏历史。

## 创建、恢复与自动保存链路

- 手动创建：页面 → `Manager.create` → `Engine.save(kind=manual)` → 一致性捕获与资源打包 → 编码校验 → 原子发布 `.wcbak` → `Store.prune`。
- 自动保存：配置/资源或前台通知 → 标记待检查 → 前台、开关开启且到期后尝试。每 10 秒检查调度，静默目标 30 秒，持续修改约 5 分钟检查一次，失败约 60 秒后再试。相同账号/安装来源最近的自动快照内容未变时直接复用，忽略仅分组当前选中状态的变化。
- 版本更新：比较 `protectedVersion` 和当前插件版本 → 插件已就绪且没有未完成事务时保存 `kind=upgrade` → 写入成功版本标记。此检查不受“自动备份”开关控制。
- 恢复/重置：选择模块与原所属账号 → 预览差异 → 保存保护快照并记录事务 → 用户手动重新打开微信 → 校验账号和配置版本 → 应用、回读核验、确认启动；中断可按日志回滚。准备计划不会立即覆盖当前配置。
- 导入：校验并发布，额外写入本机 `importedAt`，不自动应用。导出：仅编码快照到系统临时目录，分享结束移除临时副本。

`Engine.save` 在每次新快照成功发布后统一调用清理，故手动创建、自动保存、版本更新都可能触发已有历史的数量清理。自动去重直接复用旧文件时不执行该次清理。恢复准备直接 `publish` 保护文件，本身不调用 `prune`。

## 清理与删除的精确规则

`CSBackupStore.m:120–128` 按快照内部 `createdAt` 从新到旧遍历：

| 类型/条件 | 当前行为 |
| --- | --- |
| `automatic` | 普通清理候选保留最新 20 份，超额尝试删除 |
| `protection`、`upgrade` | 合并一个计数，普通候选保留最新 5 份 |
| `manual`、`imported` | 没有自动清理额度，直接跳过 |
| 可读 `.meta` 中 `favorite=true` | 跳过，不占上述额度 |
| 可读 `.meta` 有 `importedAt` | 跳过，不占上述额度，即使文件内原类型是 automatic |
| 当前恢复日志引用的 source/protection | 底层删除拒绝，因此保留；它们仍可能计入普通候选计数 |
| `.wcbak` 损坏或不兼容 | 扫描返回错误，本次 `prune` 中止，原文件保留 |

数量按整个 `BackupV2` 目录计算，没有按微信账号、插件版本或安装来源分开计数。关闭自动备份只停止调度自动保存；升级保存和手动保存仍可触发清理。

单份“删除备份”由 `CSBackupSettingsViewController.m:191` 经 `Manager.remove` 调到 `Store.remove`。底层仅检查 UUID 和恢复事务引用，**不检查收藏状态**。收藏在当前文案中的含义是“不自动清理”，不是禁止用户主动删除。该路径与用户“没有手动删除”的描述不一致，不能据此解释本次事件。

删除仅移除 `.wcbak`，对应 `.meta` 没有同步移除。恢复日志归档只删除 `transaction.plist`；重置只修改选中登记配置；分享完成只删除临时导出文件。没有发现这些路径递归清空 `BackupV2`。

## 已复现缺陷：收藏元数据读取失败后丢失保护

收藏动作只写 `.meta`，不写回不可变 `.wcbak`。读取逻辑如下（`CSBackupStore.m:82–85`）：

```objc
NSData *data = CSBackupReadFile(url, 16384, NULL);
id value = data ? [NSPropertyListSerialization propertyListWithData:data
    options:0 format:NULL error:NULL] : nil;
return [value isKindOfClass:NSDictionary.class] ? value : @{};
```

文件缺失、损坏、超出 16 KiB、不是普通文件或其他读取失败，都变成空字典，错误被丢弃。`prune` 随后读取空字典的 `favorite` 得到 false，于是继续计数和删除。这把“无法确认收藏状态”错误地处理成“确定未收藏”。

复现中先保存收藏，确认能读出 true，再故意破坏隔离的元数据；准备超过额度的新快照后，调用生产 `prune` 或生产 `Engine.save(kind=upgrade)`。前者真实删除旧文件，后者成功创建版本快照同时真实删除旧文件；均不返回元数据错误。

测试也确认写入端未限制 `.meta` 大小，而读取端只接受 16 KiB。超大元数据是人工构造的防御边界场景；正常 UI 的名称长度有限，没有证据表明实际用户操作会自然生成这个大小。

**重要限制：这条路径仅影响有清理额度的类型。** 手动备份即使元数据损坏，也在 `!quota` 条件直接跳过，模拟升级保存后仍然存在。需要先核对原始 `kind`，不能仅看用户自定义的显示名称。

## 另一条路径：快照仍在，但不显示

`Store.snapshots` 只把通过当前 codec 完整验证的 `.wcbak` 加入列表。校验失败时保留文件，报告“损坏或不兼容的文件已保留，未列入可恢复备份”。收藏不能绕过这项验证。

因此手动/收藏快照也可能从列表消失，而没有经过删除逻辑。复现确认：一份收藏快照内容失效后，列表数量为 0、文件仍存在、收藏元数据仍正常，`prune` 返回错误并中止。

本次只模拟了“快照无法通过校验”，未证明某次实际升级制造了不兼容。Git 对比显示，自 `1109280c`（1.8-41 提交）至当前 HEAD，`CSBackupStore`、`CSBackupEngine`、`CSBackupManager`、`CSBackupRegistry`、`CSBackupCodec` 没有源码变化；不能把近期版本号变化本身视为兼容性失效证据。

## 对本次手机现象的核对顺序

1. 确认实际运行插件版本和微信 bundle/容器，保留原 `BackupV2`、旧 `Library/Backup`、日志和偏好信息的副本。单纯在同一个微信应用内切换账号不会让当前列表按账号过滤：`Manager.list` 没有账号过滤条件。
2. 检查原 `.wcbak` 是否存在；存在则核对文件名与内部 UUID、`kind`、完整性及具体解码错误。尤其检查页面是否出现“损坏或不兼容”的提示。
3. `.wcbak` 不存在而对应 `.meta` 留存，符合当前删除实现留下孤立元数据的形态，但仅凭这点无法区分主动删除、自动清理或外部文件操作。
4. 若确认原始 `kind=automatic/protection/upgrade`，进一步检查收藏 `.meta` 的状态、时间与可读性，以及目录候选数量和版本更新时间；这与已复现的元数据误判路径相符。
5. 若确认原始 `kind=manual`，应继续追踪实际安装代码、读目录/校验失败和容器文件变动；当前 `prune` 无法解释其被删除。缺少设备目录与操作记录时，不给出确定的现场归因。

## 建议的修复边界

1. 将元数据读取区分为“有效”“预期未创建”“异常不可读”，异常时保留对应快照并报告，不继续推定未收藏。
2. 对“元数据丢失”采用持久保护记录或冗余索引。当前普通自动快照原本可以没有 `.meta`；仅把“所有缺失 .meta 都跳过”会让现有自动清理基本失效，不能作为完整修复。需要明确新快照元数据初始化、旧数据兼容以及收藏记录的恢复办法。
3. 清理保留可审计结果：删除 ID、类型、原因、是否读到元数据及错误；快照发布成功和历史清理结果分开报告。当前 `prune` 丢弃单份删除错误，`Engine.save` 又通过 `prune:NULL` 不向调用方报告清理问题。
4. 页面保留“异常但文件仍在”的条目和具体原因，提供导出原件、重试校验等处理方式，避免把列表移除呈现成文件丢失。
5. 如需增加“清空普通备份”，集中复用保护规则，默认保留收藏、手动和事务引用，并明确展示将删除哪些文件。主动删除收藏可增加专属提示；这是交互策略变化，不是本次未手动删除现象的证据。

本轮仅做分析及隔离诊断，没有修改上述生产行为。
