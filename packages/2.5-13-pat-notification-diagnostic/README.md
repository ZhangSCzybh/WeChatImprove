# 2.5-13+diag.1 群后台拍动通知定位包

本包用于定位 **群聊后台／锁屏时必须回到微信前台才回复，而私聊后台正常** 的问题。基于正式 `2.5-13`（`65193f29b33988b0154bdfe96372d8d86dde64fc`）；当前问题尚未解决，本包不宣称修复或秒回。用户已确认测试群未开启消息免打扰、未折叠。

## 安装与采样

用户当前使用 Rootless：安装本目录 `com.wechat.improve_2.5-13+diag.1_iphoneos-arm64.deb`，按包管理器提示重新加载微信。包内含 arm64 / arm64e，最低 iOS 15.0；包标识仍为 `com.wechat.improve`。在插件中确认显示版本 `2.5-13+diag.1`。

本轮只需 **一份采样**，在同一轮内比较群聊和私聊：

1. 保留原账号、目标群及已有生效名单；确保用于对照的私聊也在同一拍动功能的生效名单中，执行延迟为 0。进入插件“自动功能”底部“临时拍动定位”，点“开始新一轮采样”。
2. 将接收端微信退到后台并锁屏。由另一端先在目标群拍一次，记下大概时刻；保持接收端锁屏，等约 20 秒。
3. 再从已生效的私聊拍同一接收者一次，继续保持接收端锁屏约 20 秒。记下私聊是否立即回复，以及此前群回复是否在这时一起出现。
4. 最后才打开接收端微信，进入同一页面点“停止并导出”。保存 `WeChatImprove-2.5-13-diag1-…json`，同时说明群触发、私聊触发和回前台的大概时刻。

不要为了确认聊天记录而在步骤 2、3 中途打开接收端微信；回前台本身会改变同步与任务执行条件。如果已经打开，保留本轮并说明时刻。此前“接收端聊天记录已显示拍动后仍等待”的观察仍然有效，本次对照用于定位当前版本的新阻塞点。

## 记录了什么

- 微信原生通知、APNs 同步入口、两种长连接数据推送、原生同步请求与响应、前后台在线状态上报、通知数据消息处理。
- 已有事件同步的唤醒、主队列接续、账号／服务检查、need／busy／pause 等状态与请求返回。
- 原始拍动快照、解析、持久认领、群资料检查、任务等待、文字／回拍提交、文字原生成功／失败回调。
- 每 2 秒一条本地 `runtime.pulse`，只证明该时刻主队列获得过执行机会。间隔较大可能是挂起或主队列阻塞，不能单凭空白认定没有收到推送。

本包沿用 2.5-13 的收发、配置、去重和同步策略。采样探针不发起同步，不修改微信在线模式或原生状态。`runtime.pulse` 是本地记录计时器，不是网络补拉。成功回调不等于对方最终收到或看到消息。

采样默认关闭，每轮最多 10 分钟／4000 条，内存保存；停止、清空、到期及容量上限按原诊断规则处理。微信退出会丢失当前记录。导出不包含账号、群号、成员、消息正文、XML、原始服务端消息编号或随机盐。匿名键仅可在本轮内关联。`protected_available` 不是锁屏真值。

## 本轮结论和验证边界

静态核对确认：群／私共用原生 `OnGetNewXmlMsg` 与 `addPatWrap`，插件也共用同一套发送核心。群聊有连续拍动展示记录合并分支，但现有共同 `addPatWrap` Hook 已覆盖正常返回。群提交前额外检查群资料、成员身份与退出状态；目前没有本版手机记录证明这些检查被阻塞。

微信前后台会分别上报不同 `onlineMode`，APNs／数据推送也并非都经过 `setNeedSyncWithScene:`。这些是已观察到的原生代码差异，不能据此断定服务端群推送策略或本次手机故障的根因。旧 2.5-11 采样不能证明 2.5-13 的实际接收路径。

本机验证已包含：记录器与发送关联、原调用透传与 ABI 拒绝、原始拍动解析、开启／关闭诊断的 Manager 与同步集成，以及 Rootless 双架构编译。原生探针专项 2081 项通过；真实记录器同步集成保留原有 528 项断言，并验证新增同步阶段顺序。手机后台与锁屏行为仍待本轮采样，测试夹具不代表手机实际到达或送达。

451 项冻结生产输入一致；成品版本、Rootless 路径、双架构、iOS 15.0、dSYM UUID、symbols.zip CRC 和 SHA-256 已核验。78 个历史包文件的 SHA-256、大小与修改时间保持。正式源码仍为 2.5-13，诊断代码以独立补丁归档，见 [可复现源码和验证记录](../../docs/audits/pat-notification-diag-2.5-13/README.md)。
