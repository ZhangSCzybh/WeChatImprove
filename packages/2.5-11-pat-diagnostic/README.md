# 2.5-11+diag.1 临时拍动定位包

本包以正式版 `2.5-11`（提交 `39930b3d31e54d8719eca1494e13f1f801f10b5b`）为基础，只为定位“拍我后自动回拍 / 回复较慢”的具体等待阶段。正式项目目录和 GitHub 发布不切换到诊断版；源码及构建材料保留在本地审计目录。

- 包版本：`2.5-11+diag.1`。
- 包标识：`com.wechat.improve`，与正式版相同。
- 平台：仅 rootless；包架构为 `iphoneos-arm64`，插件包含 arm64 / arm64e。
- 正式回退版本：`2.5-11`。诊断完成后安装同一包标识的正式版；包管理器如提示降级，应选择正式版 `2.5-11`。
- 本文为诊断操作说明；最终包校验值、编译和回归结果由构建记录提供。

## 采样方式和数据范围

在插件“自动功能”页面底部进入“临时拍动定位”分组：

| 操作 | 行为 |
| --- | --- |
| 开始新一轮采样 | 清空上一轮内存记录，生成本轮随机盐并开始采样。 |
| 停止采样 | 停止加入新记录，保留本轮记录供导出。 |
| 停止并导出 | 先停止采样，再将 JSON 文件交给系统分享面板。 |
| 清空采样 | 停止采样，并清除本轮内存记录。 |

每轮最多 600 秒，最多保存 4000 条记录；到达时间上限即停止，存满后再有记录时停止并丢弃该条新记录。采样初始关闭，必须手动开始。采样期间记录只保存在进程内存中，不持续写磁盘；微信被系统终止或插件重新加载后，本轮内存记录会丢失。导出时仅将当前快照写入一个临时 JSON 文件，分享流程结束后移除该临时文件。

记录内容仅用于比较各阶段的先后和耗时：固定阶段名、本轮相对时间、匿名事件关联键、进程内账号代次数字、有限的状态标志、是否主线程、缓存的应用状态和受保护数据状态。事件关联键由本轮随机盐、事件服务端 ID 和账号代次计算摘要；不导出原始服务端 ID 或随机盐，新一轮采样不能与上一轮关联。

不导出账号 ID、联系人、群 ID、昵称、消息文本、XML、AI 提示词、密钥、照片或其他消息附件。记录器使用已有事件字典和已有局部结果，不为定位额外读取原生消息内容或原生账号信息。

`protected_available` 仅表示 iOS 受保护数据是否可用，**不能直接当作手机锁屏状态**。`app_state` 表示当时缓存的应用生命周期状态。锁屏与后台场景应以实际操作记录为准，并结合导出的生命周期阶段分析。

## 四个对照场景

先保持当前账号、群、自动功能名单、开关、回复文案及用户延迟配置不变，并记下当前延迟秒数。使用另一台设备或另一位参与者触发“拍我”，从发送端观察自动回拍 / 回复是否出现以及端到端耗时。每个场景单独开始一轮采样并单独导出，共四份文件。

同一场景连续触发两次，两次间隔 20–30 秒。使用相同发送者、相同接收者；前三个场景使用同一个群。为保留后台和锁屏证据，观察期间不要点通知、解锁接收端或将接收端微信切回前台。

1. **群聊前台**：在接收端开始采样，再进入目标群并保持微信前台。发送端在该群拍接收者两次，间隔 20–30 秒；记录发送端观察到的回拍 / 回复时间。
2. **同群后台**：开始新一轮采样，在接收端进入同一群后切换到其他 App，保持接收端微信后台。发送端按相同方式触发两次并观察。
3. **同群锁屏**：开始新一轮采样，在接收端进入同一群后锁屏。保持锁屏，发送端在群中触发两次并观察。
4. **私聊锁屏**：开始新一轮采样，在接收端进入对应私聊后锁屏。保持锁屏，发送端在私聊中触发两次并观察。

每个场景在第二次触发后，如仍未观察到回复，再等待至少 30 秒才将接收端微信切回前台导出。返回前台可能使微信主动同步或恢复处理，因此必须保留返回前后的生命周期记录；“回前台后才回复”也是有效定位结果。不要为重新开始而清除微信数据、变更账号或重置插件配置。

导出文件请分别标记“群前台”“群后台”“群锁屏”“私聊锁屏”。另用普通文字记录每次触发时间、回拍 / 回复是否出现、发送端观察到的耗时及接收端是否曾被意外唤醒。导出的时间是每轮相对时间，不含发送端的真实触发时间，故端到端耗时仍需发送端观察记录。

## 如何判断等待阶段

定位时先按匿名事件键把同一拍动的阶段串起来，再比较相邻阶段的相对时间；无事件键的同步和生命周期记录用于提供上下文。

| 观察结果 | 可以支持的判断 |
| --- | --- |
| 发送端已触发，但接收端直到很晚才出现拍动入站阶段 | 等待主要发生在插件获得拍动事件之前；结合后台补拉请求、原生接受结果和生命周期继续判断。没有入站记录不能单独证明服务端未发送。 |
| 已有事件解析成功，但持久认领开始或结束明显较晚 | 等待位于事件接纳、I/O 排队或运行记录持久保存环节；需比较对应阶段，不能只因代码包含 `fsync` 就判定原因。 |
| 认领完成后，直到用户延迟到期才提交动作 | 对照当前配置的用户延迟；这是预期调度的一部分。 |
| 到期后反复出现账号、群成员、原生接口等暂不可用状态 | 动作已具备事件，正在等待发送条件；查看明确拒绝阶段，不根据汇总状态猜测。 |
| 原生发送提交及时，但发送端很晚才看到结果 | 插件交接之后仍有微信原生处理或网络等待；“已提交”不等于对方已收到。 |
| 返回前台后才出现入站 / 提交 | 结合前台生命周期阶段，区分恢复同步和恢复执行；不把回前台后的耗时当成锁屏下持续运行的证据。 |

2.5-11 中拍动后台约 10 秒补拉、提交前忙碌约 2 秒复查仍沿用正式策略；它们不保证 10 秒内响应，也不向 iOS 申请新的执行机会。原生推送及时到达时，不要求每个拍动先等待一次补拉周期。用于可选撤回的 30 秒结果观察发生在回拍提交之后，不是首发固定延迟。

退群本地提示通过 `AddLocalMsg` 直接插入本地聊天记录；入群欢迎和可选退群群发走文本发送，而真正回拍走 `SendPatMgr`。因此这些功能的可见速度只能作对照，不能把本地提示时间直接等同于网络回拍时间。

## JSON 字段与 flags

JSON 顶层包含版本、schema、是否仍在采样、停止原因、已采样时长、上限、满容量时丢弃的新记录数，以及 `records` 数组。停止原因 `manual` 为手动停止，`expired` 为时间到期，`capacity` 为存满后遇到下一条记录，`record_error` 为记录器异常后自动停止，`not_started` 为尚未开始。

每条记录使用以下字段；没有真实事件服务端身份的生命周期、同步或早期拒绝记录，`key` 为空字符串，不可把它们视为同一个真实拍动。

| 字段 | 含义 |
| --- | --- |
| `t_ms` | 从本轮开始起的单调时钟毫秒数。 |
| `stage` | 固定允许列表中的阶段名。 |
| `key` | 本轮匿名事件关联键；同一真实服务端事件和相同账号代次在各阶段一致。 |
| `epoch` | 进程内账号代次；0 表示该位置没有已知代次，不是账号 ID。 |
| `flags` | 下表定义的位标志或有限数值；含义随阶段变化。 |
| `main` | 是否在主线程记录。 |
| `app_state` | 缓存的应用状态：0 前台、1 暂时非活动、2 后台、-1 未知。 |
| `protected_available` | 缓存的 iOS 受保护数据可用状态，不是锁屏真值。 |

下表中的 bit0、bit1、bit2 对应数值 1、2、4；“数量”“枚举”“索引”按整数读取，不按位读取。未列出的生产阶段 `flags=0`，阶段名本身描述拒绝、异常、进入或返回位置。

| 阶段 | flags 含义 |
| --- | --- |
| `hook.add.enter`、`hook.async.enter`、`hook.sync.enter`、`hook.notadd.enter` | bit0：消息对象非空。 |
| `hook.publish.enqueue` | bit0：既有流程判断为本插件发送的消息。 |
| `hook.publish.main` | bit0：原始拍动命中微信撤回表。 |
| `hook.raw.deliver`、`hook.direct.deliver`、`hook.batch.deliver` | bit0：群会话。 |
| `hook.compound.accept` | bit0：使用快照；bit1：群会话。 |
| `hook.compound.reject` | bit0：使用快照。 |
| `hook.batch.raw.snapshot` | bit0：原始 from 字段以 `@chatroom` 结尾；不代表其他路由不能属于群。 |
| `hook.batch.enter` | bit0：微信原调用的 fromPush；bit1：showPush。 |
| `hook.batch.native.before`、`hook.batch.enqueue`、`hook.batch.main` | 当前候选事件数量。 |
| `hook.batch.native.return` | bit0：微信原批次调用返回接受。 |
| `hook.direct.native.before` | bit0：pat 对象非空；bit1：newXML 非空。 |
| `hook.direct.native.return` | bit0：localID 非零；bit1：newXML 非空；bit2：pat 对象非空。 |
| `parse.raw.accept` | bit0：群会话；bit1：匹配到原生精确 sender 前导结构。 |
| `parse.pat.accept`、`pat.converted` | bit0：群会话。 |
| `pat.queued` | bit0：配置 ready；bit1：正在 loading；bit2：正在 saving。 |
| `event.decisions` | 已有决策产生的动作数量。 |
| `admit.begin`、`admit.existing`、`claim.no_storage`、`claim.queued`、`claim.io_begin`、`claim.main`、`task.created`、`task.retry_5s`、`gate.begin`、`text.begin`、`pat_action.begin` | 低两位：1 为回拍、2 为文字回复；bit2：群会话；右移 16 位后为当前动作用户延迟秒数，范围 0–300。 |

| `claim.retry_5s` | bit0：存储错误允许重试；bit1：账号能力暂不可用。 |
| `gate.final` | bit0：最终发送条件检查通过。 |
| `pat_action.invoke_return` | bit0：获得已交接的回拍对象；bit1：提交条件拒绝；bit2：原生能力暂不可用，允许延后。 |
