# 2.5-11+diag.2 临时文字回复定位包

第二版定位包沿用第一版的采样入口，在原有“拍动入站 → 解析 → 持久认领 → 发送提交”记录后，新增微信文字消息成功 / 失败回调的时间与关联信息。本轮针对已观察到的情况：**接收端聊天记录已显示拍动，自动文字回复随后才出现**。人工观察继续采用接收端聊天记录显示拍动的起点，结合另一端看到文字的时间，定位提交前后各段等待。

| 项目 | 本包约定 |
| --- | --- |
| 版本 | `2.5-11+diag.2` |
| 包标识 | `com.wechat.improve`，与正式版相同 |
| 平台 | 仅 rootless；`iphoneos-arm64` 包，插件含 arm64 / arm64e，最低 iOS 15.0 |
| 正式回退 | 安装同一包标识的正式版 `2.5-11`；包管理器如提示降级，选择正式版 |
| 源码基线 | 正式提交 `39930b3d31e54d8719eca1494e13f1f801f10b5b`，保留第一版诊断逻辑后增加本次采样 |
| 保存边界 | 正式工作目录与第一版审计、构建和成品保留；第二版使用独立审计目录和构建目录 |

本包记录微信回调事实，不改变文字发送、等待、重试、去重或自动功能配置。成功回调意味着微信原生成功路径执行，**不等同于对方最终收到或看到消息**。没有看到回调，也不能直接认定为网络超时或微信回调丢失；需要同时查看回调 Hook 的安装状态、采样是否仍有效及发送关联记录。

## 使用采样入口

进入插件“自动功能”页面底部“临时拍动定位”分组：

- **开始新一轮采样**：覆盖上一轮内存记录，使用新的随机盐开始记录。
- **停止采样**：停止新增记录，保留当前记录。
- **停止并导出**：停止后生成 JSON，通过系统分享面板导出。
- **清空采样**：停止并清除当前内存记录。

采样默认关闭。每轮最多 600 秒，最多保存 4000 条记录；时间到期停止，存满后再有记录时停止并丢弃该条新记录。采样期间不持续写磁盘；微信退出、被系统终止或插件重新加载会丢失本轮内存记录。导出只产生一份临时 JSON 文件，分享流程结束后移除该临时文件。

保留原有固定阶段、相对时间、匿名事件关联键和有限状态，新版只为已关联的自动文字回复补充元数据和成功 / 失败回调阶段。本轮内存最多保留 128 个回复关联；停止、清空、时间到期或容量停止时清除关联元数据。导出不包含账号、联系人、群 ID、昵称、消息正文、XML、附件、密钥、原始服务端消息 ID 或本轮随机盐。不同轮次的匿名键不能相互关联。

`protected_available` 仅表示 iOS 受保护数据是否可用，不能作为手机锁屏真值；`app_state` 为缓存的应用生命周期状态。实际锁屏、解锁和前后台操作请按下面步骤记录。

## 本轮只做两个场景

沿用已确认的定位配置：**只开启“拍我自动回复”，本模块延迟为 0 秒，关闭自动回拍**；保持现有账号、目标群、生效名单和回复文案。使用同一个群、同一个触发者，两次触发间隔 20–30 秒。观察尽量在另一端完成，不通过点击通知或打开接收端微信来催出回复。

1. **群锁屏主场景**：在接收端开始新一轮采样，进入目标群后锁屏；保持锁屏，由另一端拍接收者两次，两次间隔 20–30 秒。记录另一端实际看到每次文字回复的时刻。实际看到回复后，至少再等待 10 秒才解锁接收端并导出；第二次仍未看到回复时，等待 30 秒再回到接收端微信导出。保留返回前台前后的记录。
2. **群前台对照**：开始新一轮采样，接收端停留在同一群的聊天界面；由相同触发者拍两次，间隔 20–30 秒。继续从另一端观察回复。最后一次文字出现后至少再等 10 秒，或最后一次触发 30 秒仍未见回复时，停止并导出。

分别保存“群锁屏”和“群前台”两份文件；系统分享中的导出文件名前缀为 `WeChatImprove-2.5-11-diag2-`。另记录两次触发、接收端聊天记录中拍动起点和另一端实际看到文字的时间，以及接收端是否被意外解锁或切回前台。既有起点按实际观察保留，不需要为了补采样而反复唤醒接收端确认。

如必须回到接收端微信才能导出，记录该操作时间；回到前台可能触发新的同步和处理，导出的生命周期阶段可帮助区分恢复前后发生的事件。不要重置微信数据、重新登录、清空账号配置或覆盖原有群名单。

## 如何阅读新增证据

先找到同一拍动的匿名 `key`，查看原有的解析、持久认领、任务和 `text.invoke_begin` / `text.invoke_return`，再查看 `reply.track`、`reply.update` 与对应 `reply.callback.begin` / `reply.callback.end`。`reply.hook.state` 记录成功、失败回调的安装可用性，应与本轮记录一起看。

| 观察 | 可以支持的结论 |
| --- | --- |
| 拍动已进入处理，但认领或任务建立较晚 | 等待位于自动功能提交前；结合排队、I/O、任务延迟和能力检查阶段定位。 |
| 文字提交及时，成功或失败回调很晚 | 已将等待缩小到文字交接后的原生处理 / 回调路径；与另一端可见时间对照。 |
| 成功回调及时，另一端稍后才看到文字 | 回调和对方可见是不同阶段；回调不能单独证明最终送达。 |
| 发生失败回调 | 查看该次原生失败路径及前后元数据；本包不会因此新增重发。 |
| 存在提交记录但无匹配回调 | 先检查 Hook 安装状态、关联是否成功、记录是否到期或已满、是否跨账号 / 新一轮采样；没有回调不能单独判定根因。 |
| 回到前台后出现回调或其他后续阶段 | 保留生命周期边界，按发生顺序分析；不把回前台后的处理当作锁屏期间已经发生。 |

回调前后都保留原调用参数、结果和异常语义；采样仅观察。匿名关联在本轮内使用，匹配不成功时不会猜测关联，也不会扫描聊天记录查找候选消息。

新增记录继续使用 `t_ms`、`stage`、`key`、`epoch`、`flags`、`main`、`app_state`、`protected_available` 字段。其中 `key` 关联最初的拍动事件，元数据只以“是否存在”和“匹配方式”导出：

| 阶段 | flags |
| --- | --- |
| `reply.track`、`reply.update`、`reply.callback.begin`、`reply.callback.end` | bit2 / bit3 / bit4：分别存在本地 ID / 服务端 ID / 客户端 ID；bit5：相同消息对象和创建时间匹配；bit6：本地 ID 和创建时间匹配；bit7：服务端 ID 匹配；bit8：客户端 ID 匹配。回调阶段另有 bit0：成功选择器；End 阶段 bit1：微信原调用正常返回。 |
| `reply.hook.state` | bit0：成功选择器，否则为失败选择器；bit1：安装成功。安装未尝试时可能没有该条记录。 |
| `reply.callback.unmatched` | `key` 为空，bit0 / bit2 / bit3 / bit4 同上；bit9：存在多个候选，拒绝猜测。每个成功 / 失败选择器每轮最多 8 条。没有当前账号代次的追踪条目时，不为此读取消息元数据或记录。 |

bit0、bit1、bit2 等分别为数值 1、2、4 等二进制位。`reply.callback.end` 的原调用返回标志只说明原回调方法是否正常返回，不能解释为接收方已看到消息。

## 本地材料与验证记录

- `baseline.json`：正式基线、第一版诊断基线与第二版源目录。
- `source/`：第二版独立源码副本。
- `historical-artifacts.json`：本轮开始前 62 个历史文件的快照。
- `validation-summary.json`、`package-verification.json`：已完成的回归、构建输入、成品及历史文件核验结果。

正式 `2.5-11` 的原群管理测试包含一条历史断言，仍要求进入后台后关闭群入口并清空欢迎任务；第一版诊断已在正式版和诊断副本确认同一失败。本轮如复现该既有失败，会与新增问题分开记录，保留原断言，不作为本包通过的证据。

额外执行的 `verify-close-friend-alerts.sh` 也存在基线夹具失配：提取的群角标代码使用 `usesNativeSessionModel`、`tabBadgeSections` 等属性，旧 `CloseFriendAlertTests.m` 未声明，产生 7 个编译错误。正式工作目录和本诊断副本均已复现；相关 runner、fixture 与 `CSGroupListAdapter` 源码、头文件哈希完全相同。本包保留此限制，不将该 runner 计为通过。新增回调 Hook 有独立测试覆盖。
