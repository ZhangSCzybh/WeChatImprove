# 2.5-12 后台拍动改为事件触发同步

基于正式 2.5-11（`39930b3d`），修复后台／锁屏拍动要等插件定时补拉才进入自动功能的问题。当前已完成实现、主机回归和打包；手机实际回复时效尚待本版安装确认。

## 行为变化

在微信 **8.0.80** 且原生方法／状态 ABI 检查通过时，开启有效的拍我自动回拍或拍我自动回复配置后：

1. 微信设置待同步需求，插件在原方法返回后合并主队列唤醒，立即调用原生 `NotifyToSync`，使用微信选择的原场景。
2. 正在请求、处理数据或暂停时保留需求，实际同步完成／恢复后继续，支持原生成功续页。
3. 新入口停用拍动的 **10 秒轮询计时器**，新通知也不等待插件 **10／45 秒补拉预算**；没有待同步需求时不发起请求。
4. 调用中嵌套的 setter／reset 不产生请求循环；返回 NO 或抛异常不自动反复重试，新通知或恢复事件提供新的处理机会。

其他宿主或原生 ABI 不满足检查时保留 2.5-11 的兼容策略。AI 自己的约 45 秒后台兜底与完整同步观察规则保持。原始拍动入站、账号／授权／名单、持久去重、独立回拍和文字回复、用户设置的延迟及成功回拍后的撤回规则保持。未增加诊断开关、聊天记录采集或运行时调试日志。

具体原生依据、函数位置与推断边界见 [链路核对记录](../../docs/audits/pat-native-sync-2.5-12/README.md)。新入口是同步需求触发：收到通知便推动微信取回实际消息，然后按原自动功能执行。它不能保证网络通知尚未到达或微信已被系统挂起时仍然秒回。

## 安装包

用户当前为 **Rootless**，安装 [com.wechat.improve_2.5-12_iphoneos-arm64.deb](com.wechat.improve_2.5-12_iphoneos-arm64.deb)。安装后重启微信以载入新的 Hook，原有配置继续使用。对照测试时把回拍／回复的用户延迟设为 0，在同一个群分别测试前台、后台和锁屏；两项都开启时，同一次拍动应各回拍一次、回复一次。

同时保留 [Rootful 安装包](com.wechat.improve_2.5-12_iphoneos-arm.deb)、[Rootful 重签用 dylib](WeChatImprove.dylib)、[符号文件](symbols.zip) 和 [SHA-256 校验清单](SHA256SUMS)。旧 [2.5-11 Rootless 包](../2.5-11-pat-latency/com.wechat.improve_2.5-11_iphoneos-arm64.deb) 保留用于回退。

## 实测边界

新路径消除了插件自身轮询等待，并通过静态证据排除了事件创建之后还必须等待 `TryStartEvents` 才启动请求的假设。当前尚未直接观察本版在用户手机上的推送、网络发包、文字显示或耗电；也未证明所有群拍动都经过同一 setter 分支。系统执行机会、原生服务可用性和网络仍影响实际回复时间。

本轮使用用户原 checkout，没有更换账号、配置、数据库、注入环境或后台保活方式；未操作手机安装，也未把主机测试描述为真机验收。
